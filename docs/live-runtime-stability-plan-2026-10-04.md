# План стабилизации переходов и завершения звонка

Дата: 4 октября 2026. Ветка: `codex/hybrid-consent-feasibility`.

Статус: `live-managed-v9` реализован, полная регрессия пройдена, локальный API обновлён. Тест в 15:13–15:14 Europe/Zurich подтвердил корректное начало фразы по оценке пользователя и точное двухсекундное окно по событиям. Версия приемлема как рабочая база для этого сценария. Осталась некритичная шероховатость: самостоятельное native прощание до штатного резюме и прощания приложения. История `v8` и её неудачной приёмки первой фразы сохранена ниже. Документ продолжает [реализацию гибридного согласия](hybrid-consent-implementation-2026-10-04.md).

Предлагаются локальные исправления в существующих `UnifiedLiveCall` и `OpenAILiveConversation`: идемпотентное прощание, один таймер с точным сроком запроса backend и согласованный переход к речи после consent. Live сохраняет обычный диалог, backend — интерпретацию задачи и инструменты, приложение — разрешения, запись и обязательное воспроизведение. Отдельный управляющий слой не нужен.

## Границы изменений

Основные изменения ожидаются в [unified-live-call.ts](../apps/api/src/voice/unified-live-call.ts) и [live-conversation.ts](../apps/api/src/voice/live-conversation.ts), с регрессиями в существующих voice tests. Небольшое изменение `LiveLifecycle` допустимо только для передачи необходимого факта между этими двумя владельцами состояния. Новые сервисы, фоновые очереди, библиотеки и миграции БД на первом этапе не требуются.

Сохраняются текущий переключатель consent, оба режима `semantic_native` и `hybrid_deterministic_v1`, approved snapshots, initial disclosure, default `assistanceReason=none` и opt-in варианты причин помощи. Recording admission, AMD, appointment authorization, privacy boundary, DTMF и semantic fallback остаются действующими ограничениями.

Обычная речь остаётся native Live. План не добавляет проверку каждой реплики через LLM, классификатор конца задачи по ключевым словам, обязательное TTS-открытие разговора, новый ASR, перезапуск Live session при consent или буферизацию целых реплик ради последующей проверки. Согласованные 200/900 мс consent settle и принятый риск позднего продолжения Live deltas этим планом не пересматриваются.

Долгая подготовка плана — отдельный HTTP/durable retry flow. Её оптимизация не входит в эти изменения голосового рантайма.

## Последовательность исправлений

### 1 Сделать активное прощание идемпотентным

Это первый и наиболее определённый по причине дефект. Проверка должна происходить до отмены playback и увеличения счётчика попыток.

- Если прощание для текущего terminal decision уже рендерится или проигрывается, `keep_closing` подтверждает существующее состояние. Generation, таймер, render promise и ожидаемый mark сохраняются.
- Повторный `end_call` во время того же завершения не создаёт новое прощание. Используется существующее решение и его revision; сравнение свободного текста или новый semantic запрос для дедупликации не нужны.
- Реальное прерывание получателем продолжает отменять playback. После существующей проверки ответа `keep_closing` возобновляет разрешённое прощание, если активного playback уже нет; `resume_conversation` сохраняет существующий возврат в разговор.
- Повтор после ошибки рендера или недоставки остаётся ограниченным прежними deadline и лимитом попыток. Поздний callback от отменённого playback не отменяет текущий и не инициирует ещё один retry.
- Завершение звонка происходит один раз после актуального Twilio mark. Provider/backend completion не заменяет этот mark.

Результат: ненужные `clear`, повторный TTS и `application_interrupted` от повторного `keep_closing` исчезают как следствие исправления, а не подавления диагностики.

### 2 Убрать округление ожидания backend к следующим пяти секундам

Сейчас `scheduleTaskDecision()` ставит таймер на 5 секунд. Если `requestTaskDecision()` ещё видит недавнюю native активность, он назначает следующие полные 5 секунд. Так возникает лишнее ожидание сверх уже требуемой тишины.

Оставить один существующий timer и вычислять ближайшее время, когда запрос допустим:

`dueAt = max(answerSettledAt + nativeGraceWindow, lastNativeActivityAt + quietWindow)`

Первый патч сохраняет `quietWindow = nativeGraceWindow = 5000 ms`, чтобы отдельно проверить устранение лишнего ожидания без одновременного изменения политики вмешательства backend. Уточнение формулы при реализации: первоначальное окно для самостоятельной native реакции тоже сохраняется; иначе при отсутствии недавнего исходящего audio backend запрашивался бы сразу после settlement. Это проверено регрессиями. Таймер ждёт только остаток до `dueAt`. Повторная проверка без новых событий не переносит срок на `now + 5000`.

Новая речь, новая revision ответа или реальная native активность пересчитывают срок. При истечении таймера повторно проверяются нынешняя phase, readiness, свежесть ответа, выполняющийся или уже объявленный backend и дедупликация. Если backend занят, освобождение существующего запроса возвращает проверку readiness; циклический polling на коротком интервале не добавляется. Закрытие звонка отменяет таймер.

Один актуальный ответ не должен порождать несколько одинаковых `response.create`. Нативная модель по-прежнему может инициировать необходимый backend сама. Таймер остаётся страховкой от отсутствующего решения, а не режиссёром каждой реплики.

Уменьшение самого `quietWindow` до 1,5–2 с — возможный следующий эксперимент после измерений. В базовый патч оно не входит: сначала исключаем дискретное лишнее ожидание и проверяем отсутствие конкурирующих ответов. Это также не ускоряет автоматически собственную генерацию native подтверждения.

### 3 Согласовать переход после consent с готовностью Live

Запрос записи по affirmative остаётся немедленным. Ожидание готовности речи не переносится перед recording request и не добавляет semantic consent.

Использовать уже имеющийся механизм `suspendOutput` / подтверждения контекста / `outputFenceMs` для перехода после записи. У состояния должен быть один владелец; параллельную независимую машину состояний для opening не создавать.

1. Пока disclosure и consent принадлежат приложению, native output остаётся закрытым. Входящее audio продолжает поступать в Live без задержки.
2. После recording start передать approved task context и явный факт, что disclosure завершён, affirmative принят, запись начата, требуется перейти к задаче без повторного представления и вопроса о записи. Устранить противоречащие этому устаревшие stage instructions точечным обновлением.
3. Использовать correlation существующих команд с ACK. Готовность перехода требует подтверждения необходимых обновлений, а не только факта вызова `configureBackend()` или получения любого ACK. Независимые подтверждения не превращать в последовательность дополнительных round trips.
4. Применить существующую границу native output; не выпускать старый хвост только потому, что приложение уже сменило phase. Post-consent input и его persistence продолжают подчиняться действующей recording boundary.
5. Поздний ACK после закрытия звонка, смены generation или отмены перехода ничего не открывает. Отказ или timeout используют существующую ограниченную обработку ошибок; разрешать output «на всякий случай» нельзя.

Есть существенный предел протокола: ACK означает оценённое внедрение контекста, а не завершение речи или playback. В текущем transport native audio chunks не имеют timestamp/utterance ID. Поэтому ACK сам по себе не доказывает, что старый звук исчез. Это прямо согласуется с [официальной документацией OpenAI о Live updates](https://developers.openai.com/api/docs/guides/live-delegation#send-the-right-kind-of-update).

Приёмка перехода обязательно проверяет оба эффекта одновременно: отсутствие повторного disclosure и сохранение начала новой фразы. Механически отбросить audio до запоздавшего transcript delta и обрезать первое слово — не исправление. Если существующий механизм не проходит эти проверки на реальном Live, этот пункт остаётся незавершённым; сложный буфер, новый renderer или дополнительный LLM-контроль автоматически не добавляются. Сначала уточняется конкретная последовательность событий и корректируется контекст перехода.

### 4 Проверить полноту транскрипта после устранения причин

Этот пункт — проверка последствий первых трёх исправлений, а не самостоятельная перестройка transcript pipeline.

- Не сдвигать recording boundary назад и не сохранять pre-consent recipient text/audio ради заполнения пропуска.
- Не удалять `incomplete` и issue codes у уже состоявшихся звонков.
- Реально проигранное, но оборванное audio, отсутствие mark или потеря post-consent текста по-прежнему означают неполное покрытие.
- Полностью подавленный assistant output, который доказуемо не отправлялся получателю, не должен считаться потерянной слышимой речью. Уточнение такой диагностики допустимо лишь по данным существующего output gate; если доказательства нет, сохраняется консервативный статус.
- Вызов без реальных разрывов должен завершаться с complete capture; намеренное прерывание проверяется отдельно и может корректно оставаться incomplete.

Сначала выполняются затронутые voice suites, typecheck и build. После стабилизации исходников — один полный API-прогон с отдельной временной БД. Contracts/web расширяются и проверяются только если изменится их контракт; существующий набор сохранения disclosure и approved snapshots обязателен. Во время тестов рабочая локальная БД не очищается и не пересоздаётся.

## Измерения и приёмка на телефоне

Использовать существующие events и несколько технических timestamps в ограниченном журнале: последнее речевое событие, готовность ответа, dueAt/requestAt backend, recording start, ACK перехода, первый отправленный voiced frame, generation/mark прощания. Содержание pre-consent речи не журналировать. Новая аналитическая подсистема не нужна.

Перед исправлениями снять короткую сопоставимую базовую серию, затем повторить на том же сценарии и locale. Минимум: по три обычных прохода на каждый голос; отдельно interruption/correction и один проход прежнего semantic режима. Автоматические тесты покрывают все locales, реальные тесты начинают с de-CH и ru-RU. Выборка подтверждает локальную приёмку, но не доказывает безусловную стабильность всех будущих звонков.

Условия приёмки:

- initial disclosure слышен один раз при непрерванном playback; после affirmative отсутствует второй вопрос о записи;
- первая task-фраза начинается целиком, получатель может говорить во время перехода;
- запрос recording не ждёт нового ACK и по-прежнему связан с affirmative;
- при неизменном входе backend запускается в рассчитанный dueAt с обычной погрешностью event loop, без добавочного полного пятисекундного окна;
- повторное подтверждение завершения сохраняет одно активное прощание и один действительный mark;
- завершение следует за полным прощанием; исправление не мешает реальной поправке получателя;
- статус capture отражает наблюдаемое покрытие и не становится complete посредством удаления реальных gaps;
- полезная первая фраза и пауза перед прощанием измерены отдельно от времени до любого первого audio packet.

Порог общей задержки не обещается заранее: provider latency и native речь измеряются отдельно от управляемых приложением ожиданий. Нынешние 559 мс до первого пакета не являются эталоном правильной первой task-фразы, поскольку в исследованном звонке она содержала повтор disclosure.

## Поставка и откат

Исправления выполняются последовательно: прощание → планировщик → переход → общая проверка capture. Каждая часть остаётся отделимой для ревью и отката. При реализации обновляется существующий runtime version descriptor, чтобы последующие звонки отличались от `live-managed-v7`; approved snapshots и сохранённая история не переписываются.

После утверждения плана локальный API перезапускается только при отсутствии активного звонка, с сохранением текущих provider settings, worker и tunnel. Проверяются health и подпись Twilio, затем выполняется согласованная ручная приёмка. Production rollout этим планом не запрашивается.

Переключатель consent откатывает способ распознавания согласия, но не эти общие исправления Live. Для них откат — предыдущая проверенная сборка или отдельный патч. Новые временные feature flags и комбинации режимов для трёх небольших исправлений не добавляются.

Полная приёмка требует прохождения регрессий и проверки слышимого результата. На этапе составления плана код и процессы не изменялись; после утверждения реализация описана ниже.

## Реализация 4 октября

- Повторные `keep_closing` и `end_call` сохраняют текущий terminal decision, render, generation и mark. Реальное прерывание и ограниченное восстановление продолжают работать.
- Таймер хранит время settlement текущего ответа и пересчитывает остаток до срока. Завершение занятого backend, включая оставшуюся consent continuation, возвращает проверку готовности; проверка после освобождения не начинает новое пятисекундное окно.
- Native output закрыт со старта Live. После affirmative запись запускается как раньше. Task configuration, части approved context и новое stage instruction отправляются вместе, output ожидает всех соответствующих ACK. При явном отказе команда повторяется один раз; устаревший ACK не открывает другую generation.
- Существующая transcript fence отсекает старое native output. Контекст прямо сообщает, что полное представление/disclosure уже проиграно и согласие принято, и отменяет устаревшую инструкцию ждать после решения.
- Полностью подавленный assistant fragment проверяется до recording-boundary диагностики. Recipient boundary и final drain остаются защищены. Неатрибутированное voiced audio после ACK, но до свежего transcript, учитывается числом миллисекунд и оставляет capture неполным; оно не маскируется под complete.
- Новые технические logs: `Live output context acknowledged`, `Live output boundary ready` (включая `unattributedAudioMs`), точные `answerSettledAt` / `quietDueAt` / `requestedAt` backend. Pre-consent содержимое не добавляется в logs.
- Версия новых runtime descriptors и telemetry — `live-managed-v8`; контракт по-прежнему принимает исторические версии. Approved snapshots и старые звонки не переписываются.

Остающееся ограничение: транспорт не даёт надёжно сопоставить untimed audio с ещё не доставленным transcript. Поэтому кандидату нельзя заранее приписать гарантию сохранности первого слова. Автотесты проверяют выдачу первого frame после свежего transcript и консервативный статус при обратном порядке. Проверка на телефоне должна подтвердить отсутствие повторного disclosure и обрезанного начала одновременно; до этого переход не считается полностью принятым. Буферизация реплик и дополнительные LLM-вызовы не добавлены.

## Утверждённая реализация v9: первая фраза и ожидание завершения

4 октября 2026 пользователь разрешил реализовать оба следующих изменения и проверить результат реальным звонком. Работа продолжена в той же ветке. Новых сервисов, LLM-классификаторов, аудиобуферов или runtime-переключателей не добавлено.

### Подготовка и начало речи

`OpenAILiveConversation.configureBackend()` по-прежнему вызывается только после affirmative consent и подтверждённого начала recording. Существующий канал output остаётся закрытым на время подготовки:

1. Модель получает инструкцию подготовить задачу молча и ждать отдельной команды начала. То же условие закреплено в startup-инструкции; одни данные задачи или результат consent tool не разрешают начинать речь.
2. Через существующие команды передаются настройки backend и approved execution context. Сохраняется ожидание всех сопоставленных ACK, включая ACK инструкции подготовки, и прежняя ограниченная обработка ошибок.
3. После последнего ACK открывается передача native audio и отправляется короткая инструкция `Begin the approved task now`. Её ACK и первый transcript **не закрывают и не переоткрывают** аудиоканал. Аудио, пришедшее до них, передаётся с первого пакета. ACK команды начала не сдвигает transcript fence.
4. Повторные ACK не отправляют команду начала повторно. Новое защищённое воспроизведение или закрытие инвалидирует ожидающий переход. Автоматический запрос решения по задаче ждёт завершения подготовки; посторонняя речь собеседника продолжает обрабатываться и сохраняться только после прежней recording boundary.

Правила задачи передаются на стадии молчаливой подготовки. Короткий запуск использует последний ответ получателя, сохраняет contextual readiness и запрещает повторять уже прозвучавшее представление, assistance reason или вопрос о записи. Тексты initial disclosure и approved snapshots не изменены. Сохраняются все 7 locales, default `assistanceReason=none` и оба opt-in значения.

Для следующего разбора лог `Live task opening requested` содержит время запуска, generation, контекстную временную границу и `suppressedPreparationAudioMs`: суммарную длительность подавленных voiced-пакетов **после recording admission**, без сохранения их содержимого. Это диагностический счётчик, а не доказательство акустически целой фразы. Защита возобновления речи после appointment/application playback оставлена прежней.

### Срок запроса решения о завершении

Один существующий таймер использует одинаковую формулу и при планировании, и перед запросом:

```text
dueAt = max(answerSettledAt + 5000, lastNativeVoicedAt + 2000)
```

Первоначальные 5 секунд сохраняют время для самостоятельного native ответа/delegation. После native ответа достаточно 2 секунд без новых voiced-пакетов; silent packets не продлевают срок. Речь собеседника, незавершённый ответ, уже занятый backend, устаревшие revisions и существующие closing/deadline правила по-прежнему проверяются. Служебный recheck не добавляет новое полное окно. Идемпотентное прощание из v8 сохранено.

На шкале предыдущего звонка эта формула дала бы запрос около 14:39:03.042 вместо 14:39:06.042, то есть выигрыш примерно 3 секунды. Backend и TTS по-прежнему занимают собственное время; мгновенное прощание не ожидается.

### Проверки и локальный запуск

Добавлены проверки первого аудио до ACK/transcript, фрагментов слова ровно от границы подготовленного контекста, позднего ACK команды начала, повторных ACK и ошибок обоих этапов. Проверяются recording-before-output для deterministic/semantic/DTMF, новый voiced output, silent packets, новая реплика получателя и прежние защищённые playback fences.

### Что проверяет реальный звонок

Первое слово task-фразы должно слышаться целиком, без повторного представления/разрешения на запись. После содержательного ответа должны следовать одно резюме и одно прощание, без прежнего лишнего трёхсекундного ожидания. Новая реплика до прощания должна оставаться доступной модели.

Ограничение остаётся явным: ACK сообщает доставку контекста, а не начало новой фразы; у primary WebSocket audio нет timestamp/utterance ID. Изменение устраняет локальное отбрасывание начала речи, запущенной отдельной командой, но не доказывает, что модель всегда молчит во время подготовки или не продолжит уже начатую ею речь. Это проверяется акустически. Две секунды отсчитываются от серверного voiced packet, не от Twilio playback mark обычной native речи. Основание: [официальное описание Live context и audio](https://developers.openai.com/api/docs/guides/live-conversations).

### Оставшаяся шероховатость завершения

В native transcript после ответа получателя есть `Alles klar, danke. Ich notiere, dass Sie Pizza möchten. Auf Wiederhören.` Позже приложение воспроизводит `Sie möchten heute Pizza zum Abendessen. Текущая frontend-инструкция явно требует молчать после разрешённого `end_call`, но до него допускает обычные подтверждения. Здесь Live добавил прощание к такому подтверждению до решения backend. При следующей небольшой доработке можно уточнить frontend-инструкцию: финальное резюме и прощание всегда принадлежат приложению; до `end_call` допустимо только краткое подтверждение с передачей завершения backend. Это гипотеза улучшения поведения модели, требующая телефонной проверки, а не гарантированный фильтр речи. Изменять state machine, добавлять классификатор или сокращать таймер ещё раз для этого результата не требуется.
