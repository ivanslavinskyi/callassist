# SHPROHLI — аудит готовности к публичному тестированию

Дата: **13 сентября 2026**. Код: `ef36cfa8cd17e740395a4e120be6bbc23f347b4e`.
Это снимок **до исправления B01/B02**. Последующая [приёмка B01/B02](b01-b02-remediation-2026-09-13.md) фиксирует обновлённые зависимости, восстановленный System и независимое управление новыми звонками; первоначальные доказательства ниже сохранены. Единственный актуальный список работ и критериев допуска — [roadmap](mvp-plan.md).
Предыдущий roadmap сохранён [без потери исходного текста](release-roadmap-history-2026-09-12.md).

## 1. Решение

**NO-GO для публичного тестирования текущей сборки.** Для контролируемых внутренних проверок основа уже достаточно зрелая. Продукт не требует переписывания: основной цикл, права доступа, кредиты, подготовка планов, запись, результаты и значительная часть эксплуатации реализованы.

Главные причины NO-GO:

1. Свежий production dependency audit не проходит: **2 critical и 1 high** в Next.js/sharp.
2. **Admin → System возвращает 500 при наличии фоновых задач**, скрывая в том числе управление остановкой исходящих звонков. Подтверждено и на memory, и чтением локальной PostgreSQL.
3. Первичное подтверждение email отсутствует. Смена email уже реализована, но реальная отправка не настроена в проверенном окружении и не имеет полноценного контроля доставки.
4. SMS-код написан, но отсутствует конфигурация Verify Service в локальном `.env`; доставка и противодействие SMS-abuse не подтверждены.
5. Нужны рабочий deployment, ограничение набора тестировщиков/расходов, корректный IP за reverse proxy, аварийные процедуры и проверенный канал поддержки.
6. Исходники, черновики и опубликованный CMS-контент расходятся. Обещания про согласие и бесплатные звонки требуют согласования с фактическим поведением.
7. Нет полной приёмки текущего кандидата с реальными голосовыми провайдерами, отказами, результатами и операционными действиями.

Минимум здесь — **публично доступная бета с ограниченным набором участников**, разрешёнными сценариями и работающим оператором. Неограниченная регистрация требует дополнительных общих лимитов и защиты от множества аккаунтов. Рекомендованный стартовый размер и пороги приведены в roadmap; это предложение, а не уже принятая настройка.

## 4. Подтверждённые дефекты и незакрытые поверхности

### A01 — production-зависимости снова уязвимы → B01

В lockfile Next.js **15.5.21**, принудительный override sharp **0.35.0**. Старое состояние R01 «dependency gate passes» больше не актуально.

| Advisory | Условие / граница | Исправленная ветка |
| --- | --- | --- |
| [Next.js: Windows RCE](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36) | Специфично для Windows-hosted server; ОС будущего deployment неизвестна | Next.js 15.5.24+ |
| [Next.js: AVIF Image Optimization RCE](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4) | Зависит от обработки входного AVIF через image optimization | Next.js 15.5.24+ |
| [sharp/libheif](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c) | Условия описаны upstream, включая обработку недоверенных изображений | sharp 0.35.4+ |

Это три записи audit, а не три независимо подтверждённые эксплуатации приложения: AVIF-цепочки пересекаются. Exploit не запускался, доступность уязвимых путей не доказана. Минимальное решение: обновить Next.js и согласованный eslint-config-next, изменить override sharp, обновить lockfile, frozen install, свежий audit и регрессия/build. Переход на новую major-версию не обязателен.

### A02 — System 500 после появления durable jobs → B02

**Воспроизведение:** пустой memory repository → `getAdminSystemStatus(false)` проходит; `service.prepare(...)` создаёт задачу → тот же метод падает. На текущей локальной PostgreSQL такой же результат при read-only вызове.

Ошибка: `ZodError / unrecognized_keys / textArtifactId / jobs.recent[0]`. На PostgreSQL неверны все 20 возвращённых recent jobs. Поле попадает в DTO даже для задачи, не относящейся к text artifact.

Причина: оба repository удаляют из job часть внутренних полей через rest destructuring, но оставляют новое `textArtifactId`. [Strict schema](../packages/contracts/src/admin-operations.ts#L190) этого поля не принимает. См. [memory mapping](../apps/api/src/storage/in-memory-call-repository.ts#L2116), [PostgreSQL mapping](../apps/api/src/storage/postgres-call-repository.ts#L3481), [финальную валидацию](../apps/api/src/call-service.ts#L472).

**Влияние:** весь `/admin/system` становится недоступен, скрывая components, очередь, алерты и outbound control. Сам control API не доказан сломанным: ошибка именно чтения общего состояния и зависимого UI. Уже существующие задачи делают проблему постоянной, а не только во время выполнения.

Минимум: явная проекция публичного job DTO либо осознанное расширение контракта; один regression test через реальный admin endpoint с непустой очередью для обоих repository. Отдельный endpoint/секция аварийного stop должен оставаться доступным при поломке диагностической панели.

### A03 — email: смена есть, первичного подтверждения нет → B03

[Регистрация](../apps/api/src/auth/auth-service.ts#L109) создаёт аккаунт и отправляет SMS. В пользовательском контракте нет состояния `emailVerifiedAt`; первичная принадлежность email не доказывается. Это допускает опечатку/занятие чужого адреса и ненадёжную доставку сообщений владельцу. Это не доказательство захвата чужого аккаунта: текущий recovery привязан к телефону.

[Смена email](../apps/api/src/auth/auth-service.ts#L454) уже содержит текущий пароль, session-bound challenge, HMAC-код, TTL 10 минут, бюджеты попыток, письмо с кодом новому адресу, уведомление старому, атомарное подтверждение и отзыв других сессий. [UI](../apps/web/components/account-console.tsx) тоже существует. Это надо довести и настроить, а не реализовывать заново.

[Email provider](../apps/api/src/auth/email-provider.ts) имеет только два сообщения о смене. [Resend adapter](../apps/api/src/auth/resend-email-provider.ts) отправляет EN/DE plain text и проверяет только HTTP success. Нет явного deadline/AbortSignal, сохранённого provider message ID, idempotency, durable delivery/retry, bounce/delivery обработки. `Promise.all` двух писем может привести к частичной отправке с инвалидированным challenge, если второй запрос упал.

В локальной конфигурации отсутствуют `EMAIL_DRIVER`, `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_VERIFICATION_HASH_KEY`. Non-production может использовать mock; production запрещает mock и требует реальные значения.

**Минимальная транзакционная поверхность:**

| Событие | Необходимое поведение |
| --- | --- |
| Первичная регистрация | Проверяемый адрес, resend с cooldown, истечение/неверный/использованный код, исправление опечатки; явное состояние в UI и политика для существующих аккаунтов |
| Смена адреса | Существующий код новому адресу + уведомление старому; после подтверждения уведомить о завершении, отозвать остальные сессии |
| Смена телефона / recovery | Уведомление проверенному email об изменении доступа; понятные действия при чужой операции |
| Ошибка доставки | Пользователь видит возможность повторить; оператор различает rejected/bounced/delivered, не видит пароль/OTP; временные сбои повторяются ограниченно |

Брендированный HTML + text fallback полезны для доверия, но простое аккуратное письмо достаточно для старта. Маркетинговая welcome-цепочка и рассылка результатов звонков не нужны. Не стоит добавлять чувствительный transcript в email по умолчанию.

До запуска проверить домен отправителя: [Resend требует SPF/DKIM](https://resend.com/docs/dashboard/domains/introduction); DMARC — дополнительная настройка. Ответ API не доказывает попадание письма в ящик: нужны статусы [delivered/bounced/failed](https://resend.com/docs/webhooks/event-types) и реальные проверки EN/DE хотя бы на двух почтовых системах. Для небольшой беты часть диагностики допустима в кабинете провайдера, если доступ и ответственный определены.

### A04 — SMS: реализовано, но не принято в эксплуатацию → B04

[Twilio Verify adapter](../apps/api/src/auth/twilio-verification-provider.ts) и [фабрика](../apps/api/src/auth/create-verification-provider.ts) работают с Service SID, SMS и `approved`; mock запрещён в production. Регистрация, resend, recovery, смена телефона и recipient opt-out уже используют verification.

При `TELEPHONY_DRIVER=twilio` фабрика может выбрать Twilio и без отдельного `VERIFICATION_DRIVER`. Поэтому наличие телефонии **не означает наличия настроенного Verify Service**. В локальном `.env` нет `TWILIO_VERIFY_SERVICE_SID`. Настройки внешнего аккаунта Twilio не обследованы, отсутствие сервиса в кабинете не утверждается.

Минимум: Verify Service, секреты и environment parity API/worker; реальные EN/DE SMS, неверный/истёкший код, resend, номер уже занят, отказ провайдера, recovery и phone change. Явно определить страны **мобильного номера пользователя** отдельно от CH-only **номера назначения звонка**: регистрационный контракт сейчас принимает международный E.164.

Добавить контролируемые таймауты, наблюдение ошибок/стоимости, предел отправок по пользователю/IP/номеру/стране. Настроить Verify geographic permissions/Fraud Guard/Service Rate Limits согласно [Twilio](https://www.twilio.com/docs/verify/preventing-toll-fraud). Не ограничивать регистрацию только CH автоматически: это продуктовое решение для аудитории, живущей в Швейцарии с иностранными SIM.

Recovery сейчас опирается на verified phone. При потере номера автоматического обхода нет; до релиза нужен понятный операторский путь без небезопасного «сменим номер по письму». Email password reset как второй механизм не обязателен для первой беты, если ограничение SMS recovery явно принято и поддержка работает.

### A05 — IP-лимиты за reverse proxy и общий бюджет → B05/B06

В [Fastify setup](../apps/api/src/app.ts#L183) не задан `trustProxy`; auth limits используют `request.ip`. Это безопасно игнорирует произвольный `X-Forwarded-For`, но за одним reverse proxy пользователи будут выглядеть одним клиентом.

Репродукция: шесть регистраций разных вымышленных аккаунтов с разными `X-Forwarded-For` через один socket → пять ответов 202, затем 429. Лимит регистрации — **5/IP/час**. Это проверка текущего поведения приложения; фактический production proxy пока неизвестен.

Минимум: доверять только заданным proxy hops/адресам, обрезать внешние forwarded headers на ingress, проверить разные реальные IP и подделку заголовка. Не включать безусловный `trustProxy: true` на публично доступном backend.

Account quotas уже есть: один активный звонок, лимиты стартов, recipient frequency, credits. Однако [проверка частоты адресата](../apps/api/src/storage/postgres-call-repository.ts#L4440) ограничена `user_id`; несколько аккаунтов не делят этот бюджет. Регистрация даёт три кредита после подтверждения телефона. Общего admission cap/invite gate в просмотренном коде не найдено; kill switch есть, автоматический общий hard spend stop не подтверждён.

Для первой беты достаточно контролируемого набора участников, provider budget/alerts, общего аварийного stop и ограничений длительности/конкурентности. Для свободной регистрации дополнительно нужны общие лимиты по адресату и противодействие multi-account abuse. Нельзя считать SMS-верификацию достаточным общим финансовым ограничением.

### A06 — deploy/configuration ещё не является воспроизводимым релизом → B06/B11/B12

Есть production validation, отдельный durable worker, DB миграции, backups/rotation tooling. В [runtime validation](../apps/api/src/config/runtime-environment.ts) production требует PostgreSQL, Twilio, OpenAI compiler, external worker, реальные auth/email провайдеры, независимые ключи и HTTPS.

Проверенный `.env` соответствует разработке: локальная БД, localhost/временный tunnel, отсутствуют `DURABLE_WORKER_MODE`, `NEXT_PUBLIC_SITE_URL`, `INTERNAL_API_URL` и часть auth delivery configuration. Конкретный внешний deployment этим аудитом не установлен. Полного готового production deployment manifest в просмотренном repo не найдено; Docker Compose обслуживает локальную PostgreSQL.

Обязательно проверить: один корректный cookie hostname для browser/API, SSR internal origin, Secure/SameSite cookies, CSRF, точный CORS, отсутствие localhost в canonical/OG, отдельный Twilio ingress с проверкой подписей, SSE без буферизации/обрывов proxy, WebSocket timeout, worker heartbeat и controlled restart.

Реальная генерация text artifacts по умолчанию выключена, если не выставлен `TEXT_ARTIFACT_GENERATION_ENABLED=true`; разрешённые направления задаются отдельно. Выбор языка в UI не доказывает включённую summary/translation. `REALTIME_AGENT_HANGUP_ENABLED` также имеет repository default false. Нужна проверенная матрица effective configuration каждого процесса, а не только заполненный `.env.example`.

Backups/ротация локально покрыты кодом и предыдущими drills. До внешних пользователей нужны отдельные credentials, секретное хранилище, managed backup/PITR либо эквивалент, успешный restore в изолированное окружение, доступные ключи и повторное применение удалений/recipient suppressions. RPO/RTO и ответственные должны быть названы; наличие скрипта backup не закрывает этот пункт.

## 5. Лендинг, обещания и публикация → B07

### Что не так с текущей подачей

Существующий визуальный язык Emerald Paper можно сохранить. Основная проблема — информационная структура и границы обещания, а не необходимость нового дизайна.

На первом экране есть три последовательных объяснения, две CTA, badges и пример плана. На DE mobile основной заголовок занимает много строк, а к разнообразию задач пользователь приходит существенно позже. Длинный учебный пример полезен, но его полный план/разговор/результат лучше оставить раскрываемым, сохранив короткое доказательство результата рядом с основным действием.

Пять текущих карточек — врач, муниципалитет, школа/курс, арендодатель/ремонт, страховая — перечисляют **организации**. Они не объясняют, что сервис подходит для множества обычных вопросов и самостоятельной постановки задачи. Это создаёт впечатление узкого набора заранее запрограммированных сценариев, хотя свободное описание уже реализовано.

«Консультация» подходит как **получить ответы от выбранной организации/специалиста по согласованным вопросам**. Не обещать собственную профессиональную консультацию ИИ, принятие решений вместо пользователя или гарантированное согласие собеседника обсуждать персональный кейс. «Свой сценарий» должен вести к тому же свободному описанию и проверке плана, а не означать отсутствие ограничений.

### Рекомендуемая структура главной

1. Короткое обещание: «Опишите, что нужно выяснить по телефону. SHPROHLI подготовит план и позвонит после вашего подтверждения». Рядом оставить понятное объяснение помощи при речевом/языковом барьере.
2. Одно основное действие «Описать задачу» с сохранением введённого после регистрации; пока такого переноса нет — честное «Создать аккаунт». Второе — «Посмотреть пример».
3. Краткие ограничения рядом: швейцарские номера, AI представляется и спрашивает согласие, бета/кредиты. Детали списания доступны здесь же, не только внизу страницы.
4. Шесть карточек по намерению, последняя всегда «Своя задача». Для каждой 2–3 разных примера, не длинный отдельный маршрут.
5. «Как это работает»: задача → план/разрешённые сведения → подтверждение → ответы/следующие шаги. Не обещать фиксированный результат звонка.
6. Один компактный пример с возможностью раскрыть полный план и transcript. FAQ, языки, данные/поддержка, финальная CTA.

Это контентная переработка в существующих компонентах. Для первого релиза не нужны новый wizard, каталог из десятков отдельных страниц или новая сценарная архитектура.

### Реальный пул задач

Таблица — пул для карточек, подсказок и приёмочных fixtures. Все примеры требуют проверки плана и разрешения пользователя на передаваемые сведения; при отказе адресата задача может остаться нерешённой.

| Семейство | Реальные примеры | Граница и ожидаемый результат |
| --- | --- | --- |
| Узнать информацию и условия | Часы работы мастерской; есть ли услуга ремонта конкретного велосипеда; как принимают крупногабаритный мусор | Получить сведения и дальнейший контакт; без покупки/обязательства |
| Получить ответы / предварительную консультацию | Какие документы нужны для записи на языковой курс; как подготовиться к разговору с сервисным специалистом; какие варианты услуги предлагает организация | Заранее согласованные вопросы; не диагностика, юридическая позиция или финансовая рекомендация от ИИ |
| Проверить статус | Получили ли заявление; готов ли ремонт; на каком этапе заказ/доставка | Передать разрешённый номер заявки и имя; не обходить идентификацию и не сообщать новые чувствительные сведения |
| Уточнить документы и процедуру | Что отсутствует в пакете документов; куда отправить справку; как получить копию счёта | Список недостающего и способ передачи; сервис сам ничего не отправляет, если такой интеграции нет |
| Проверить наличие и доступность | Есть ли запасная деталь; есть ли свободные места в группе; доступен ли вход без ступеней | Узнать наличие/условия; не обещать бронь товара или оплату |
| Согласовать одну встречу | Записаться в мастерскую в заданном окне; выбрать первичный приём в разрешённое время; подтвердить личную встречу | Только явно разрешённая booking/confirmation action и подтверждение адресата; без переноса/отмены/депозита/новых условий |
| Передать сообщение и уточнить следующий шаг | Сообщить арендодателю о протечке; предупредить контактное лицо об опоздании; попросить обратный звонок от сервиса | Передать согласованный текст, выяснить реакцию; не переговоры о компенсации и не экстренная помощь |
| Своя задача | Уточнить правила посещения мероприятия; задать несколько вопросов спортивному клубу; узнать, кто отвечает за ошибку в документе | Свободное описание цели, вопросов, известных фактов и ограничений; компилятор уточняет или отклоняет неподдерживаемую задачу |

На самой главной можно объединить «документы» со «статусом», а «наличие» с «информацией» — получится шесть читаемых карточек. Расширять примеры можно через CMS. Не следует показывать 24 карточки сразу.

**Шаблон свободной задачи:** кому звонить → что выяснить/передать → 2–5 вопросов → что разрешено сообщить → что нельзя обещать → допустимые варианты встречи, если она нужна. Поля должны помогать сформулировать цель, сохраняя возможность написать обычный абзац.

### Source seed, draft и published — три разных состояния

Read-only снимок локальной CMS на 13 сентября:

| Объект | Published | Draft | Решение перед публикацией |
| --- | --- | --- | --- |
| Landing collection | r5 | r3 | Черновик старше текущей публикации; сверить и перенести нужные изменения в актуальную основу |
| FAQ collection | r4 | r5 | Проверить содержание и ссылки в обеих локалях |
| Navigation collection | r2 | — | Проверить итоговые маршруты/контакты |
| Privacy page | r3 | r4 | Обновить описание обработки до согласия и фактических провайдеров |
| Terms page | r3 | r4 | Согласовать scope/credits/consent и re-acceptance |
| Acceptable Use page | r4 | r2 | Не публиковать старый draft без сверки |
| Support page | r4 | r2 | Перенести нужные изменения, подтвердить рабочий канал поддержки |
| FAQ page metadata | r3 | r4 | Синхронизировать с отдельной FAQ collection; это не дубликат редактора вопросов |
| Imprint page | r1 | r2 | Проверить фактического оператора/контакты; наличие draft не доказывает опубликованное исправление |

В опубликованных локальных Privacy/Terms всё ещё сказано, что согласие запрашивается до обработки разговора. Фактически отдельная AI-сессия уже распознаёт ответ о согласии. В Privacy перечислены Twilio/OpenAI, но не описан email-провайдер Resend. В старом Landing остались формулировки «Free public beta / 3 calls included»; текущая source-версия описывает credits точнее. Номера source seed r1 не сопоставимы с номерами мигрировавшей БД как показатель «свежести».

Остаточная неточность есть и в source: [dashboard privacyText EN/DE](../apps/web/lib/i18n/messages.ts#L374) по-прежнему говорит о согласии до processing/recording. Пройти не только legal pages, но и dashboard, auth copy, FAQ, demo, badges, onboarding и spoken notice.

[Seed initialization](../apps/api/src/content/postgres-content-repository.ts#L176) использует `ON CONFLICT DO NOTHING`. Изменение текста в существующем seed не перепубликует старый объект в БД. Новые seed IDs могут создавать отдельные публикации при инициализации; управлять editorial release через незаметную подмену seed IDs тоже не следует. Использовать существующий candidate/dry-run/preview/publication workflow с фиксированными revision IDs и проверкой публичных страниц после публикации.

### A07 — CMS позволяет менять часть demo, которую сайт игнорирует

[Editorial editor](../apps/web/components/admin-editorial-console.tsx#L525) показывает `items` блока `example`. Однако [public renderer](../apps/web/components/public-home.tsx#L146) передаёт в `LandingDemo` только `title`, а сам пример берётся из кода. Редактор видит поля, изменения которых не могут изменить публичный пример.

Это подтверждено связью editor → renderer; реальный CMS-контент не публиковался для проверки. Минимум: либо связать поля с demo, либо убрать неработающие поля и явно обозначить, какие части примера задаются в коде. Не расширять CMS только ради иллюстрации перед первой бетой.

Раздел `/admin/audit` с фильтрами actor/action/time полезен, но для небольшой беты допустим защищённый операторский read-only просмотр существующего immutable audit, с понятным runbook. Большая analytics-панель, автоматическая маршрутизация жалоб и новая ticketing-система не являются минимумом.

## 7. Приёмка реального звонка и результатов → B09

Ранее зафиксированы supervised calls, включая подтверждённую личную встречу, и реальные text-provider fixtures. Это ценные, но датированные частичные доказательства: [результаты 11 сентября](call-result-live-fixes-2026-09-11.md). Они не закрывают текущую матрицу всего пути и всех failure modes.

| Группа | Минимальные сценарии | Критерий приёмки |
| --- | --- | --- |
| Вход / подготовка | Новый пользователь, SMS+email, onboarding, свободная информационная задача, clarification, редактирование, оригинал/перевод | Нет потери ввода; понятные ошибки; звонок нельзя начать с устаревшим/чужим review receipt |
| Соединение | No answer, busy, wrong recipient, voicemail, ранний provider failure | Корректные терминальные состояния, объяснение, кредит/резерв соответствует событию соединения |
| Согласие | Явное yes/no, тишина, неразборчиво, «да, но без записи», смена языка, DTMF | До согласия нет основного разговора/записи; ограниченная consent recognition объяснена; отказ не превращается в согласие |
| Выполнение | Несколько информационных вопросов; административная консультация; custom request; одна разрешённая встреча | Ассистент использует только разрешённые факты/действия, соблюдает окна; «слот возможен» не считается записью без подтверждения |
| Завершение | Пользователь Stop, адресат просит остановиться, обычное прощание, перебитое прощание, пауза | Нет озвучивания tools, преждевременного hangup или бесконечного ожидания; длительность ограничена |
| Сбои | SSE reconnect, отзыв сессии, Realtime disconnect, API/worker restart, ASR/text 429/timeout | Нет двойного звонка/списания, нет утечки после revoke, partial status честный, фоновые задачи возобновляются/дают управляемую ошибку |
| Результаты | ASR, оригинал/перевод, summary с источниками, смешанные имена/даты, PDF/playback, feedback | Summary не выдумывает подтверждения; источники открываются; нужные языки включены; ошибки retry не теряют готовый оригинал |
| Данные / поддержка | Export, audio retention 0/7/30, ручное удаление, account deletion needs_support, suppression и restore | Удалённое не возрождается фоновым job/restore; оператор может довести запрос до конца |

В первую очередь — EN/DE и выбранные реальные направления перевода, затем остальные показываемые языки. Если язык не прошёл приёмку, его следует временно скрыть/пометить доступность на стороне продукта и API, а не молча считать поддержанным по наличию enum.

Модельная Realtime-сессия после обрыва сейчас завершает звонок. Это допустимая граница первой беты при корректном объяснении, завершении и расчёте кредита. Бесшовный provider reconnect не нужен для GO. SSE reconnect и восстановление durable jobs уже существуют и не равнозначны восстановлению разговора.

CLI real-provider harness имеет prepare/poll/read, но старт новых v2 plans не передаёт необходимые review evidence. Если приёмка и бета работают через UI, можно явно исключить этот CLI из релизного маршрута. Исправлять его только ради закрытия исторического R06 не обязательно.

## 8. Доступность, приватность и поддержка → B10/B11/B12

SHPROHLI предназначен в том числе для людей с речевыми ограничениями. Поэтому нельзя делать телефонный звонок единственным способом получить помощь. Нужны доступные текстовые Support/complaint контакты, часы реакции и ответственный; наличие ссылки `mailto:` этого не доказывает.

В browser smoke desktop/mobile не выявлено общего горизонтального overflow; отдельно измерены DE Landing 390 px и email form 320 px. Это не доказывает WCAG compliance. Минимум: весь путь клавиатурой, видимый focus, читаемые ошибки с привязкой к полям, password-manager/OTP autofill, 200% zoom, screen reader для регистрации/approval/live/result, проверка touch-целей и контраста в обеих темах. Live transcript не должен непрерывно перебивать assistive technology; критическая кнопка Stop должна оставаться доступной.

Нужны конкретные интервалы хранения по категориям. Audio «0 дней» означает удаление записи после финальной транскрипции, а не удаление всех текстов. Contact-change challenges уже очищаются; scheduled retention recovery/session/operational records остаётся отдельной работой. Проверить фактические ciphertext/plaintext поля, доступ к БД/логам/backup и непротиворечивость Privacy. Не требовать шифрования каждого поля в приложении без оценки — защищённый storage/TLS/least privilege и честный inventory важнее универсальной декларации.

Минимальный эксплуатационный сценарий: поступила жалоба → оператор нашёл звонок без лишнего раскрытия текста → остановил дальнейшие обращения → при необходимости suspend/revoke → ответил человеку → оставил audit evidence. Отдельно пройти deletion needs_support и provider outage. Это можно организовать существующими средствами и простым защищённым журналом; полномасштабный helpdesk не обязателен.

Privacy/Terms/Imprint и соглашения с провайдерами требуют проверки ответственным за продукт/данные, включая pre-consent recognition и международную обработку. Здесь зафиксированы технические расхождения, а не вывод о выполнении конкретных правовых требований.
