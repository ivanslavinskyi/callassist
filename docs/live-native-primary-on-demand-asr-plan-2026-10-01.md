### Отдельная неточность summary

Русский execution snapshot содержит критерий: «Согласованные дата, время, место и существенные детали повторены и подтверждены». Summary отмечает его `achieved`, хотя процитированные сегменты содержат имя, услугу, дату и время, но не место. В сохранённых репликах адрес/место сеанса не подтверждены. Это отдельная проблема проверки составного критерия; смена источника транскрипта сама её не исправит. При этом подтверждение записи и попадание 15 октября в утверждённое расписание подтверждены данными.

## 2. Почему до сих пор два транскрипта

Исправление v6 было недостаточно широким: оно добавило подтверждённые реплики application TTS в Live-проекцию, но сохранило прежнее правило «неполный capture → заменить весь итоговый транскрипт ASR».

| Участок реализации | Текущее поведение и последствие |
| --- | --- |
| `apps/api/src/voice/unified-live-call.ts`: `#clippedTaskSpeech`, `#clear`, `#cancelCritical`, `nativeTranscriptGap` | Прерывание уже выпущенной речи или разрыв на границе подавления выставляет один флаг на весь звонок. Причина и интервал неполноты отдельно не сохраняются. |
| `apps/api/src/voice/live-conversation.ts`: `#transcript`, `#capture`, `#finalize` | Пересекающиеся с подавлением фрагменты могут отбрасываться; capture становится `incomplete`. Отдельно отбрасываются фрагменты, начавшиеся до разрешённой границы записи. |
| `apps/api/src/storage/native-transcript.ts`: `assembleNativeTranscript` | Любой статус, кроме `complete`, даёт `null`; также требуется начало recording и хотя бы одна реплика recipient. Полезные native-данные из неполного звонка не становятся итоговым текстом. |
| `apps/api/src/call-service.ts`: `setNativeTranscriptCapture`, `#processRecording` | Фоновая `final_transcription` выбирает между native и полной ASR-обработкой. При `null` автоматически скачивает и распознаёт recording. |
| `apps/api/src/storage/postgres-call-repository.ts`: `completeFinalTranscript` | Оба пути записывают один основной результат, публикуют текущую revision и запускают последующую обработку. Здесь же назначается срок удаления записи. |
| `apps/web/components/live-call.tsx`: `transcriptView`, проверка `isLiveTranscript` | По умолчанию выбран `final`. Второй, «предварительный», транскрипт скрывается только при `live_native/live_composed`. При `recording_asr` снова видны оба. |

Таким образом, простое переключение первой вкладки не остановит ASR и не исправит источник summary/export.

В русском звонке доказан достаточный триггер: в `11:45:54.268Z` задача стала stale из-за `recipient_transcript`, `released:true`; `request_appointment` отклонён с `appointment_delivery_interrupted`. В этом пути `#cancelCritical` выставляет флаг неполноты. Последующая успешная проверка статуса не снимает его, поэтому ASR обрабатывает весь звонок.

В немецком звонке capture также неполон при успешной Live-сессии и доставленном goodbye. Обнуление очереди native audio перед приложением и пересечение suppression boundary — возможные причины по коду; установить, какая первой выставила флаг, по сохранённой телеметрии нельзя. Нужна диагностика причин, а не утверждение об установленном триггере.

Пограничные native-фрагменты перед началом записи сейчас отбрасываются целиком. Это объясняет механизм потери вступления, но без исходных отброшенных событий нельзя восстановить точные слова и их допустимые интервалы. При исправлении нельзя ослаблять consent gate ради более полного текста.

## 3. Что следует из актуальной документации OpenAI

Документация проверена 1 октября 2026 по официальным страницам; это не предположения по прежнему Realtime API.

- Native речь обеих сторон приходит через `session.input_transcript.delta` и `session.output_transcript.delta`. Фрагменты нужно накапливать без изменения текста, сохраняя порядок доставки. API не обещает готовые разговорные turns или transcript-done. [Live API reference](https://developers.openai.com/api/reference/cli/resources/live).
- Времена фрагментов приблизительные; речь сторон может перекрываться. Группировка для интерфейса не должна менять управление задачами, а native output transcript сам по себе не подтверждает воспроизведение. [Managing GPT-Live sessions](https://developers.openai.com/api/docs/guides/live-conversations).
- Для окончания сессии нужны корректное закрытие и обработка `session.closed`; один разрыв WebSocket не подтверждает завершённую финализацию. [WebSocket connections](https://developers.openai.com/api/docs/guides/voice-websockets).
- Язык речи задаётся инструкциями и примерами на нужном языке; важные имена и произношение стоит уточнять и проверять на звонках. Это не гарантия безошибочной входной транскрипции. [Prompting GPT-Live](https://developers.openai.com/api/docs/guides/live-prompting).
- `gpt-live-transcribe` — отдельная streaming STT-модель с собственными возможностями hints. Она не является настройкой качества нативных deltas разговорного `gpt-live-1`. Подключать её вторым постоянным распознавателем для этой задачи не предлагается. [GPT-Live-Transcribe](https://developers.openai.com/api/docs/models/gpt-live-transcribe).

В проверенных руководствах нет обещания, что native всегда точнее recording ASR, или режима, делающего native гарантированно дословным. Практическое улучшение здесь — корректно сохранить уже полученные данные и явно показывать ограничения, без дополнительной модельной оркестрации.

## 4. Целевой контракт

1. Один основной источник `live` на попытку звонка. Он включает native deltas и подтверждённые application playback receipts. Название UI — «Транскрипт Live»; происхождение application-реплик доступно в деталях. Технический `live_composed` не нужно превращать в отдельную пользовательскую вкладку.
2. Полнота и источник независимы. Неполный Live остаётся основным; UI показывает конкретный пропуск/прерывание или общую отметку, если интервал неизвестен.
3. Дополнительный источник `recording_asr` имеет собственный статус, revisions, ошибки и запрос на генерацию. Он не заменяет Live, summary, assessment или выставленный счёт.
4. Открытие страницы, вкладки, GET, обновление SSE, callback recording, завершение capture, восстановление worker и summary job не создают ASR-запросы.
5. Единственное основание новой ASR-генерации — сохранённый запрос авторизованного владельца через явную кнопку. Уже готовый результат читается из БД.
6. Основной Live-текст публикуется даже без доступного recording, без ответа recipient или при незавершённой сессии. При отсутствии допустимых фрагментов показывается «Транскрипт Live недоступен», а не придуманная реконструкция.
7. Transcript admission, consent, инструментальные разрешения, подтверждения записи и процедура hangup сохраняют самостоятельные правила. Рефакторинг отображения не должен управлять ходом разговора.

## 5. Последовательность реализации

### Шаг 1. Разделить хранение источников и версии

Добавить родительские transcript artifacts с уникальностью `(call_attempt_id, kind)`, где `kind = live | recording_asr`. Live-artifact привязан к attempt/session, а recording ID для него необязателен. Recording-artifact требует ID конкретной записи этой попытки. Это устраняет ограничение нынешнего единственного `final_transcripts` на recording.

Существующие immutable revisions связать с artifact, сохранив их ID, source hashes и ссылки из summary. Текущая revision выбирается отдельно для каждого artifact. Не перезаписывать исходный ASR существующего звонка нативным текстом в той же revision.

В snapshot добавить явные `transcripts.live`, `transcripts.recordingAsr` и ссылку на revision, послужившую основанием результата. Старое поле `finalTranscript` оставить только как переходный адаптер для потребителей; новый UI не должен выбирать вкладку по source этого поля. Модель и версия сборщика сохраняются как provenance, а не как способ выбора источника.

Развести состояния:

- Live lifecycle: `collecting | finalized`; coverage: `complete | partial | unavailable`; transport finalization: подтверждена или нет.
- Quality issues: тип, session/attempt, связанные fragment IDs, известный интервал, фактическая причина. Например: crossing consent boundary, output cleared, interrupted application playback, persistence failure, session close timeout. Точная номенклатура закрепляется в контракте.
- Recording ASR: `not_requested | queued | processing | completed | failed | unavailable`; `requestedBy`, `requestedAt`, request ID, recording fingerprint, generator version.

Не называть coverage модельной confidence: числовой уверенности распознавания текущие данные не дают.

Основные изменения: contracts, DB migration, Postgres и in-memory repositories, snapshot/SSE contracts, revision lookup и data deletion. Устаревшие UI/API-клиенты не должны через прежний retry неявно включать ASR.

### Шаг 2. Сделать один детерминированный сборщик Live

Сохранить исходные допущенные фрагменты без переписывания; добавить отдельный монотонный ingestion sequence и receivedAt. Уникальность native-события — attempt/session/event ID. Повторы доставки устраняются по идентификатору, а не по одинаковым словам. Текст одного говорящего собирается в порядке получения; приблизительное время используется для размещения реплик сторон на общей шкале. Группировка не переупорядочивает текст внутри говорящего.

Один сборщик используется для текущих captions, завершённой страницы, plain text, PDF и входа в summary. Сейчас frontend grouping и серверный `assembleNativeTranscript` независимы; их расхождение должно исчезнуть. Поздние фрагменты обновляют соответствующую реплику, включая перекрывающуюся речь. Границы пузырей — представление, не новые факты о завершении turn.

Заменить global `clippedTaskSpeech` как блокирующий фильтр публикации на набор quality issues. Сохранить его влияние там, где оно реально нужно для гарантии доставки критической речи; не заменять `incomplete` на `complete` для обхода проверки.

Application TTS добавляется в основной разговорный текст только при действительном подтверждении полного playback. Mark, пришедший после clear, нельзя принимать за доказательство полного проигрывания. Для прерванного TTS сохраняется событие прерывания; целиком запланированный текст не выдаётся за услышанное собеседником. Receipt подтверждает проигрывание клипа с известным входным текстом, но не даёт пословной аудиопроверки.

Для native audio отдельно учитывать подавленную/очищенную выдачу. Целиком подавленную речь не показывать как произнесённую; пересечение границы отмечать как неопределённость. Приблизительный transcript interval и acknowledgment добавленной инструкции нельзя использовать для точного отсечения слов. Если безопасно восстановить слышимый кусок нельзя, показывать пропуск/неподтверждённое воспроизведение. Не дублировать одну application-реплику через native и receipt.

Consent boundary остаётся строгой: предшествующие ей слова не сохраняются/не восстанавливаются. Пограничные потери учитываются метаданными без текста до согласия. Убрать зависимость допустимого Live-текста от наличия скачиваемого audio file; хранить разрешённую временную границу отдельно от жизненного цикла файла.

Финализация: завершить разрешённый drain, дождаться очереди записи, опубликовать доступный Live с его coverage. Timeout, ошибка БД и restart дают явный partial/unavailable и восстановление из durable данных; они не разрешают ASR. Сборщик при повторном запуске даёт тот же результат. Изменение одних диагностических метаданных не создаёт новую текстовую revision или повторный summary.

### Шаг 3. Убрать все автоматические ASR-пути

Разделить нынешнюю `final_transcription` на финализацию Live и отдельную recording-ASR job. Capture completion и recording callback могут будить только соответствующее разрешённое обслуживание: публикацию Live, обновление доступности записи, retention. Они не создают запрос на ASR.

Перед каждой новой операцией ASR worker проверяет durable user request, владельца, attempt/recording, согласие, доступность и срок хранения, generator version, бюджет и lease. Этот инвариант нужен на сервере, не только в UI. Старые queued/retrying jobs без запроса не должны обойти правило после обновления процесса.

Нынешний `retryFinalTranscript()` переиспользовать без изменения нельзя: он запускает старую общую job, требует recording, а готовый Live в worker немедленно завершает обработку. Новый endpoint должен адресовать только recording-artifact; прежний endpoint обновить/закрыть совместимым явным ответом, без скрытого fallback.

Для явного запроса сделать authenticated POST, например `/calls/:id/recording-transcript`; GET возвращает только существующее состояние. POST атомарно создаёт запрос и job, возвращает 202; повторный POST при queued/processing/completed возвращает существующую работу/результат. Ключ дедупликации включает attempt, запись и версию обработки, а не случайный новый ID на каждое нажатие.

Сохранить ограничения бюджета, provider ledger, checkpoint успешно обработанных chunks и fencing stale workers. Retry после ошибки продолжает только недостающие части того же запроса; не сбрасывает весь кэш. Не обещать exactly-once оплату при сетевом исходе, неизвестном после отправки провайдеру: такой chunk требует явного учёта неопределённости и ограниченной политики повтора. ASR failure не блокирует основной текст и итог звонка.

В этом изменении не требуется менять ASR-модель или заново проектировать сегментацию аудио. Сначала отделить жизненные циклы и расходы; сравнительную оценку других моделей проводить отдельно.

### Шаг 4. Развязать retention и завершение транскрипции

Сейчас `completeFinalTranscript` назначает `delete_after` и retention job. Если просто убрать автоматический ASR, часть записей может остаться без назначенного удаления. Планирование retention перенести на независимый этап доступности записи/окончания звонка и назначать срок однократно, без его продления при ASR/retry.

Для новых записей закрепить явный anchor, например момент получения доступной записи; срок считается от него и не зависит от обработки текста. Для существующих записей сохранить уже назначенный `deleteAfter`. Отразить семантику в пользовательском описании хранения и runtime docs.

При `audioRetentionDays=0` запись удаляется согласно выбранной политике без ожидания возможного будущего ASR; дополнительная расшифровка после удаления недоступна. Нельзя незаметно продлить хранение ради кнопки. У обоих проверенных звонков выбрано 7 дней, записи на момент аудита доступны.

Race запроса с удалением решать атомарно: не принимать новую работу после deadline; перед скачиванием/повтором проверять доступность. Истечение срока или удаление аккаунта отменяет работу и очищает временные аудиоданные; job не удерживает файл сверх разрешённого срока. Уже готовый текст живёт по политике хранения текста. Удаление данных охватывает оба artifacts, revisions, receipts, requests, chunk caches и временные файлы.

### Шаг 5. Перестроить страницу и зависимые результаты

По умолчанию показывать «Транскрипт Live». Вторая вкладка — «По аудиозаписи». Если ASR не запускался, она содержит объяснение и кнопку «Расшифровать аудиозапись»; само открытие вкладки бесплатно в смысле отсутствия нового модельного запроса. Не обещать, что вторая версия обязательно точнее. После запуска показывать статус; после готовности — сохранённый результат. Для failed показывать явный retry; для deleted/expired/no recording — конкретную причину недоступности.

Переключение вкладок и приход SSE не должны самопроизвольно возвращать пользователя на другую вкладку. При отсутствии native основной раздел показывает честное состояние недоступности и ссылку на дополнительную версию. Для исторических Realtime-звонков источник обозначается как прежний/ASR, без переименования в native Live.

Summary, оценка, перевод, копирование и PDF получают явно выбранный artifact/revision. Для новых Live-звонков итог строится на основном Live и существующем action/calendar evidence; ASR по нажатию не пересчитывает итог, не меняет источник цитат и не списывает повторно стоимость звонка. Экспорт выбранной вкладки содержит именно её текст и обозначение источника.

Неполнота в существенном месте должна сохраняться как неопределённость результата; её нельзя скрыть автоматическим ASR или восполнить ожиданиями из brief. Ссылки на evidence открывают именно ту revision и источник, по которым был сформирован вывод. Поиск/админка также явно выбирают источник, не склеивают две версии в один рассказ.

**Отложено по указанию пользователя:** проверку составных критериев summary (дата, время и обязательное место) в эту имплементацию не включать. Действующую оценку `achieved` и календарный расчёт по утверждённым windows не менять.

### Шаг 6. Перенести существующие данные без повторных расходов

1. Аддитивная миграция создаёт source artifacts, связывает старые revisions, сохраняет IDs и summary evidence. Готовый ASR переносится в дополнительный источник без повторного распознавания.
2. Для Live attempts с сохранёнными допустимыми deltas собрать основную native/application-проекцию без вызова модели, в том числе при старом `capture=incomplete`. Старую неполноту сохранить; неизвестную историческую причину не придумывать.
3. Исторические ordering данные не позволяют восстановить утраченный receive sequence. Использовать существующий стабильный порядок и отметить ограничение; новая точная последовательность начинается с обновлённого runtime.
4. Существующие summaries остаются привязанными к первоначальной revision. UI показывает источник результата, а evidence может открыть ASR-вкладку без генерации. Не пересчитывать массово summaries и assessments только из-за миграции. Новые звонки сразу используют Live.
5. Старые pending ASR jobs без явного запроса перевести в отменённое/пропущенное состояние. Обновление worker выполнить согласованно: остановить выдачу старых jobs и дождаться/ограничить уже запущенные операции. Новые provider requests из старого процесса после переключения запрещены; уже отправленные запросы нельзя «отменить задним числом».
6. Backfill идемпотентен, имеет dry-run и счётчики; ошибки отдельного звонка не уничтожают старую версию. Rollback UI не должен снова включать auto-ASR. Серверное требование явного запроса сохраняется независимо от отката интерфейса.

## 6. Проверки и критерии приёмки

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Обычный разговор; assistant или recipient завершает первым | Один основной Live; прощание/прерывание отображается по имеющимся данным; ASR provider operations = 0 до запроса. |
| Application goodbye полностью проигран | В Live присутствует одна реплика с receipt, без дублирования и автоматического ASR. |
| Native interruption, clear очереди, crossing suppression boundary | Полезный текст сохраняется; локальная неопределённость отмечена; источник не меняется. |
| Application TTS прерван или mark возвращён после clear | Полный запланированный текст не маркируется как полностью произнесённый. |
| Реплики перекрываются, delta приходит поздно, повторяется event ID | Текст каждой стороны корректно дополняется; повторов доставки нет, намеренные повторы слов сохраняются. |
| Disclosure/consent, отказ, voicemail, silence, deadline | Правила приложения соблюдаются; запрещённый текст не сохраняется; отсутствие разговора не запускает ASR. |
| Fragment пересекает consent/recording boundary | Никаких до-согласительных слов в persisted/UI/summary; допустимый пропуск обозначен. |
| Нет recipient-текста, recording ещё недоступен/удалён, Live socket оборвался | Имеющийся Live доступен с корректным состоянием; нет платного fallback. |
| Restart во время drain, ошибка записи, lease потерян | Восстановление только из разрешённых durable данных, без новой автоматической ASR. |
| Страница, вторая вкладка, GET, SSE, summary/reconciliation/retry старой job | Ни одного ASR-запроса без durable user request. |
| Двойное нажатие из двух вкладок/одновременные worker | Один логический запрос и артефакт; успешно завершённые chunks используются повторно. |
| ASR ошибка/лимит бюджета/unknown provider outcome | Ошибка только дополнительной версии, ограниченный явный retry, основной результат не меняется. |
| Retention 0, истёк срок, удаление одновременно с POST/скачиванием | Нет продления хранения и работы с удалёнными данными; ясное unavailable/canceled. |
| Вторая попытка того же brief | Фрагменты, receipts, jobs и evidence разных attempts не смешиваются. |
| Исторический Live+ASR, только ASR, старый Realtime | Сохранены источники и ссылки; backfill не делает model requests. |
| Copy/PDF/перевод/evidence во второй вкладке | Используют выбранную revision; ASR не становится основным результатом автоматически. |
| Подтверждены дата/время, но не обязательное место | Отложено по указанию пользователя; текущую логику составного критерия не менять. |

Обязательные тесты: reducer/property cases для порядка и replay; repository/integration для раздельных revisions, миграции и атомарного запроса; worker tests для всех старых auto-ASR входов и retention races; UI tests для default tab, explicit button, SSE и выбранного источника экспорта. Реальные персональные тексты не переносить целиком в общие fixtures — использовать обезличенные эквиваленты двух кейсов.

Финальная приёмка на телефоне: немецкий вопрос с прямым обращением, русская запись с неоднозначной датой, прерывание финала, ранний hangup собеседника. После каждого звонка проверить основной Live и provider ledger до нажатия ASR. Затем один раз явно запросить ASR, проверить появление только второй версии, повторное открытие без новых запросов и неизменность основного результата. Новые тестовые звонки выполнять в согласованном порядке, не запускать их в рамках этого аудита.

Диагностика: сохранять причины partial capture, число принятых/отброшенных fragments с основаниями, подтверждённые/прерванные application clips, основание ASR-запроса, request/artifact IDs, число provider calls и причины unavailable. Метрики не должны содержать речь, имена или телефоны. Ключевой проверяемый инвариант: **ASR operation без явного request ID невозможна**.

## 7. Границы работ

Этот план меняет хранение, финализацию, UI и запуск дополнительной расшифровки. Он не добавляет модель, редактор транскрипта, детектор завершения реплик или новый слой управления разговором.

Повторная проверка записи, многословный status-check и произнесённый `Europe/Zurich` в русском звонке требуют отдельного улучшения голосового сценария. Их не следует скрывать обработкой транскрипта. Также остаётся отдельная телефонная проверка случая, когда native уже попрощался, а человек не кладёт трубку.

При реализации обновить `docs/architecture.md`, `docs/runtime-reference.md`, `docs/live-unified-runtime.md`, `docs/local-testing.md`, описание transcript API/retention и прежние документы о post-call fallback. Устаревшее правило «неполный Live автоматически заменяется ASR» должно быть явно помечено как отменённое только после поставки изменения.
