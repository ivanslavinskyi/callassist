# Ограничения беты и исправление recompile, 14.09.2026

Дополнение того же дня: пользовательский кредит теперь используется после согласия
и первого подтверждённого содержательного ответа. [Новое правило и проверки](conversation-credit-2026-09-14.md)
заменяют прежнюю семантику списания при соединении. Лимиты и учёт расходов USD из
этого отчёта сохраняются; результаты ниже относятся к предшествующему checkpoint.

Отчёт о реализации после `34a0746`. Единственный актуальный backlog —
[roadmap](mvp-plan.md). Этот этап закрывает реализацию B05 и локальный дефект
recompile из B12; внешний запуск по-прежнему NO-GO до оставшейся приёмки.

## Принятые настройки

В `/admin/system` добавлена независимая панель **Beta access and spending**.
Администратор видит состояние; superadmin меняет настройки с причиной и
подтверждением. Изменения записываются в аудит. Версия настроек защищает от
перезаписи параллельным оператором. Ошибка общей System diagnostics не блокирует
эту панель.

| Параметр | Начальное значение / поведение |
| --- | --- |
| Открытая регистрация | 30 публичных аккаунтов; лимит меняется в админке |
| Приглашения | Дополнительные места сверх публичного лимита, один код / один аккаунт / 7 дней; создание и отзыв в админке |
| Начальные кредиты | 3, выдача идемпотентна; приглашение не даёт дополнительных кредитов существующему аккаунту |
| Длительность | 7 минут; меняется в админке, новые звонки получают новое значение |
| Параллельность | 1 звонок на аккаунт; 2 на весь сервис, общий предел меняется в админке |
| Частота | 3 начала / скользящий час и 10 / UTC-день на аккаунт |
| Получатель | 2 начала за последние 24 часа суммарно со всех аккаунтов |
| Валюта | USD |
| Денежный лимит | Сумма задаётся в админке; изначально не заполнена, новые платные запросы запрещены |

Публичный счётчик учитывает созданные аккаунты, включая незавершённую регистрацию;
удаление не освобождает место. Миграция включает существующих обычных пользователей
в исходное число; staff не включён. При необходимости оператор увеличивает cap.
Проверка лимита и создание пользователя находятся в одной транзакции; ошибка
создания откатывает счётчик и использование приглашения. Хранится только SHA-256
случайного 256-битного кода; сам код возвращается один раз при создании. Автоматической
рассылки приглашений нет. У регистрационной формы есть необязательное поле кода,
подсказки и ошибки переведены для EN/DE.

## Денежный контроль

API и отдельный worker используют один PostgreSQL-контроль. Перед каждым реальным
запросом резервируется консервативная сумма. Проверка остатка и запись резерва
атомарны, в том числе при конкурирующих запросах разных процессов. Сохранённый
идентификатор одного запроса не списывается второй раз. Повторное чтение существующей
подготовки доступно и при остановленных расходах.

Начальные **защитные оценки**, редактируемые в расширенных настройках:

| Операция | Резерв USD |
| --- | --- |
| Минута звонка: voice + Realtime + recording | 2.00 |
| Один text-запрос, включая подготовку / модерацию / перевод | 0.50 |
| Один запрос итоговой транскрипции | 1.00 |
| Одна отправка SMS Verify | 0.50 |
| Одно транзакционное письмо | 0.01 |

Это **не тарифы провайдеров и не измеренная стоимость**. Семиминутный звонок
резервирует 14 USD сразу; подготовка, отдельные text/ASR запросы и сообщения
учитываются дополнительно. Неуспешный звонок или сообщение не возвращают денежный
резерв: запрос мог быть оплачен при потерянном ответе. Резерв выходит из расчёта
через 24 часа, независимо от запоздавшего invoice. Кредит пользователя при
подтверждённом отсутствии соединения возвращается по прежним правилам.

Если следующий резерв не помещается, провайдер не вызывается. Пустой бюджет или
снятое **Allow new paid requests** также останавливают новые платные запросы.
Чтение результатов, ввод уже полученного OTP и Stop остаются доступны. Для новой
регистрации есть предварительная проверка бюджета до создания аккаунта; атомарный
контроль непосредственно перед SMS всё равно может отказать при конкурирующем
расходе — в таком случае аккаунт остаётся ожидающим подтверждения и доступен resend.

При пересечении 80% и отказе по бюджету пишутся безопасные агрегатные события
`beta_budget_threshold_reached` / `beta_budget_request_blocked`; текущее состояние
видно в админке. Доставка тревоги оператору ещё относится к B12. Прогнозные резервы
не гарантируют совпадение со счётом провайдера: перед GO нужны калибровка по B09,
контроль upstream-тарифов/географии, provider billing alerts и мониторинг затрат,
не связанных с отдельным запросом (аренда номера, длительное хранение).

## Звонки и отказы

Допуск резервирует полный максимум длительности; изменение настройки не меняет
уже допущенный звонок. Таймер приложения и reconciliation используют это значение.
В Twilio Call create передаётся `timeLimit`; его поддерживает
[официальный Call resource](https://www.twilio.com/docs/voice/api/call-resource).
При неизвестном результате остановки слот остаётся занят до подтверждения
терминального статуса провайдером. Это намеренный отказ в новом допуске, требующий
разбора reconciliation, а не повод вручную обнулять счётчики.

Все допущенные попытки считаются в ограничениях частоты, включая failed/refunded.
Глобальный recipient cap использует отдельные HMAC-отпечатки с доменным разделением
и ключами data keyring: удаление исходного номера из звонка не сбрасывает окно.
Предыдущие ключи нужно сохранять минимум на оставшийся срок окна при ротации.
Записи старше 24 часов удаляются при следующем успешном допуске; обслуживание при
отсутствии трафика и срок хранения audit/spend хвоста входят в B11.

`CALL_MAX_*` из env остаются fallback для memory/test режима; PostgreSQL runtime
получает эти значения из панели беты. Существующий выключатель **Outbound calls**
останавливает новые звонки независимо от бюджета. Бюджетная пауза шире: касается
также сообщений и обработки текста. Ни одна из пауз сама не завершает активный звонок.

## Исправление фоновых ошибок B12

Детерминированный тест воспроизвёл PostgreSQL `40P01`: пересборка удерживала brief
и ожидала FK-блокировку пользователя, а text mutation удерживала пользователя и
ждала brief. Исправлен порядок блокировок owner → brief. Блокировка пользователя
в text mutation изменена на `FOR SHARE`: она сохраняет защиту от удаления/смены
статуса и совместима с FK-вставкой `call_events`.

Устаревший text artifact при быстрой новой компиляции теперь завершает свою job
как `cancelled`, оставляет доказательство `TEXT_ARTIFACT_STALE` в попытке и не
порождает ложный retry/dead letter/background error. Это не подавление прочих ошибок:
неожиданные сбои по-прежнему видны. В безопасных логах сохраняются контролируемый
код ошибки и ограниченная цепочка cause без SQL, аргументов, сообщений и stack.
Twilio webhook fixture дополнен отсутствовавшим `calls().fetch`; тесты теперь
проверяют отсутствие неожиданных фоновых ошибок при завершении.

## Локальная проверка и ввод в работу

Тесты используют свежую изолированную PostgreSQL-базу и подставные провайдеры;
реальные SMS, письма и звонки в ходе проверки не отправлялись.

- Полный прогон: **1 163 passed / 0 failed**, 143 файла, без skips: contracts 97,
  web 189, API 877. Нет неожиданных `background_call_operation_failed`,
  `durable_worker_operation_failed` или `DATABASE_DEADLOCK`; fault-injection тесты
  намеренно пишут ожидаемые ошибки доставки/лимитера.
- Typecheck, lint и build: по 3/3 пакета. Сборка использовала отдельный каталог Next,
  не заменяя сборку работающего приложения. Copy check: 587 файлов.
- Каталог: 70 миграций, 0070 применена к основной локальной БД; API перезапущен после
  проверки нулевых активных звонков/подготовок, `/health/ready` возвращает 200.
- Регрессионные проверки: конкурентный cap/одноразовое приглашение/rollback;
  идемпотентные кредиты; общий USD резерв из разных клиентов; неизвестный provider
  terminal и удержание слота; recipient cap после редактирования исходного номера;
  новые и повторные подготовки при пустом бюджете; отсутствие реального dispatch;
  admin RBAC/Origin/revision/независимость от diagnostics; передача Twilio timeLimit;
  воспроизводимый порядок блокировок и отмена superseded text job.
- Browser: отдельный стенд 3100/4100, вымышленный superadmin, изолированная БД и mock
  providers. Проверены вход, System, значения 30/7/2/USD, пустой бюджет и предупреждение,
  поля и действие создания приглашения. Native confirm при сохранении открылся,
  но in-app automation не смог его подтвердить; вкладка закрыта. Успешное браузерное
  сохранение не засчитывается, HTTP-сохранение и конфликты проверены тестами.

Основное приложение 3000/4000 и Twilio-only ingress/тоннель оставлены работающими.
Реальный бюджет не менялся; исходный публичный счётчик после миграции — 7 из 30.
Машиночитаемый [протокол](../Design/beta-controls-2026-09-14/evidence.json) содержит
только агрегатные значения и границы проверки.

Перед использованием: применить additive migration `0070_beta_controls.sql`,
перезапустить API и отдельный worker, открыть `/admin/system`, ввести согласованный
бюджет USD и причину изменения. Не добавлять сумму в env. Не откатывать миграцию
удалением таблиц: при откате кода сначала закрыть публичный доступ и новые расходы,
так как старый бинарник не исполняет новые ограничения.
