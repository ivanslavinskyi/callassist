## 3. Автоподстановка имени и фамилии

### Поведение

- Источник для нового плана — **текущий профиль**: регистрационные имя и фамилия
  с учётом последующих изменений в настройках аккаунта.
- Оба поля сразу заполнены и доступны для обычного редактирования, с доступными
  подписями. Короткое пояснение сообщает, что начальные значения взяты из профиля
  и их можно изменить для этого звонка. По уточнению пользователя от 2026-09-08
  не добавлять кнопку разблокировки, `readOnly`, переключатель режима или модальное
  подтверждение.
- Изменение относится только к плану; профиль аккаунта не обновляется.
  Отдельная кнопка возврата к профильным данным также не нужна.
- Если профиль содержит пустое/невалидное имя, показать обычную валидацию.
  Не создавать видимость корректности невалидных данных и не блокировать
  пользователю возможность исправления.
- При редактировании/перекомпиляции существующего плана приоритет целиком у
  `initialValue`, включая отличающееся от профиля имя. Не подмешивать профиль
  к пустым полям сохранённого плана скрытым fallback: их нужно исправить явно.
  Сохранённая пара имён также сразу доступна для редактирования в форме.
- Пользовательские правки не затираются при ререндере, смене языка UI,
  повторной отправке, ошибке подготовки или обновлении данных профиля во время
  работы с формой. Новый профиль используется при открытии нового плана.

### Реализация

1. Передать из серверной страницы в `Dashboard`, затем в `CreateCallForm`
   только необходимые `id`, `firstName`, `lastName` с типами из contracts.
   Не сериализовать в клиент лишние поля `User`.
2. Добавить отдельный prop для профильных значений. Инициализировать форму один
   раз: полный `initialValue`, если он передан; иначе defaults + профильные имена.
   При смене аккаунта исключить сохранение состояния предыдущего пользователя.
3. Сохранить обычные редактируемые inputs и добавить пояснения EN/DE в
   существующую структуру `apps/web/lib/i18n/`. Сохранить лимит 80 символов,
   Unicode, существующую нормализацию и серверную валидацию.
4. Проверить оба места переиспользования формы в `live-call.tsx`. Не менять
   контракт создания плана, компилятор или схему БД ради этой автоподстановки.
5. Проверить, что preview раскрытия представляемого человека, payload подготовки,
   review и новая компиляция используют именно видимые значения формы.
   Изменение имени в утверждённом плане требует обычной перекомпиляции и нового
   одобрения; immutable execution snapshot не переписывается.

Приёмка: регистрация → новый план без повторного ввода имени; намеренное изменение
→ review с изменённым именем и неизменным профилем; редактирование
старого плана после изменения аккаунта; длинные и Unicode-имена; ошибки отправки;
клавиатура и мобильный экран; EN/DE. Покрыть правила приоритета значений и сохранения
ручного ввода небольшими поведенческими тестами, а доступность и интерфейс проверить
в браузере. Не добавлять тяжёлый тестовый стек только ради статической формы.

## 4. Агент сам завершает разговор

### Основное решение

Добавить Realtime function tool `end_call` с ограниченным набором причин,
например `objective_resolved`, `recipient_requested_end`, `cannot_proceed`,
`voicemail`. Причина не означает автоматически успешное выполнение задачи.
Модель сообщает намерение завершить разговор; сервер управляет прощанием,
воспроизведением и разрывом линии.

Инструмент доступен в содержательной части после согласия и обязательного opening.
Пути отсутствия согласия и ошибки записи сохраняют собственные правила.
Модель должна завершать разговор после выполнения цели, отказа продолжать или
предусмотренного stop condition; не завершать его из-за обычной паузы, ожидания
ответа/перевода звонка, слова «спасибо» или цитирования прощания. Подчинять
voicemail текущей утверждённой политике; не добавлять отдельный AMD-проект.

Не распознавать завершение регулярным выражением по тексту транскрипта.
Не использовать OpenAI SIP hangup API: текущая телефонная линия принадлежит Twilio.

### Контролируемая последовательность

1. Объявить tool и обрабатывать полный `function_call` из успешного
   `response.done`. Проверять имя инструмента, JSON, enum причины, текущие
   response/attempt и фазу разговора. Дедупликация по attempt + tool `call_id`;
   отклонённые, отменённые и устаревшие ответы не завершают звонок.
2. Переходы вынести в небольшой контроллер с состояниями
   `active → farewell_pending → farewell_playing → terminating → closed`.
   Перед финальной фразой агент может кратко подвести итог. Само прощание создаёт
   сервер отдельным аудиоответом по короткому шаблону языка разговора.
   Это исключает зависимость от обещания модели вызвать tool после уже сказанного
   прощания. Не допускать двух прощаний и дополнительных вопросов в этой фазе.
3. Вернуть `function_call_output` для исходного вызова, затем создать ровно один
   ответ с назначением `farewell`; запретить повторный tool в этом ответе.
   Подавить конкурирующие автоматические ответы VAD/DTMF в фазе прощания,
   сохранив обнаружение перебивания. Учёт usage должен включать этот ответ.
4. После отправки последнего аудиочанка успешного farewell поставить уникальный
   Twilio `mark`, привязанный к attempt, response и поколению воспроизведения.
   `response.done` означает завершение генерации, но не конец воспроизведения
   в телефонной линии. Завершать нормально только после соответствующего mark.
5. Если собеседник заговорил до фактического завершения прощания, отменить pending
   hangup, инвалидировать mark **до** отправки `clear`, остановить/отменить остаток
   ответа и вернуться в `active`. Синхронизировать историю модели с реально
   воспроизведённым аудио. Поздний mark от очищенного буфера не имеет силы.
   После уточнения можно снова завершить через новый вызов tool; явный отказ
   продолжать не должен приводить к повторному обсуждению цели.
6. После подтверждённого воспроизведения выполнить единый идемпотентный путь
   завершения привязанной попытки. Закрытие Twilio WebSocket продолжит существующий
   TwiML до `<Hangup>`. Для ограниченного по времени резервного пути использовать
   `telephonyProvider.stopCall(providerCallId)` и existing reconciliation.
   Не вызывать пользовательский `CallService.stop()`.
7. Добавить watchdog как на генерацию farewell (в том числе отсутствие
   `response.done`/аудио), так и на ожидание mark. Исходные настройки для проверки:
   до 10 секунд на генерацию; ожидание mark — по оставшейся длительности отправленного
   аудио плюс 2 секунды запаса, с общим пределом фазы прощания 15 секунд.
   Это предлагаемые параметры, их нужно подтвердить live-drill. Таймаут — аварийное
   завершение с отдельной причиной, а не фиктивное «прощание прослушано».
8. Привязать резервное завершение к точным `callBriefId`, `callAttemptId` и
   `providerCallId`, проверять актуальность перед внешним действием. Не использовать
   «последнюю попытку» вместо попытки текущего потока. Ошибка/таймаут Twilio допускает
   ограниченные повторы; сначала проверять фактическое состояние после неопределённого
   результата. Терминальный звонок — успешный no-op, а не повторная финализация.
9. До необратимого завершения сохранить намерение и возможность восстановления
   через существующие durable jobs. Проверить пригодность текущего reconciliation
   с его leases и сроками; если нужен новый persisted reason/deadline — добавить
   минимальную forward migration. Перезапуск процесса и потеря callback не должны
   оставлять попытку бесконечно активной. Существующий максимум длительности звонка
   остаётся последним ограничением, а не обычным способом повесить трубку.

Основания для протокола: [OpenAI Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)
описывает полный function call в `response.done` и ответ через `function_call_output`.
[Twilio Media Streams](https://www.twilio.com/docs/voice/media-streams/websocket-messages)
описывает подтверждение проигрывания через mark, в том числе возврат marks при `clear`;
поэтому требуется инвалидировать очищенные поколения.
[Twilio Stream](https://www.twilio.com/docs/voice/twiml/stream) описывает продолжение
TwiML после закрытия WebSocket. [Twilio Call resource](https://www.twilio.com/docs/voice/api/call-resource)
документирует управление активной линией. Документация проверена 2026-09-08;
конкретный контроллер и параметры выше — предлагаемое решение проекта.

### Статусы, наблюдаемость и границы

- Расширить `packages/contracts/src/call-telemetry.ts`: различать намерение агента,
  подтверждение playback, отмену из-за перебивания, fallback и подтверждение конца.
  Сохранять безопасные коды/идентификаторы и задержки, не тексты беседы и имена.
- Нормальное завершение на уровне телефонии становится `completed` по provider
  status/reconciliation. Ручное `stopped` сохраняет свой смысл. Не приравнивать
  `objective_resolved` из аргумента модели к подтверждённому бизнес-результату.
- Сохранить порядок записи транскриптов, usage и закрытия realtime sessions;
  дождаться либо обеспечить надёжное продолжение необходимых асинхронных записей.
  Последнее прощание не должно исчезать из записи/расшифровки из-за гонки.
- Запись, ASR, стоимость, credits и SSE проходят существующий путь финализации
  ровно один раз даже при совпадении Stop, tool call, stream stop и webhook.
- Добавить переключатель автозавершения обычного разговора, по умолчанию выключенный
  до проверки. Отключение не должно отменять уже начатое завершение или влиять на
  consent/error-пути. Это даёт быстрый откат поведения без отката данных.
- Эта правка закрывает жизненный цикл обычного разговора. Она не доказывает
  выполнение всех требований R08 по принудительной voice safety.

### Проверки телефонии

| Сценарий | Ожидаемый результат |
| --- | --- |
| Цель выполнена; человек молчит и не кладёт трубку | Одно полное прощание; линия закрыта агентом. Цель: запрос завершения ≤1 секунды после валидного playback mark; подтверждение Twilio измеряется отдельно. |
| «Мне неудобно», «закончим», задача не решена | Короткое завершение, без навязывания продолжения и ложного успешного результата. |
| Пауза, hold, промежуточное «спасибо», неясный ответ | Самопроизвольного hangup нет. |
| Человек перебивает прощание вопросом | Pending hangup отменён; очищенный/поздний mark игнорируется; беседа продолжается. |
| Повторные/невалидные tool calls, старый response, отменённый ответ | Нет лишнего прощания или завершения чужой/новой попытки. |
| Нет аудио, нет response.done, нет mark, потеря сокета | Ограниченное ожидание и наблюдаемый fallback, без вечной активной линии. |
| REST timeout/ошибка, процесс перезапущен, callback потерян/задвоен | Восстановление и подтверждение состояния; один учёт usage/кредитов и один итог. |
| Одновременно ручной Stop и агент; человек завершает первым | Идемпотентность, сохранение правильной причины и терминального статуса. |
| Отказ от consent, ошибка записи, DTMF, voicemail policy | Существующие ограничения и правила сохраняются. |
| После завершения | UI выходит из live; запись и финальная ASR доступны согласно retention; последний фрагмент и стоимость учтены. |

Автоматизация: fake sockets/timers в `openai-realtime-bridge.test.ts`, отдельные
тесты контроллера состояний, сервис/telephony tests и telemetry contracts.
Если меняется persisted intent — parity memory/PostgreSQL и integration-тест
восстановления с leases, повторными событиями и неактуальной попыткой.
После локальных тестов — контролируемые звонки с согласным тестовым получателем:
минимум обычное завершение, отказ, перебивание и молчание после прощания;
проверить все поддерживаемые языки шаблона в тестах, а live — как минимум de-CH и en.
Сохранить обезличенные timelines и измерения задержек. Новые реальные звонки
не выполняются в рамках подготовки этого плана.

## 5. Порядок реализации и выпуск

1. **A — favicon:** ассеты, metadata, проверка вкладки и production build.
2. **B — профильные имена:** передача данных, обычные редактируемые поля, EN/DE,
   проверки создания, изменения и повторной подготовки плана.
3. **C — завершение:** сначала контроллер и тесты событий, затем tool/prompt,
   playback, attempt-bound hangup, восстановление, telemetry и общий lifecycle.
4. **D — приёмка:** целевые тесты, затем `corepack pnpm typecheck`,
   `corepack pnpm lint`, `corepack pnpm test`, `corepack pnpm build` и
   `corepack pnpm copy:check`. При изменении схемы — проверка миграций на отдельной
   тестовой БД. Зафиксировать выполненные проверки и недоступные внешние проверки
   раздельно, без переноса старого evidence на новую реализацию.
5. **E — контролируемое включение:** включить флаг в тестовом окружении, провести
   live-drill; после успешной приёмки включать для целевого окружения. Следить за
   долей fallback/ошибок, преждевременными завершениями и хвостом длительности
   после прощания. При регрессии отключить флаг и сохранить evidence.

A и B можно принимать независимо от C. Код, успешные локальные проверки и реальное
подтверждение провайдера — отдельные этапы. Производственный деплой в этот план
как уже разрешённое действие не включён.
