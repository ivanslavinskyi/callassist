# Языки интерфейса, задания, звонка и результата

Дата: 9 сентября 2026. Статус: архитектура реализована в рабочем дереве; workflow уточнён после пользовательского теста для сокращения выбора языков. Требование пользователя: расширять интерфейс до 7–15 языков независимо от языка ввода, телефонного разговора и результата.

Для реализации использовать [единый подробный план W00–W10](unified-implementation-plan-2026-09-09.md). Этот документ сохраняет основания языковых решений; порядок работ, API, миграции и критерии готовности собраны в едином плане.

## 1. Решение

Определять язык пользовательского запроса существующим compiler и предлагать его как язык плана и результата. Пользователь может изменить этот выбор. Хранить определённый язык текста отдельно от выбранного языка помощи; смена интерфейса не меняет уже созданное задание.

В форме выбирается только «Язык звонка». После компиляции рядом с планом показывается «Язык плана и результата: русский · Изменить»; исправление раскрывается до утверждения. Язык приложения остаётся в общих настройках. Сводка и перевод расшифровки используют сохранённый язык задачи без дополнительных меню языков; доступны оригинал и перевод.

Пример: интерфейс на английском, задача написана по-русски, звонок на немецком Швейцарии. Кнопки остаются английскими; план, уточняющие вопросы и итог предлагаются по-русски; исполняемый план и разговор — по-немецки. Переключение приложения на украинский не меняет эти данные.

## 2. Независимые значения и возможности

| Значение | Назначение и источник |
| --- | --- |
| `uiLocale` | Меню, кнопки, системные уведомления, форматирование интерфейса. Выбирается пользователем для приложения. |
| `inputLanguageDetection` | Наблюдение о конкретной версии ввода: основной язык или отсутствие определённого языка, признак смешанного текста, источник/версия определения. Начальный источник — существующий `sourceLanguage` compiler. |
| `callLocale` | Язык и нужный региональный вариант телефонного разговора. Явный выбор из поддержанных голосовых сценариев; существующий `rawBrief.locale` сохраняет эту роль. |
| `taskContentLanguage` | Сохранённый язык общения с пользователем по этой задаче: уточнения, проверка плана и язык результата по умолчанию. Хранится с источником выбора: task override / account preference / detection / initial fallback. |
| `artifact.targetLanguage` | Язык конкретного перевода плана, расшифровки или сводки. Пользовательский workflow берёт его из `taskContentLanguage`. Модель данных сохраняет независимый язык артефакта и прежние версии для совместимости. |

Использовать нормализованные языковые теги BCP 47: например `ru`, `uk`, `de-CH`; письменность/регион добавлять при необходимости. Код не следует ограничивать ровно двумя буквами или определять эквивалентность через безусловное отбрасывание всего после дефиса. Основание: [W3C — Choosing a Language Tag](https://www.w3.org/International/questions/qa-choosing-language-tags).

Валидация кода языка и доступность функции — разные проверки. Нужны независимые наборы возможностей:

- языки интерфейса с готовыми словарями;
- фактически опубликованные языки каждой CMS-страницы;
- проверенные направления перевода текста и генерации итога;
- разрешённые голосовые локали с соответствующими возможностями провайдеров и текстами звонка.

Можно переиспользовать справочник названий языков, но нельзя выводить все четыре набора из одного `SUPPORTED_LOCALES`. API отдаёт доступные варианты для соответствующей функции. Добавление языка интерфейса не включает автоматически звонки или переводы на нём.

### Уточнение: названия языков звонка и один английский

- Названия в поле «Язык звонка» брать из общего UI-словаря по `uiLocale` и стабильному коду `callLocale`. Например, `de-CH` отображается как «German (Switzerland)» в EN и «Deutsch (Schweiz)» в DE. Смена интерфейса меняет подпись, сохраняя выбранное значение. Новые UI-словари включают названия всех доступных языков звонка.
- По согласованию с пользователем оставить в выборе для новых задач один английский — **британский, `en-GB`**. Подпись единственного варианта: «English» / «Englisch» / «Английский», согласно языку интерфейса. `en-US` убрать из списка выбора.
- Отделить список выбираемых языков от совместимого контракта чтения: сейчас `SUPPORTED_CALL_LANGUAGES` одновременно порождает `callLocaleSchema`. Сохранить поддержку `en-US` для прежних заданий, fallback, утверждённых планов и истории; прежние данные и hashes не переписывать в `en-GB`. Новая задача на основе старой при смене языка проходит обычную компиляцию и утверждение.
- Приёмка: в немецком интерфейсе все варианты имеют немецкие названия; английский в новом выборе один; переключение UI не меняет `callLocale`; прежний звонок с `en-US` открывается корректно. Общий справочник также используется для отображения языка в review и истории, где старый вариант при необходимости явно подписывается как американский.

## 3. Определение языка и создание задачи

1. Получать определение в уже существующем запросе compiler, без отдельного LLM-вызова на каждый ввод символа. Анализировать прежде всего собственную формулировку objective; использовать контекст как дополнительный сигнал. Имена, адреса, цитаты и вставленные чужие документы не считать достаточным основанием для выбора языка пользователя.
2. Считать ответ модели подсказкой. Нормализовать тег и проверить поддержку. Для короткого, неоднозначного или смешанного ввода допускать неопределённость; не использовать самооценку confidence модели как проверенную вероятность.
3. Для новой задачи приоритет такой: явная настройка задачи → поддержанный определённый язык ввода → резервный язык аккаунта → поддержанный язык интерфейса → английский. Уже сохранённый контекст задачи сохраняется. Найденное или резервное значение можно исправить при проверке плана; по стране номера язык не определяется.
4. Язык аккаунта — дополнительная резервная настройка для случая, когда язык запроса не определён или не поддерживается. По умолчанию отдельное значение не задано; настройка не переопределяет распознанный язык ввода.
5. Показать найденное значение рядом с планом: «Язык плана и результата: русский · Изменить». Не требовать отдельного подтверждения языка в обычном однозначном случае.
6. Привязать результат определения к версии исходного ввода. Ответ для старой версии не должен изменить новое задание. После первого показанного review или ручного выбора сохранить язык задачи: большая правка текста может предложить смену, но не переключает его автоматически.
7. Переводить также содержательные уточняющие вопросы и объяснения compiler. Сохранять ID вопросов, коды ошибок и условия политики; перевод не меняет их смысл или готовность к звонку. Ответы пользователя могут быть на любом поддерживаемом языке ввода. Общие подписи и технические ошибки интерфейса остаются в `uiLocale`.

У текущего compiler уже есть исключение: `blockingIssues.question` предписано формировать на языке objective; остальные human-facing поля — в `callLocale`. Поэтому готовый `sourceLanguage` и вопросы на языке ввода ещё не решают ручной выбор языка помощи и язык всех пояснений. Для первого этапа подходит отдельная проекция отображения compiler-результата на `taskContentLanguage`, с сохранением уже подходящих по языку вопросов; для blocked/clarification результата она привязана к compilation и hash исходного содержимого, а не требует наличия уже утверждённого execution snapshot.

## 4. Проверка плана и звонок

1. Compiler создаёт один исходный план на языке звонка. Отдельная фоновая задача переводит его поля для пользователя. Не генерировать два независимых плана из сырого запроса и не переводить пользовательскую версию обратно для исполнения.
2. Перевод для проверки готовить автоматически, когда язык отличается: он нужен для осознанного утверждения. Показывать вкладки «На русском» и «На языке звонка — немецкий». Названия локализованы на языке интерфейса, содержимое имеет собственные `lang`/направление текста.
3. Разрешить исправление языка задачи в одном раскрываемом control до утверждения. После утверждения доступны исходный план и сохранённый перевод на язык задачи; selector не показывается. При отсутствии перевода показать состояние и повтор после ошибки; не подменять его молча исходным языком.
4. При утверждении записать точный исходный snapshot и реально выбранную версию проверки: `compilationId + snapshotHash + reviewLanguage + reviewArtifactId + reviewContentHash`. Для проверки оригинала явно записывать `reviewMode=original`; отдельный перевод не нужен.
5. Изменение задачи или языка звонка создаёт новую compilation и требует нового утверждения. Старый перевод может оставаться в истории, но не подходит для нового плана. Просмотр другого языка после утверждения не переписывает историческую запись и не меняет исполняемый план.
6. Runtime получает прежний утверждённый план на `callLocale`. Язык браузера, текущий просмотр перевода и язык итогов не являются входами в принятие решений во время звонка.

До запуска пользователь должен осознанно проверить доступный вариант. Сбой перевода не является поводом автоматически утвердить непонятный оригинал.

## 5. Расшифровка и итог

**Полная расшифровка — перевод по запросу.** После завершения ASR показать оригинал и кнопку «Перевести на русский» без меню другого языка. Использовать сохранённый язык этой задачи, а не заново читать текущий UI или определять язык старого objective. После готовности остаются вкладки «Оригинал / Русский» без дублирующей кнопки показа перевода.

Первое нажатие создаёт фоновую задачу; далее показываются «Переводится», «Повторить» или вкладки «Оригинал / Русский». Повторное открытие использует готовый перевод без нового provider-запроса. В будущем автоматический перевод можно включить настройкой, не меняя модель данных.

Оригинал остаётся неизменным. Перевод связан с его content hash, сегментами, ролями и временными отметками. Нельзя считать весь фактический разговор немецким только потому, что выбран `callLocale=de-CH`: возможны переключения языка. Для смешанного текста перевод сохраняет уже понятные фрагменты и переводит остальные; неизвестные роли не выдумываются. Пропуск перевода допустим лишь при подтверждённом совпадении языка/письменного варианта исходного текста с целевым, по явной политике сопоставления.

**Краткий итог — автоматически на языке задачи.** Worker формирует ответы, неизвестные и следующие шаги прямо из исходной расшифровки, с `targetLanguage=taskContentLanguage` и ссылками на исходные реплики. Перевод полной расшифровки для этого не нужен. Отдельного выбора языка сводки нет. Сводка остаётся AI-интерпретацией с источниками.

Переключение между оригиналом и переводом после звонка меняет только отображение. Оно не меняет прежнее утверждение плана и не вызывает новый звонок. Для уже утверждённого звонка язык результата сохраняется в контексте попытки, чтобы последующие настройки аккаунта его не переписали. Прежние переводы на другие языки не удаляются; упрощение интерфейса не требует миграции артефактов.

## 6. Данные, API и совместимость

- Хранить настройки языка задачи и наблюдения определения отдельно от исторических raw/compiled объектов, участвующих в hash v1. Не добавлять туда default-поля так, чтобы reader изменил hashes прежних подтверждений. Новую политику review вводить явно версионированно.
- Не вводить столбцы `plan_ru`, `plan_de` или отдельные endpoints для каждого языка. Производные версии хранятся строками с типом, языком, версией источника, состоянием и зашифрованным содержимым. Схемы содержимого плана, transcript и summary остаются типизированными, даже если общие метаданные переиспользуются.
- Для создания/чтения перевода API принимает ID доступного пользователю источника и `targetLanguage`; сервер проверяет владельца, поддерживаемую операцию и текущую версию. Предпочтение языка не является частью проверки доступа.
- Ключ дедупликации: источник/попытка + вид операции + source content hash + target language + версия преобразования; для summary также hash утверждённых вопросов/исполнительного плана. Проверять соответствие источника ещё раз перед публикацией.
- Пересоздание ASR делает прежние переводы и сводки устаревшими. Смена UI не делает их устаревшими. Смена языка просмотра не запускает повтор уже готовой операции.
- Применить существующие механизмы durable jobs, PostgreSQL/memory repositories, шифрования, удаления, экспорта, ограниченных повторов и учёта расходов. Производные тексты не продлевают хранение аудио.

## 7. Что отвязать для 7–15 языков интерфейса

Сейчас `UiLocale`, `ContentLocale`, account locale, маршрутизация и часть SQL-ограничений отдельно зашиты на EN/DE. Это требует однократной подготовки слоя локализации. Точечное добавление третьего значения только в словарь не решит задачу.

1. Централизовать реестр доступных UI-словарей, обработку префиксов маршрутов, cookie и fallback. Убрать бинарные развилки EN/DE и ограничения количества ровно двумя локалями. Различать системный UI fallback и выбранный язык пользовательского текста.
2. Согласовать сохранение UI-настройки в аккаунте: текущий переключатель меняет cookie/маршрут, а сохранённое значение аккаунта используется в том числе для email. Явно определить синхронизацию, чтобы язык письма не оставался случайно старым.
3. Развести доступность UI и переводов публичного контента. Расширение UI до 15 языков не должно автоматически требовать 15 CMS-переводов для публикации одной версии страницы. Готовность нужных переводов определяется политикой конкретной страницы/выпуска.
4. Для CMS/onboarding использовать явный выбор опубликованной локализации и видимый fallback. В принятии документа записывать язык реально показанной версии, а не язык кнопок. Старые опубликованные версии и записи принятия не переписывать.
5. Одной совместимой forward migration заменить жёсткие DB CHECK со списком EN/DE на проверку формата/ссылку на реестр, пригодную для расширения данными. Доступность конкретного UI-языка проверяется отдельным реестром сервиса. Следующий UI-язык не требует новой миграции схемы call domain или изменения `callLocaleSchema`; прежние значения продолжают читаться.
6. Добавление очередного UI-языка после этого означает словари, при необходимости CMS-контент и проверку отображения/RTL/маршрутов. Схемы задания, утверждения, звонка и результатов от этого не меняются.

## 8. Порядок внедрения и проверка

1. Зафиксировать независимые значения, resolver приоритетов и реестры возможностей; подготовить совместимые схемы хранения и убрать связь языка задания с текущим UI.
2. Внедрить выбор/определение языка задачи, проекцию уточнений и P02 с версионным утверждением.
3. Добавить автоматический итог P04 и перевод полного transcript по запросу P03 на общей инфраструктуре производных данных.
4. Подготовить UI/CMS к расширению и подключать словари отдельными пакетами. Сами переводы интерфейса на 7–15 языков — отдельный объём, а не неявная часть P02–P04.

Проверить комбинации: EN UI + RU ввод + DE-CH звонок; DE UI + UK ввод + FR-CH звонок; одинаковые языки; разные письменности; смешанный/короткий ввод; ручной выбор; смена UI в середине работы; редактирование objective; старый ответ определения; уточнения до готового плана; смена review-варианта; повтор перевода; регенерация ASR; удаление во время фоновой задачи; добавление UI-локали при прежних списках голосовых и текстовых возможностей. Часть сочетаний намеренно включает UI-язык, не поддерживаемый для перевода, чтобы проверить явный выбор вместо скрытой подмены.

Прежние 17–29 дней — ориентир P02–P04 до этой детализации. Подготовка UI/CMS, уточнения и матрица независимых языков уточняют объём; перед реализацией нужна переоценка по пакетам. Этот документ не утверждает, что локализация на 15 языков входит в прежний диапазон.
