# Live v4: последний звонок и план стабилизации завершения

**Последующее изменение:** [имплементация от 1 октября](live-stabilization-implementation-2026-10-01.md)
заменяет описанный ниже v4. Аудит сохраняет исторические доказательства исходного звонка;
его transcript и результат автоматически не переписываются.

Проверено 1 октября 2026 года. Статус: **анализ и предложение, без изменения runtime**.
Дополнено разбором календарной ошибки в итоговом отчёте по скриншоту пользователя.
Подробный [план имплементации](live-stabilization-implementation-plan-2026-10-01.md)
содержит контракты, файлы, порядок работ и критерии приёмки; календарная часть не
добавляет новых model calls, tools, агентов или runtime orchestration.
Этот разбор дополняет [отчёт о v4](live-combined-stabilization-implementation-2026-09-30.md)
результатами следующего реального звонка. Предыдущие положительные тесты не означают,
что качество завершения v4 прошло приёмку на телефоне.

## Вывод по последнему звонку

**Завершение инициировало приложение.** В сохранённой расшифровке нет финального
резюме записи и прощания: последняя реплика ассистента лишь повторяет адрес.
Приложение ошибочно допускает такое содержимое в качестве проигранного завершения.
Это воспроизводимый дефект оркестрации, а не просто недостаточно настойчивая инструкция модели.

Проверенная попытка: `dc5b115e-340f-43fa-a476-05e4fdafdf66`.
Доказательства: 37 durable events, 11 provider operations, утверждённый execution snapshot,
native transcript и финальная расшифровка, журнал действий, assessment, API log,
read-only Twilio GET и воспроизведения на текущих исходниках.

Активный процесс API: PID 10784, запущен 01.10 в 09:46:51 Europe/Zurich;
коммит `55f2ca157a3ea167c57eb8a4d2c0f3bcc927e4e9`, runtime `live-managed-v4`.
Все 636 хешей файлов совпали с сохранённым v4 candidate. Проверены живой процесс,
его лог и readiness. Это **локальный работающий runtime с публичным Twilio-туннелем**;
проверка не устанавливает состояние отдельного удалённого production-сервера.

В звонке была одна сессия `gpt-live-1`, голос `cedar`, семь успешных делегаций
`gpt-6-luna`, один синтез начального disclosure. Ошибок/таймаутов backend в этой
попытке нет; медиана успешной делегации 1327 мс, максимум 2827 мс. В логе нет
`Live task decision requested` для task recovery: нельзя приписывать этот конкретный
сбой доказанному конфликту нескольких recovery-запросов.

## Дефекты и границы доказательств

### 1. Любая реплика может стать «прощанием» — P1

В [LiveClosingSpeech](../apps/api/src/voice/live-closing-speech.ts) нужны всего четыре
условия: backend завершён, есть непустой текст, есть voiced audio, прошла секунда
без нового voiced/text фрагмента. После подходящего Twilio mark вызывается hangup.
Смысл текста, наличие результата и прощания не проверяются.

В [UnifiedLiveCall](../apps/api/src/voice/unified-live-call.ts), `#requestClosing` /
`#startClosingSpeech`, gate создаётся сразу при принятии tool, до окончания continuation.
Текущая обычная фраза может попасть в gate хвостом. `backendCompleted()` делает этот
уже накопленный текст пригодным для закрытия. Отдельной границы новой финальной реплики нет.

Реальные времена согласуются с этим механизмом: повтор адреса начался до end_call,
закончился около завершения continuation, после чего был принят closing mark.
Изолированный тест воспроизводит hangup после «Understood, Example Street.» без
произнесения переданного результата и без goodbye. Старый unit test даже явно допускает
`Understood.` перед `backendCompleted()` как достаточный материал для mark.

### 2. Разрешение завершить и достоверность результата слишком слабо связаны — P1

`end_call` проверяет структуру аргументов; только `objective_resolved` требует
recipient evidence и подтверждённого appointment action. `cannot_proceed` и
`recipient_requested_end` не требуют отдельного основания, а `resultSummary`
проверяется лишь как строка длиной 2–400 символов. Он возвращается backend, но не
сохраняется в closing state; fallback знает только общее прощание.

Диагностика принимает `cannot_proceed` с выдуманным сообщением о подтверждении записи
и оплате даже без task evidence. Это доказывает слабость application validator,
**не** наличие такой выдуманной фразы в реальном звонке.

Отсутствие journal confirmation может объяснять избегание `objective_resolved`, но
почему backend выбрал `cannot_proceed` в этом звонке — гипотеза. Исправление должно
различать временный пробел в доказательствах и фактическую невозможность продолжить.

### 3. Backend отклоняет действие, а Live продолжает говорить как при успехе — P1

В реальном звонке запрос отклонён как `unconfirmed_details`; ни request, ни status check
не создали journal action. При этом Live произнёс «фиксирую», затем получил подтверждение.
В обычной фазе `audio()` передаёт native speech напрямую. Защита начинается внутри
принятого `request_appointment`, но не закрывает речь после его отклонения.

Диагностика подтверждает: после rejected tool искусственно поданная реплика о записи
проходит в Twilio, хотя журнал пуст. Это проверка transport guard, а не оценка вероятности,
с которой модель произнесёт такое обещание. В реальном звонке подобное расхождение уже есть.

Дополнительно frontend prompt всё ещё описывает возможный повтор never-transmitted
request, тогда как v4 backend и код используют status-only recovery. Эти инструкции
нужно привести к одному контракту. В данном звонке повторного запроса не было.

### 4. Полезный backend-текст может считаться отсутствием прогресса — P1

В [OpenAILiveConversation](../apps/api/src/voice/live-conversation.ts) обработчик
`response.output_item.done` сохраняет только function calls. Проверка полезного
ответа без tool смотрит в `response.completed.response.output`. По текущей официальной
документации forwarded lifecycle payload содержит пустой output.
Диагностика с реальной формой протокола — отдельный message item и финальный `output: []`
— после двух полезных ответов вызывает `LIVE_TASK_PROGRESS_MISSING`.

В последнем звонке такой ошибки нет. Это самостоятельный дефект, особенно важный
после разрешения backend возвращать обычные факты без обязательного report_task_state.

### 5. Ожидание «залипает» и фоновая тишина имитирует активность — P1/P2

`#waitingExpired` устанавливается после 45 секунд, но не сбрасывается новым recipient turn.
Диагностика показывает, что свежий полезный ответ всё равно получает
`waiting_deadline_exhausted`. Отдельно каждый `session.output_audio.delta`, включая
пакет тишины, обновляет `#nativeActivityAt`; такие пакеты откладывают обычный пятисекундный
recovery. Общий 45-секундный deadline остаётся, поэтому это не доказательство вечного зависания.

Оба дефекта воспроизведены, но не установлены как причина последнего звонка.
Контрольный тест подтвердил наличие ожидания уже с начала task phase: первоначальная
гипотеза о полностью отсутствующем таймере до первого task-ответа не подтвердилась.

### 6. Локальный таймаут выдаётся за освобождение backend — P1

После 30 секунд run помечается `settled/completed`, хотя provider terminal event или
подтверждённая отмена не пришли. `#backendOccupied` перестаёт учитывать этот run;
для устаревшего ответа запускается новый recovery. Диагностика воспроизводит новый
`response.create` без terminal event старого response и без подтверждения его остановки.

Локальная недействительность результата и фактическое окончание provider work — разные
состояния. В этом звонке таймаутов нет; нельзя объявлять такой конфликт его причиной.

### 7. Итоговый отчёт не получил известные приложению календарные факты — P1

На скриншоте «неизвестно, входит ли 3 октября в ближайшие две недели» — текст
**post-call summary**, а не высказывание Live и не код отказа appointment tool.
Проверен сохранённый artifact `52003ea4-2cff-4d45-97b4-6a3fa6d0f23b`, связанный
с исходной transcript revision `966bcbdd-bb43-4c7c-ab41-7b301d03b09c` и compilation
`724ca682-6b8c-48e2-a54f-8e369f17e735`. Его payload совпадает с показанным текстом.

**3 октября 2026 года, 11:00 разрешено утверждённым планом.** В execution snapshot
прямо присутствует окно `{date: "2026-10-03", startTime: "09:00", endTime: "18:00"}`,
зона `Europe/Zurich`. Дата — суббота. Звонок состоялся 1 октября; 3 октября находится
через два календарных дня. Для доказательства допуска достаточно уже утверждённого
окна: повторно интерпретировать фразу «две недели» вообще не требуется.

Детерминированный `validateAppointmentProposal` с этим слотом и временем звонка
возвращает `ok: true`, `startsAt: 2026-10-03T09:00:00.000Z`, если остальные
проверяемые условия подтверждены. С `detailsConfirmed: false` он возвращает
`unconfirmed_details` **до** проверки окна. Это тот же код отказа, который записан
во время звонка. Raw tool arguments не сохранены, поэтому нельзя приписывать реальному
tool искусственно реконструированные поля. Однако данных о календарном отказе
`outside_authorized_window` нет; код `unconfirmed_details` сам его не означает.

В compiler уже есть разделение интерпретации и вычисления: модель возвращает
`schedulingInterpretation`, `resolveAppointmentSchedule` разворачивает даты с доверенными
часами и зоной, затем сохраняются конкретные разрешённые windows. Воспроизведение
`relative_days(offset=1,count=14)`, исключение пятниц, время 09:00–18:00 на 1 октября
даёт в точности сохранённый набор окон. Это проверка эквивалентности, а не восстановление
не сохранённого исходного model selector. Отдельный compiler/calendar bug здесь не установлен.

Точное место потери данных:

1. [summary-input.ts](../apps/api/src/text-processing/summary-input.ts) получает полную
   compilation, но оставляет в context только objective, taskType и стороны разговора.
   Из плана передаёт текстовые successCriteria/orderedQuestions. Отбрасывает
   `appointmentAuthorization`, зону и календарные аннотации. Аргумента attempt у функции нет.
2. [text-artifact-service.ts](../apps/api/src/text-processing/text-artifact-service.ts),
   `#inputs`, читает правильную compilation исходной попытки, но добавляет лишь
   `transcriptPersisted` и `resultHandling`. Даты звонка, approval и windows не добавляет.
   Transcript segments имеют относительные секунды, а не абсолютную дату звонка.
3. [openai-text-processor.ts](../apps/api/src/text-processing/openai-text-processor.ts)
   требует подтверждать проверки разговором и запрещает вычислять новые значения.
   Исключение для application facts разрешает лишь факт внутреннего сохранения текста.
   Поэтому модель видит «следующие две недели» без начала отсчёта и без готовых окон.
4. [text-validation.ts](../apps/api/src/text-processing/text-validation.ts) проверяет
   цитаты и числа по transcript. Известные серверу факты не являются отдельным типом
   источника. Добавление даты в prompt без изменения grounding-контракта недостаточно:
   корректное упоминание `2026-10-01`, которого нет в разговоре, всё ещё отклоняется.
5. Ошибка сохраняется в assessment: `criterion.1=uncertain`, остальные три criteria
   `achieved`, общий `goal=partial`. Последующие языковые summaries могут получить
   `fixedAssessment` и обязаны повторить его. Текущее сохранение ready assessment
   той же transcript revision также не заменяет старое решение новой версией evaluator.

Artifact сгенерирован одним успешным `call_summary.0` запросом к `gpt-5.6`, начатым
в 10:10:22.946 и занявшим 23 064 мс. Следовательно, **эта ошибочная послезвонковая
оценка не могла вызвать end_call в 10:10:18**. Это два отдельных дефекта. Мотив
реального `cannot_proceed` по-прежнему неизвестен; нельзя подменять его текстом summary.

Исправление: передавать доверенный контекст исходной попытки и утверждённые windows;
семантическое извлечение даты/подтверждения оставить существующему summary-запросу;
сравнение конкретного слота с windows выполнять чистой функцией. Календарный verdict,
его формулировка и ссылки на факты должны иметь одного владельца в приложении.
Не добавлять calendar-agent/tool, повторное согласование с получателем или ещё один LLM-вызов.
Не решать проблему глобальным разрешением модели «считать даты самой».

Правильное представление этого случая разделяет три утверждения:

- Получатель словами подтвердил указанную договорённость — reported, с цитатами.
- Суббота 03.10.2026, 11:00 входит в утверждённое окно — вычислено приложением по плану.
- Подтверждённого voice action в журнале нет — независимое ограничение исполнения.

Убирать ложную календарную неопределённость нельзя ценой автоматического объявления
всей записи успешно оформленной. Отдельно оценить цель разговора и execution state.

Проверка дополнения: **7 диагностических/контрольных тестов** на неизменённом коде;
дополнительно **194 теста / 4 suites** по расписанию, допуску appointment, summary workflow
и text processor прошли. Диагностика установила, что изменение windows/compiledAt вообще
не меняет нынешний summary input, сохранённый ошибочный summary проходит валидацию,
а правильный слот детерминированно разрешён. Private evidence и тесты:
`.tools/calendar-summary-audit-20261001.private.json`, одноимённый `.test.ts` и `.config.mjs`.

## Предлагаемый единый контракт

Сохранить естественный Live-диалог, приложение как владельца разрешений и playback,
а backend как интерпретатор смысла. Устранить конкурирующие трактовки результата,
прогресса и готовности положить трубку. Не добавлять ещё один постоянно работающий
контроллер, классификатор каждой обычной реплики или списки слов «да/пока».

### A. Один объект результата и одна транзакция завершения

Ввести immutable `TerminalDecision`: task revision, тип исхода, причина остановки,
references на наблюдения, подтверждённые факты, существенная неопределённость,
состояние защищённого действия и язык. Содержательные факты хранить по действующей
политике шифрования/доступа, не в общих логах. Разделить:

- Получатель сообщил результат.
- Приложение подтвердило предусмотренное действие по своему протоколу.
- Финальная реплика доставлена.
- Телефонное соединение завершено и известен/неизвестен инициатор.

`objective_resolved` требует критериев утверждённого плана. `cannot_proceed` требует
актуального stop condition, исчерпанного ожидания или отсутствующей необходимой
возможности/информации. Временный rejected tool сам по себе не является stop condition.
`recipient_requested_end` сохраняет высший приоритет без требования сначала завершить
appointment protocol. Доказательство stop не должно задерживать исполнение явного отказа.

Семантическое решение backend содержит grounding; приложение проверяет актуальность,
существование references, разрешения и противоречия journal. Эти структурные проверки
не превращают свободный естественный текст в математически доказанный факт.

### B. Финальная реплика с известным началом, содержимым и концом

Рекомендуемый вариант: **одна короткая управляемая финальная реплика** через существующий
application-rendered speech path. Backend формулирует факт результата; composer на языке
разговора добавляет уместное прощание. Для appointment date/time/weekday берутся из
валидированных структур. Одно предложение результата, максимум одно существенное
ограничение, затем прощание; без вопросов, служебных объяснений и обещаний переслать результат.

Последовательность: `decision proposed → validated → terminal audio prepared → released →
matching mark acknowledged → disconnect requested → provider termination observed`.
Ошибки, отмена и неизвестная доставка — отдельные ветви. Одна generation владеет выходом.

При переходе сохранить оставшийся обычный playback отдельно: дать короткой текущей
реплике закончиться в ограниченный срок либо явно отменить устаревшую. Её mark не может
подтвердить финальную реплику. При получательском stop — немедленно прекратить задачу.
Native output во время terminal ownership не передавать и не возобновлять в промежутках
между render/playback/отменой. Весь terminal audio подготовлен до release; mark отправляется
после последнего известного фрейма. Повторный/старый/cleared mark не завершает вызов.

Это использует уже существующий TTS-механизм. Для него отдельно проверить тембр/темп обеих
продуктовых voice settings: одинаковый voice identifier не гарантирует акустическую
неразличимость Live и Speech API. Generated terminal audio и его доставка должны правильно
попасть в финальную расшифровку; до появления надёжного смешанного transcript source сохранять
существующий recording-ASR fallback для application-rendered output.

Альтернатива с исключительно native финалом требует проверки смысла и свежести именно
финальной речи плюс bounded fallback. Одно увеличение quiet timeout или ACK instructions
проблему не решает: у native audio нет utterance ID, временных меток и audio-done.
Поэтому этот вариант сложнее в доказательстве границ и не является рекомендацией по умолчанию.

### C. Семантика прерываний и прекращения связи

Энергия входа сразу приостанавливает воспроизведение, но не переписывает исход задачи.
Полный смысл ответа решает продолжение: вежливое ответное прощание сохраняет terminal
decision; существенная поправка отменяет его и возвращает к задаче; новый запрос проходит
проверку исходных полномочий. Не перезапускать всю беседу и не повторять полный итог после
каждого «спасибо». При возобновлении произносить только необходимую недосказанную часть.

При «прекратите/не звоните» не навязывать резюме: краткое подтверждение/прощание только
если уместно. Отзыв согласия на запись должен остановить запись по политике и исключить
продолжение задачи, требующей записи. Recipient disconnect/stop callback отменяет pending
render, tools, timers и retry; поздний mark ничего не меняет. При отсутствии доказательства
причины разрыва показывать unknown/transport, не приписывать действие получателю.

Сохранить абсолютный максимум closing (сейчас 30 секунд); уточнить измеримые рабочие
цели: начало финала до 3 секунд p95 после решения и отключение до 1 секунды после actual mark
на здоровом канале. Это **критерии будущей приёмки**, не текущие измеренные гарантии.
При сбое один ограниченный запасной вариант без выдуманного результата. Если говорить
невозможно, техническое завершение с честным incomplete closing, без ложного playback_complete.

### D. Согласовать действие и речь во всех фазах appointment

Развести availability/proposal, validated request, delivered request, recipient confirmation
и reported existing appointment. `unconfirmed_details` должен возвращать структурированное
missing detail/следующий допустимый шаг. Получение нового факта снимает именно этот пробел.
Если получатель уже сообщил запись, использовать status check той же договорённости,
а не повторный booking. Проверить один action, точные date/time/zone, одну запись,
отсутствие новых финансовых обязательств и последующее contextual confirmation.

До accepted action запрещены заявления о выполнении. Для реплик, выполняющих обязательство
или подтверждающих его, использовать application-owned output и факты journal; после
rejected tool не выпускать pending commitment speech. Обычные уточнения оставить Live.
Нельзя обещать нулевой риск любого неверного утверждения в свободной native речи только
за счёт prompt: если нужна строгая предварительная проверка такой речи, потребуется
buffering/validation и отдельная оценка добавленной задержки. Проверять это явно в acceptance.

### E. Один scheduler и корректное понятие прогресса

В [live-conversation.ts](../apps/api/src/voice/live-conversation.ts) собирать message/tool
items по response/delegation, учитывать финальный текст из item events и не требовать
его повторного присутствия в lifecycle event. Tool-free полезный ответ — прогресс.

Разделить semantic turn revision, физический provider run, action revision и output generation.
Фрагмент transcript не равен завершённому ответу. Новое содержательное input делает старый
effect неактуальным, но не освобождает provider slot. Не отправлять новый application request,
пока неопределённый старый run физически не завершён либо сессия контролируемо прекращена.
Не использовать неподдерживаемый cancel event и не считать локальный timeout его заменой.
Нативные делегации наблюдать и учитывать; абсолютную сериализацию инициируемых провайдером
работ нельзя гарантировать только локальной очередью.

Recovery запускать один раз на актуальное смысловое состояние, только при отсутствии
наблюдаемого полезного прогресса. Continuation имеет приоритет над новым recovery.
Тишина, filler, ACK и пустой append не обновляют semantic progress. При новом ответе
сбросить deadline старого ожидания и его expired-флаг; отдельно ограничить hold/transfer,
provider wait и время всей беседы. Background noise не продлевает их бесконечно.

### F. Явная телеметрия и понятный результат пользователю

Сохранять decision ID/revision, основание outcome, summary hash, output generation,
release/clear/mark, closing delivery state, disconnect request и observed transport end.
В чувствительном encrypted artifact хранить terminal result и references, чтобы следующая
диагностика могла объяснить выбор cannot_proceed. Без raw audio/текста до consent.

В карточке звонка различать «завершил ассистент», «остановил пользователь»,
«связь завершилась, инициатор неизвестен», результат задачи и доставку заключения.
`endedBy=assistant` уже существует в lifecycle projection; переиспользовать его,
добавив независимый статус closing. Provider completed не заменяет ни один из этих фактов.

## Матрица приёмки по политике приложения

Это классы состояний и событий для всех пяти разрешённых task types, а не попытка
перечислить бесконечное множество формулировок. `unsupported` не допускается к исполнению.

| Класс | Основание результата / поведение завершения |
| --- | --- |
| Информация | Получен ответ; либо честно неизвестно/частично. Коротко передать факт, попрощаться |
| Подтверждение получения | Получено / не получено / не установлено; отрицательный ответ может завершить информационную цель |
| Требования к документам | Зафиксировать необходимые документы и существенные условия; не обещать собственную отправку |
| Нейтральное сообщение человеку | Доставленное сообщение; не приписывать согласие или действие адресату |
| Appointment book / confirm_existing | Точная разрешённая договорённость и journal state; reported/uncertain не превращаются в confirmed |
| Нет времени / неизвестно / частичный результат | Один необходимый уточняющий шаг, если уместно, иначе фактический partial/unresolved итог |
| Отказ / wrong recipient / policy stop | Прекратить действие; не расширять адресата, дату, услугу или финансовые полномочия |
| Получатель хочет завершить | Уважить сразу, не ждать «успеха» и не навязывать полный итог |
| Hold / transfer / пауза | Не считать концом; отдельное ограниченное ожидание, проверка полномочий нового собеседника |
| Поправка во время backend / финала | Отменить устаревший effect/output, рассмотреть полный ответ, не повторять действие |
| Взаимное goodbye / короткий шум | Остановить мешающий звук; сохранить решение о завершении, без бесконечного повторения |
| Автоответчик / fax / busy / no-answer | Существующая AMD-policy; тишина либо одно утверждённое neutral message после beep; не human summary |
| Нет consent / recording failed / отозванное consent | Нет task continuation; предусмотренное краткое завершение, без сохранения запрещённой речи |
| Caller/recipient disconnect в любой фазе | Отменить работу и не пытаться озвучить/повторить финал после разрыва |
| Provider error / потерянный ACK / reconnect / process restart | Консервативная доставка, durable termination recovery, никакого автоматического повторного booking |

Матрица пересекается с языками de-CH/fr-CH/it-CH/en-GB, ru-RU для superadmin,
историческими de-DE/en-US, обоими голосами, тремя assistance reason, разрешённым
fallback language, обычной и фоновой AMD, всеми action/delivery states.
Проверки включают фрагментированные ответы, отрицание после «да», условное согласие,
цитируемое прощание, поздние/дублированные события, пустые аудиопакеты и задержки сети.
Необходимые имена, номера, адреса, weekday/date произносить корректно; не добавлять
ритуальный «всё верно?» после уже достаточного подтверждения без причины.

## Порядок внедрения и критерии выхода

Файлы, новые типы, совместимость и точный порядок сведены в отдельный
[подробный план имплементации](live-stabilization-implementation-plan-2026-10-01.md).
Он включает post-call calendar facts; описание ниже остаётся обзором runtime-части.

1. **Закрепить дефекты тестами желаемого поведения.** Текущие diagnostic reproductions
   специально утверждают ошибочное поведение и не должны попасть в acceptance как «зелёные».
   Использовать synthetic данные, реальные формы provider events и virtual clock.
2. **Исправить terminal ownership и outcome validation вместе.** Один TerminalDecision,
   содержательная финальная реплика, exact playback receipt, interruption/remote-stop.
   Не выпускать только prompt-правку или увеличенный quiet timer как исправление.
3. **Исправить action/scheduler контракты.** Streamed message items, waiting reset,
   useful-progress clock, physical run occupancy, rejected action recovery, единые prompts.
4. **Прогнать инварианты и fault injection.** Ни одного hangup по обычной реплике;
   ни одного принятого cleared mark; ни одного повтора side effect; ни одного ложного
   confirmed; старый timeout не закрывает свежую работу. Между дозволенным выходом и
   actual mark должен оставаться один владелец; interruption проверяется на каждом переходе.
5. **Проверить настоящие provider и handset сценарии.** Сначала текст/протокол, затем
   контролируемые звонки с согласным получателем, прослушивание двух каналов и сопоставление
   концовки с событиями. Минимум все task types, оба голоса, RU/DE и языковая матрица,
   partial/refusal/hold/correction/reciprocal goodbye/recipient-first hangup и технические ошибки.
   Сохранить распределения задержки, количество повторов и долю неполных завершений;
   единичный удачный звонок не устанавливает универсальную надёжность.
6. **Активировать кандидата после проверки отсутствия активных вызовов.** Новый runtime tag,
   manifest и возможность отката, затем ограниченная наблюдаемая эксплуатация. Не менять
   исторические transcript, согласования и assessments задним числом.

## Проверки этого разбора

На неизменённых production sources прошли **7 воспроизведений дефектов и 1 положительный
контроль**. Отдельно прошли существующие **188 тестов / 2 suites**:
`unified-live-call.test.ts`, `live-closing-speech.test.ts`. Их успех одновременно с
диагностикой показывает пробел в контракте тестирования, а не отсутствие проблемы.

Первый запуск существующих suites из корня захватил семь архивных копий в `.tools`
и получил import errors; повтор из `apps/api` выполнил ровно нужные две suites и прошёл.
Первоначальная гипотеза о начальном silence timer была отклонена и превращена в контроль.
Полный repository suite не запускался: runtime code не менялся.

Приватные материалы, не для публикации: `.tools/latest-v4-call-20261001.private.json`,
review/inspect scripts, `.tools/v4-audit-20261001-cases.txt`, builder и config.
Воспроизведения используют fake sockets, synthetic audio и in-memory repository;
реальные исходящие звонки и provider inference не выполнялись. База читалась в read-only
режиме; активный API/web, конфигурация и исторические результаты не изменены.

Проверенные первичные источники OpenAI Docs:

- [Delegation and tools](https://developers.openai.com/api/docs/guides/live-delegation):
  backend и речь независимы; tool results предшествуют continuation; lifecycle output
  не заменяет поток item events; append не отменяет текущую работу.
- [Managing sessions](https://developers.openai.com/api/docs/guides/live-conversations):
  transcript deltas — фрагменты, а не завершённые turns; timing приблизителен;
  WebSocket audio не имеет timing fields или audio-done.

Эти источники объясняют границы протокола. Причина конкретного завершения установлена
по application evidence и воспроизведению, а не по документации провайдера.
