# Аудит инструкций Live: основание для минимального плана

Дата: 28 сентября 2026. Проверен текущий локальный исходный код, включая незакоммиченные изменения. Это аудит, а не реализация или подтверждение production-состояния.

Последующий документ: [подробный план реализации](live-simplification-implementation-plan-2026-09-28.md). Он фиксирует выбранный объём и уточняет открытые варианты этого аудита.

Цель: стабилизировать существующий продукт, передав Live разговорное поведение. Область будущего плана — завершение, достоверность реплик, вступление. Новые продуктовые оценки, панели мониторинга и отдельный проект телеметрии исключены.

«Понял», «фиксирую», «записал», «принял информацию» допустимы как естественное подтверждение услышанного. Они не должны автоматически трактоваться как заявление об успешной внешней операции. «Отправил письмо», «передам в отдел», «вам перезвонят» требуют основания: конкретного исполнителя, полномочия и доступного действия; для заявления о выполнении — подтверждённого результата.

## Уточнения пользователя после аудита

Эти решения уточняют направления ниже; описание найденного исходного кода остаётся историческим основанием аудита. Изменения приложения пока не реализованы.

### Обработка результата

Убрать выбор `resultHandling` из формы для всех ролей. Сохранение разговора и результата в приложении — постоянное поведение продукта, а не пользовательская настройка. Соответственно, вместо предложения передавать этот выбор обеим моделям дать им короткое постоянное описание реальных возможностей приложения.

Связанный отдельный ввод `deliveryInstruction` также не нужен в новой форме: пользователь описывает запрос внешней передачи в самой задаче, например «попросить прислать документ на указанный email». Это остаётся содержанием поручения, с указанием исполнителя и адресата; не превращается в возможность ассистента самостоятельно отправлять письма. Компилятор должен уточнять существенные недостающие детали по смыслу поручения, без зависимости от выбранного режима. Аналогично передача сообщения определяется самой задачей.

Для минимального изменения существующие поля старых сохранённых планов можно сохранить для чтения и совместимости. Не требуется массовая миграция истории. При редактировании/повторе старого плана нельзя молча потерять содержимое `deliveryInstruction`: существенные инструкции должны попасть в видимую задачу/контекст и новый план для проверки.

### Тон и обращение

Показывать настройки только при `userRole === "superadmin"`. Начальные значения для всех новых планов, включая суперадмина: `tonePreference = neutral`, `addressingMode = formal`. Суперадмин может явно изменить их; для остальных ролей действуют эти фиксированные значения. Формальность выражается естественно для языка звонка: русское «вы» — пример, а не буквальная инструкция для всех языков.

Использовать уже существующую роль пользователя; отдельная система разрешений не нужна. Нормализовать новые запросы при подготовке плана на сервере и в форме, включая восстановленные черновики и повтор звонка. Иначе скрытые старые значения `auto`/`informal` продолжат влиять на план. Сохранённые утверждённые snapshots задним числом не переписывать.

### Вопрос об удобстве

Сохранить как разговорное правило. Предлагаемая инструкция для Live:

> После согласия на запись и подтверждённого запуска записи кратко объясни цель, не повторяя представление. Спроси, удобно ли сейчас поговорить, и дождись ответа. Если собеседник уже явно предложил продолжать или сразу отвечает по цели звонка, продолжай без повторного вопроса. Если ему неудобно, уважительно заверши разговор. Выбирай естественную формулировку на языке звонка и соблюдай установленное обращение.

Согласие на запись само по себе не заменяет готовность обсуждать задачу. Решение, получен ли уже ответ на вопрос об удобстве, оставить Live. Отдельный инструмент, классификатор, список фраз и проверка дословного совпадения для этого не нужны. Технический допуск к работе по задаче остаётся связан с согласием и успешным запуском записи; разговорный переход после вопроса готовности ведёт Live.

В будущем плане согласовать compiler, schema и runtime так, чтобы сгенерированный `readinessQuestion` не оставался вторым обязательным источником дословного текста. Для новых звонков важен смысл правила; старые планы сохраняются читаемыми.

Проверены развилка legacy/runtime, связанные исторические отчёты, post-call путь и релевантные тесты.

Время звонка: 15:40:30–15:41:58 Europe/Zurich. Аудио независимо не прослушивалось. Нет оснований оценивать здесь фактический тембр или акустическую естественность.

Открыты актуальные официальные страницы OpenAI:

- [Prompting GPT-Live](https://developers.openai.com/api/docs/guides/live-prompting): короткие разговорные инструкции, обычные формулировки выбирает Live; естественные подтверждения допустимы во время backend-работы. Результат зависимого действия нельзя угадывать.
- [Delegation and tools](https://developers.openai.com/api/docs/guides/live-delegation): Responses delegation подходит для managed backend; правила действий и инструменты принадлежат backend, приложение проверяет полномочия. Обычный цикл функции — вернуть результаты и продолжить backend через `response.create`. События instructions, thinking и commentary имеют разные назначения; лимит одного append — 500 токенов.
- [Managing sessions](https://developers.openai.com/api/docs/guides/live-conversations): добавление инструкции может прерывать текущую речь; подтверждение append не означает проигранное аудио. Дословная обязательная реплика требует проверки доставки. Закрытие сессии и завершение речи — разные события.
- [WebSockets](https://developers.openai.com/api/docs/guides/voice-websockets?api=live): у Live нет события окончания отдельной голосовой реплики; воспроизведение отслеживает приложение.
- [Migrate to GPT-Live](https://developers.openai.com/api/docs/guides/live-migration): убрать ручное управление голосовыми ходами, сохранить реальные границы полномочий; отделять изменение задачи от прерывания речи.

Эти рекомендации не предписывают наш классификатор прощания. Они также не дают готового события, которым можно безопасно заменить весь контроль проигрывания.

## 1. Завершение: подтверждённая проблема и граница упрощения

### Подтверждённая цепочка

В 15:41:27 принят `end_call`, разрешающий завершение. После этого Live произнёс «Прекрасно, информация уже у меня, и я передам дальше. Спасибо, всего доброго!». Проверка завершения заняла около 4,7 секунды и вернула `different`. В 15:41:57 сработал `LIVE_CLOSING_DEADLINE`. Запись показывает около 23 секунд от конца прощания до отключения.

`LiveClosingSpeech` отправляет playback mark только после `equivalent`. Для `different`, `incomplete` и `unclear` активного выхода нет: без нового вывода система ждёт общий 30-секундный дедлайн. Это поведение закреплено тестом `silence cannot authorize hangup after %s`.

Следовательно, проблема не в неработающем API-классификаторе: запрос успешно завершился, но его отрицательный результат загнал разговор в ожидание.

### Конфликт назначения проверки

Closing policy запрещает считать завершением реплику, объявляющую дальнейшую работу. Формулировка не различает работу после звонка и обещание продолжить говорить сейчас. «Передам дальше» могло вызвать `different`, однако объяснение решения не сохранено — конкретный триггер остаётся гипотезой.

Проверке передают только причину завершения и текст прощания. Полномочий, результата действия и плана в ней нет. Поэтому она не может достоверно решать, допустимо ли обещание. К тому же речь уже передана в телефон: проверка не предотвращает произнесённую фантазию, а только задерживает отключение.

### Другие активные усложнения

После принятого `end_call` код отправляет `function_call_output`, но специально пропускает `response.create`; дальнейшее поведение вызывает отдельная `session.instructions.append`. Это отступление от обычного документированного function-result цикла. Причина в комментарии — избегать второго ответа. Его влияние на последний сбой не доказано, но при планировании надо устранить конкуренцию двух источников указаний, а не добавлять третий.

Прощание отменяется и при начале звуковой активности, и при любом непустом входном native-фрагменте. Приложение не различает благодарность, поправку и речь в сторону. Это шире разговорной interruption policy. Для последнего звонка отмена не зарегистрирована, поэтому это риск по коду, а не установленная причина конкретного таймаута.

### Направление плана

Один владелец разговорного решения — Live с managed backend. Приложению оставить физическое завершение и доставку последнего аудио. Не превращать проверку конца речи в повторную оценку всей задачи или обещаний. Устранить тупик отрицательного решения без цепочки повторных классификаторов.

Удаление `LiveClosingSpeech` нельзя объявить готовым решением только потому, что мы хотим меньше кода: native speech-done отсутствует. На этапе подробного плана нужно выбрать один способ окончания. Минимальная правка существующего пути — сузить проверку до завершённости речи и определить ограниченный выход при отказе. Более радикальная замена допустима только с понятной границей последнего аудио, без обрыва реплики по первой паузе. Новую систему управления диалогом не строить.

## 2. Достоверность: исправить знания и правила, сохранив естественную речь

### Потеря данных между планом и моделями

В утверждённом плане последнего звонка есть `resultHandling: capture_in_callassist`. Но `executionData()` не включает `resultHandling`, поэтому этот режим отсутствует в Responses backend. В кратком контексте `configureBackend()` его тоже нет.

Более того, Live получает только получателя, инициатора, цель, тексты вопросов и факты. Он не получает `backgroundSummary`, условные follow-ups, признаки обязательности вопросов, критерии успеха/неразрешённости, условия остановки, запреты и конкретные пределы appointment authorization. Часть этого есть у backend, но обычную речь Live формирует без обращения к нему. Политика хранения аудио также не передаётся в этот контекст.

Недостаток данных подтверждён кодом. Утверждать, что именно он единолично породил конкретную фразу, нельзя. Но инструкция «следуй утверждённому плану» не заменяет передачу существенных частей этого плана.

### Нет ясного различия между подтверждением и обещанием

В Live-инструкции есть запрет выдумывать уже достигнутый успех. Он недостаточно явно покрывает будущие обещания. «Я передам дальше» не заявляет, что отправка уже состоялась, и легко проходит такую формулировку.

Одновременно два места — основной prompt и инструкция включения task stage — требуют делегировать завершение ДО любого подтверждения ответа. Это смешивает «услышал ответ» и «выполнил действие». Рекомендация документации ждать backend касается зависимых результатов; она допускает обычное acknowledgment во время работы.

Нужное общее правило:

> Подтверждай услышанное естественно. О следующих действиях говори только в пределах утверждённой задачи и реальных возможностей. Различай то, что делаешь ты, обещание собеседника и действие приложения. Выполненное внешнее действие подтверждай только по результату. Если дальнейшего действия нет, не придумывай его ради вежливого завершения.

Это смысловое правило для всех сценариев и языков, а не blacklist русских фраз. «Записал» как acknowledgment допустимо; «записал вас на приём» — уже утверждение о конкретном действии.

### Значение существующих режимов

| Режим | Что должен понимать Live |
| --- | --- |
| `capture_in_callassist` | Ответ фиксируется в приложении. Это не поручение отправить его кому-то, связаться с отделом или организовать обратный звонок |
| `request_external_delivery` | Есть задача запросить указанную передачу. Нужно сохранить исполнителя и условия из плана; просьба к собеседнику отправить документ не означает, что ассистент сам имеет почтовый инструмент |
| `message_only` | Передать утверждённое сообщение текущему получателю. Не добавлять последующую рассылку или ответный контакт |

В live toolset нет универсальных инструментов email, заказа, уведомления отдела или обратного звонка. Нам не требуется добавлять их ради исправления обещаний.

### Другие поправки к промптам

`managedBackendInstructions` безусловно описывает получателя как поставщика услуги. Это неверно для родственника, коллеги и личной встречи. Общая роль — вызываемый получатель; специализированные правила должны применяться только в соответствующей задаче.

В `action_speech` policy остались инструкции для `speak` и `confirm_appointment`, хотя текущий вызов классификации передаёт только `request_appointment`. Это кандидат на точечную очистку; не причина фразы в последнем звонке. Неиспользуемый метод `commentary()` сам по себе на разговор не влияет.

Дробление контекста по 400 символов технически ограничивает размер append, но режет JSON посреди полей. При обновлении передачи плана лучше отправлять компактные самодостаточные части. Не нужен новый summarizer или модельный запрос для подготовки каждой реплики.

### Направление плана

Исправить проекцию уже существующего утверждённого плана; дать Live существенные разговорные ограничения и возможности, backend — полные правила действий. Согласовать правила в основном prompt, task-stage append, backend и end_call-описании. Разрешить acknowledgment. Убрать необоснованные будущие обещания одним общим правилом. Не добавлять проверку каждой фразы, словарь запрещённых слов или классификатор обещаний.

## 3. Вступление: убрать конфликт источников

### Повтор задан приложением

В `twilio-copy.ts` disclosure уже представляет ассистента от имени инициатора. Затем compiler prompt требует, чтобы `purposeStatement` снова содержал представление от его имени. После согласия `#grant()` склеивает три opening-поля и через `#say()` требует дословного произнесения.

Указание компилятора «один раз» относится только к трём полям opening, а не ко всему звонку. Поэтому формально оба генератора выполняют свои инструкции, но человек слышит повтор.

Требование отдельного вопроса готовности закреплено и в prompt, и в схеме обязательного `readinessQuestion`. Самой фразы «не повторяйся» в Live недостаточно: она конкурирует с приложением, которое требует прочитать весь opening точно.

### Унаследованная модель поведения

Дословный opening соответствует поведению `buildInitialResponseInstructions` в Realtime. Сам Realtime-промпт не вызывается в native Live-пути, но структура плана и модель «сначала отдельный обязательный ход, потом разрешить разговор» перенесены в новую реализацию.

Для disclosure согласия эта граница нужна продукту. Для всей обычной вступительной реплики столь же жёсткая проверка не обязательно нужна. Это разные виды речи, хотя сейчас обслуживаются одним механизмом.

Один append ограничен документацией 500 токенами, а schema допускает opening до 1 240 символов плюс assistance disclosure и служебную обёртку. Код не ограничивает полный `#say` по токенам. Превышение в последнем звонке не произошло; это отдельный риск для длинных многоязычных вступлений. Предпочтительно сократить и упростить вступление, а не создавать сложный потоковый скрипт.

### Направление плана

Сохранить ясное представление ИИ и явное согласие на запись/транскрипцию. После согласия дать Live кратко обозначить цель с учётом уже произнесённого и перейти к задаче. Готовность продолжать учитывать естественно: прямой ответ по цели не должен запускать ещё один формальный опрос готовности.

Пересмотреть вместе compiler opening, runtime-инструкцию и использование обязательного `readinessQuestion`. Не исправлять это через вырезание имён регулярными выражениями и не переписывать исторические утверждённые планы молча. Выбор совместимости старых планов относится к подробному плану изменения, а не к новому слою runtime-проверок.

## Что уже устроено правильно

Native путь использует одну Live-сессию и Responses delegation. Обычные реплики проходят без отдельного классификатора. Входной PCMU передаётся непрерывно. Backend-инструкции отделены от Live-инструкций. Факты передаются через thinking, управляющие указания — через instructions. Функции собираются из вложенных completed output items, а не только из пустого terminal output. Native transcripts и факт воспроизведения не приравниваются к завершению backend.

Сохраняются реальные границы продукта: согласие и запуск записи, утверждённые полномочия на встречу, защита от повторного действия и проверка последующего подтверждения собеседника. Их удаление не следует из пожелания упростить разговорную логику.

Старый per-turn LiveTaskController и отдельный consent-классификатор не участвуют в текущем native runtime. Legacy-ветку не надо переписывать или удалять ради этих трёх проблем. Post-call summary уже различает внутреннее сохранение и внешнюю передачу; его инструкции не возвращаются в Live и не объясняют фантазию.

## Основание для следующего подробного плана

Ровно три рабочих пункта:

1. Надёжное завершение без тупика дополнительного одобрения и без конкурирующих команд модели.
2. Полный необходимый контекст и единое правило достоверности, допускающее естественные подтверждения.
3. Краткое вступление без повторного представления; вопрос об удобстве как инструкция Live с естественной формулировкой и учётом уже полученного ответа.

Наиболее дешёвое содержательное исправление — пункт 2; явный технический дефект — пункт 1. Пункт 3 требует согласовать компилятор и runtime, поэтому его не следует маскировать одной строкой промпта.

Для проверки использовать существующие тесты и небольшой набор повторяемых разговоров: сбор информации; передача сообщения; запрос внешней отправки у получателя; согласование встречи; отказ/неизвестный ответ; благодарность во время прощания; существенная поправка во время прощания. Проверить основные языки, включая русский и немецкий. Критерии — корректное действие и речь без выдуманного продолжения, отсутствие обрыва/длинного зависания, отсутствие повторного представления. Не требуется новая платформа оценивания.
