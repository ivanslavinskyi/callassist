## Поведение приложения

- После подтверждения телефона или входа с неподтверждённым email открывается
  `/en/verify-email` либо `/de/verify-email`. Отправка — явным действием пользователя.
  В кабинете видны статус адреса и ссылка на подтверждение.
- На экране SMS можно исправить опечатку телефона до завершения регистрации:
  нужны email и пароль регистрации, затем OTP нового номера. Уже подтверждённый
  номер этим способом изменить нельзя. Проверка телефона атомарно сверяет номер,
  для которого проверялся код, и допускает только одно завершение: ответ провайдера,
  пришедший после смены номера, не подтверждает новую цель.
- Первичная проверка email: шестизначный код, 10 минут, повторная отправка через
  60 секунд. Новый запрос заменяет прежний код. Неверный код не разлогинивает пользователя.
  Адрес с опечаткой исправляется через текущий пароль и код на новый адрес.
- Проверка привязана к пользователю, адресу, назначению (`verify`/`change`) и точной
  сессии. HMAC кода хранится вместо открытого OTP; общие IP/user/address/ID limits
  дополняют восемь попыток в durable challenge. Завершение атомарно устанавливает
  `emailVerifiedAt`, отзывает другие сессии и незавершённые recovery capabilities.
- HTTP start и approve-and-start требуют подтверждённый email после проверки
  принадлежности звонка. Подготовка, история, остановка, настройки, экспорт и удаление
  остаются доступны. Это правило API; доверенный внутренний `CallService` сам по себе
  не является границей авторизации.
- Подтверждение/смена email получают HTML и plain-text письма. После смены email,
  телефона или восстановления пароля отправляется уведомление безопасности.
  Уведомления о данных аккаунта идут только на доказанно принадлежащие пользователю
  адреса; неподтверждённый старый адрес их не получает.
- Ошибка отправки OTP инвалидирует challenge и возвращает контролируемую ошибку.
  Ошибка вспомогательного уведомления не превращает уже завершённую смену контакта
  или пароля в ложный ответ об отказе операции.

### Оформление писем после пользовательской приёмки 14.09

- Вместо текстовой надписи используется существующий логотип сайта, экспортированный
  в PNG (9 453 байта, 3×). Он вложен в письмо с Content-ID и включён в API bundle,

  SVG: `node scripts/build-email-logo.mjs`.
- Общая табличная вёрстка с inline-отступами заменяет `<main>`; фон прозрачный,
  отдельной цветной подложки/карточки нет. Код остаётся текстом, у логотипа есть alt.
- По явному пожеланию владельца футер содержит только две ссылки — Impressum и
  Support (`mailto:support@shprohli.ch`). Имени, адреса оператора и privacy-ссылки нет.
  Reply-To также направляет ответы в поддержку; доступность поддержки остаётся B12.
- Футер и plain text покрывают EN/DE/FR/IT/UK/RU; RM сохраняет EN fallback.
  Для ещё не опубликованных языков ссылка Impressum ведёт на EN с явной языковой
  пометкой. EN/DE используют свои опубликованные пути.
- Origin ссылки берётся из `NEXT_PUBLIC_SITE_URL`, которую нужно передавать API
  наряду с web. В production обязательна публичная HTTPS-origin без credentials,
  query или path. На локалке ссылка localhost открывается только на машине с
  приложением; Twilio-only tunnel не публикует страницы сайта.
- Проверено: 18 provider/template tests, API typecheck/build, copy check; в браузере
  просмотрены EN/DE/RU при ширине 320 px. Это проверка HTML-предпросмотра, а не
  повторная приёмка нового оформления в Gmail/Outlook или в тёмном режиме.
  После обновления нужен новый пользовательский email; агент письма не отправлял.
  [Resend CID images](https://resend.com/docs/dashboard/emails/embed-inline-images).

## Языки

Язык UI, язык разговора и язык доставки независимы. SMS получает явную локаль UI
из запроса, иначе используется сохранённое предпочтение аккаунта; код страны номера
не выбирает язык. Для публичного opt-out используется локаль страницы.
Реестр — `apps/api/src/auth/communication-locales.ts`, типизированные письма —
`email-templates.ts`. Тест проверяет покрытие всех включённых UI-языков.

| Язык | UI сейчас | Email | Twilio SMS |
| --- | --- | --- | --- |
| EN | включён | EN | EN |
| DE | включён | DE | DE |
| FR | планируется | FR, кандидат на вычитку | FR |
| IT | планируется | IT, кандидат на вычитку | IT |
| UK | планируется | UK, кандидат на вычитку | UK |
| RU | планируется | RU, кандидат на вычитку | RU |
| RM | планируется | явный fallback EN | явный fallback EN |

Новые языки интерфейса этим изменением не включаются. Перед включением каждого
нужны UI-словарь, вычитка всех писем/ошибок, обновление статуса в реестре и delivery drill.
Для RM нужны вычитанные письма и настройка custom SMS template: Romansh есть у Twilio
среди custom-языков, но не среди default SMS. Поэтому автоматический `rm` в текущий
Verify Service не передаётся. [Twilio supported languages](https://www.twilio.com/docs/verify/supported-languages).

## Доставка и ограничения

Resend: таймаут 5 секунд на попытку, максимум две попытки с одним телом и одним
idempotency key; сетевые ошибки и короткие transient отказы допускают повтор.
Постоянные ошибки и долгий Retry-After не повторяются внутри запроса.
Провайдер сохраняет idempotency keys 24 часа.
[Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys),
[rate limits](https://resend.com/docs/api-reference/rate-limit).

Twilio: таймаут 8 секунд, без автоматического повтора отправки после неопределённого
результата. Один бюджет для signup/resend/recovery/phone change/opt-out:
одна отправка на номер в минуту, три в час, по умолчанию 10 в минуту и 100 в сутки
на приложение. Перед обращением к провайдеру резервируется shared PostgreSQL budget;
отказ/таймаут его не возвращает. Страны SMS отдельно от стран исходящих звонков:
`SMS_ALLOWED_COUNTRIES=CH,UA` (Украина добавлена по запросу владельца 14.09).
Это число отправок, а не финансовый потолок Twilio.
Geo Permissions, Fraud Guard и бюджетные alerts провайдера требуют отдельной приёмки.

Логи `transactional_email` содержат безопасный message ID, purpose, locale,
attempt, accepted/failed и Resend ID; `sms_verification_accepted` — локаль/fallback и
Verify ID. Адрес, номер, OTP, ключи, тело сообщения и сырой ответ провайдера не пишутся.
**Accepted означает принятие провайдером, а не доставку адресату.** Оператор должен
иметь доступ к поиску по ID в Resend/Twilio и наблюдению bounce/outage.
Durable outbox, очередь повторных уведомлений после перезапуска и webhook inbox
этим изменением не добавлены. Уведомление безопасности после commit может потеряться
при падении процесса или окончательном отказе; это явная граница текущего минимума.

все три выданные SPF/DKIM записи verified. Twilio GET также вернул HTTP 200:
Verify Service совпадает с `.env`, имя SHPROHLI, шесть цифр, do-not-share включён,
custom codes выключены. Проверка не подтверждает фактический SMS From или доставку.
После изменения `.env` нужен перезапуск API; локальный API уже перезапущен с актуальной
конфигурацией и новыми шаблонами, readiness БД прошёл.
Ключи не помещаются в чат, Git или этот отчёт.

Для новой среды Resend: добавить именно `shprohli.ch`, внести выданные Resend
SPF/DKIM DNS records и дождаться Verified; создать отдельный API key с правом
отправки для этого домена. Локально domain/key уже приняты read-only проверкой.
Не заменять существующие MX корневого домена записями
входящей почты Resend: для исходящих писем нужен раздел Enable Sending.
После проверки домена отдельная регистрация адреса `mail@shprohli.ch` в Resend
не нужна. [Resend domains](https://resend.com/docs/dashboard/domains/introduction),
[адрес отправителя](https://resend.com/docs/knowledge-base/how-do-i-create-an-email-address-or-sender-in-resend).

В текущем локальном `.env` уже заполнено и включено:

```dotenv
RESEND_API_KEY=<API key из Resend>
EMAIL_DRIVER=resend
```

Также заполнены `EMAIL_FROM`, `EMAIL_VERIFICATION_HASH_KEY`, `VERIFICATION_DRIVER`,
Twilio credentials/Verify SID и три SMS policy variables. Существующий
`TWILIO_VERIFY_SERVICE_SID` имеет префикс VA; MG со скриншота сюда подставлять нельзя.
Настройка sender в Twilio не заменяется переменной `SMS_FROM` — текущий Verify API
не использует такую переменную.
Повторных определений этих переменных и переопределений из shell не обнаружено;
email HMAC key — независимые 32 байта. SMS policy: CH/UA, 100 отправок в сутки,
10 в минуту на приложение. `communications:check` теперь возвращает `configured: true`
и код 0. `deliveryVerified: false` — постоянная граница самого CLI: он не делает
реальных отправок и не определяет доставку. Подтверждённые пользователем EN email
и CH SMS записаны ниже отдельно; после этих проверок CLI всё равно выводит false.

Реальные отправка/проверка кодов доступны с localhost: API делает исходящие HTTPS
запросы к Resend/Twilio, пользователь вводит полученный код в локальной форме.
Туннель для этого не нужен. Публичный callback URL понадобится для будущего приёма
вебхуков; текущая минимальная диагностика доставки находится в кабинетах провайдеров.

`corepack pnpm communications:check` проверяет конфигурацию без запросов к БД,
провайдерам и без отправки сообщений. Он выводит только наличие ключей, режимы и
языковую матрицу; код выхода 1 означает, что конфигурация для реальной доставки
не собрана. Код выхода 0 не подтверждает доставку, DNS, баланс, доступность БД или
полную production-конфигурацию. Production startup дополнительно запрещает mock и
проверяет независимость ключей/остальные runtime requirements.

Миграция **0069_email_verification.sql** применена к основной локальной БД и проверена
на свежих тестовых БД. Перед выкладкой её нужно применить на staging/production
обычным migration runner, затем обновить API и web. Старые migrations не изменены.
Существующие email **не подтверждаются задним числом**: после миграции статус null,
пользователь подтверждает адрес до следующего старта звонка. Старый код при откате
не обеспечивает новый email gate; такой откат не должен открывать публичный admission.

В локальном `EMAIL_DRIVER=mock` код `000000` (или `MOCK_EMAIL_VERIFICATION_CODE`),
в `VERIFICATION_DRIVER=mock` — `MOCK_VERIFICATION_CODE`. Эти значения не управляют
реальными провайдерами; mock запрещён в production. Автоматизированные проверки
не отправляли реальных сообщений; пользовательские delivery-тесты указаны отдельно.
