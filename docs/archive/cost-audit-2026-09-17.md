**Вывод:** текущий раздел полезен как техническая диагностика, но не даёт достоверного ответа «сколько потрачено за период». Также время разговора и оплаченные минуты различаются из-за округления. Источники: [Call Resource](https://www.twilio.com/docs/voice/api/call-resource), [расхождения Call logs и invoice](https://www.twilio.com/docs/voice/why-doesnt-my-invoice-match-what-i-pull-from-the-call-logs), [Usage Records](https://www.twilio.com/docs/usage/api/usage-record). Usage summary за незавершённый месяц остаётся текущим отчётом провайдера, не окончательным invoice.

## 2. OpenAI: расчёт воспроизведён, полнота не подтверждена

| Компонент | Уникальные usage-записи в компоненте | Расчёт |
|---|---:|---:|

| Перевод | 8 | $0.108658 |
| Итоги звонка | 6 | $0.164439 |
| Realtime: текст | 79 общих ответов | $0.393275 |
| Realtime: аудио | Те же 79 ответов | $0.970004 |
| Realtime: транскрипция | 58 | $0.044484 |
| Транскрипция после звонка | 96 | $0.160739 |

Расчёт из базы через действующий pricing policy в точности воспроизвёл все суммы скриншота. Cached input вычитается из обычного input и оплачивается отдельно; cache write также учитывается отдельно. Reasoning уже входит в output и повторно не начисляется. Realtime text/audio получают разные денежные части — денежного удвоения здесь нет. На текущих записях не обнаружено превышений cached + cache-write над input.

Проверенные стандартные публичные ставки совпадают с кодом: GPT-5.6 Sol — 4 / 0.40 / 5 / 20 долларов за миллион input / cached / cache-write / output; Realtime 2.1 — текст 4 / 0.40 / 24, аудио 32 / 0.40 / 64; realtime-whisper — $0.017/мин; gpt-transcribe — $0.0045/мин; gpt-4o-transcribe — input $2.50, output $10 за миллион. Это проверка опубликованных ставок, не подтверждение индивидуального счёта, режима обслуживания или исторических условий аккаунта. Источник: [OpenAI API Pricing](https://developers.openai.com/api/docs/pricing).

Однако:

1. Первая сохранённая операция OpenAI датирована **5 сентября 12:21 UTC**. При этом база содержит звонки за июль и август. Старого OpenAI usage в этих таблицах нет. Автоматически восстановить его по длительности звонков точно нельзя.
2. Помимо usage, есть **15 неуспешных платных текстовых операций без usage**: 13 `network_error` и 2 HTTP 503. По этим результатам нельзя установить, был ли расход у провайдера, и нельзя приравнивать его к нулю. Ещё 41 успешная moderation-операция и 1 незавершённая moderation-операция не имеют usage; их надо классифицировать отдельно, а не считать «потерянными платными запросами».
3. Скриншот OpenAI показывает **$7.62 за последние 30 дней**, а справа **$6.37 September spend** в виджете Personal. Область правого виджета не подтверждена отдельно. Нельзя автоматически считать $6.37 сентябрьской суммой только выбранного проекта.
4. 436 запросов, 613 232 токена и 153 audio transcriptions на провайдерском экране относятся к своим endpoint-категориям и фильтрам. Наши operation/session/response/chunk counters имеют другую структуру; сравнение один к одному некорректно без дневной разбивки по модели и endpoint.

**Точная причина всей разницы OpenAI в долларах пока не установлена.** Отсутствие исторического usage доказано; размер его вклада, расход операций с оборванным ответом и возможные вызовы из других окружений требуют выгрузки Costs/Usage того же проекта и периода. В окружении нет отдельного OpenAI Admin Key. Проектный ключ не использовался для платных вызовов в ходе аудита.

Для денежной сверки нужен Costs API, а Usage нужен для объяснения объёма: OpenAI отдельно предупреждает, что детальный Usage может не в точности совпадать с Costs. Источник: [Organization Usage / Costs API](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage).

## 3. Подтверждённые дефекты и ограничения по приоритету

### A1 · P1 · Неверное временное основание для сравнения с биллингом

**Факт:** $9.01 за прошлые месяцы включаются по сентябрьской дате импорта. Usage фильтруется по `usage.observed_at`, стоимость — по `costs.observed_at`, число операций — по `started_at`, основная операционная сводка — по `call_briefs.created_at`. Четыре разных множества выглядят одним отчётом.

Код: [SQL usage](C:/Users/slavi/Desktop/www/callassist/apps/api/src/storage/postgres-call-repository.ts:3205), [SQL costs](C:/Users/slavi/Desktop/www/callassist/apps/api/src/storage/postgres-call-repository.ts:3248), [cohort звонков](C:/Users/slavi/Desktop/www/callassist/apps/api/src/storage/postgres-call-repository.ts:2894).

**Исправление:** хранить отдельно время оказания услуги, провайдерский расчётный период и время получения данных. Для сверки использовать провайдерские daily buckets; для себестоимости звонка — его операции. Бэкофис должен явно переключать «расходы периода» и «стоимость выбранных звонков». Полуоткрытый диапазон `[from,to)` исключит повтор границы в соседних отчётах. Текущие rolling 24h/7d/30d дополнить «этот месяц», календарным диапазоном и UTC.

### A2 · P1 · Сверка цены прекращается раньше, чем Twilio отдаёт цену

**Факт:** у звонка 16 сентября задача `provider_call_cost_reconciliation` исчерпала 10 попыток. Все они закончились `PROVIDER_CALL_COST_PENDING`. Последняя — 17:03:27 UTC, примерно через 36 минут после звонка. Теперь цена $0.1802 доступна, но задача остаётся `dead_letter`.

Код: [ожидание цены](C:/Users/slavi/Desktop/www/callassist/apps/api/src/call-service.ts:1526), [лимит попыток](C:/Users/slavi/Desktop/www/callassist/apps/api/src/jobs/durable-job.ts:92).

**Исправление:** отделить нормальное ожидание поздней цены от технической ошибки, сделать редкие повторные чтения в течение суток и более, добавить периодическую проверку пропусков и действие повторной сверки. До получения цены показывать число незавершённых записей. Конкретную найденную задачу можно повторить штатным механизмом; в рамках аудита она не перезапускалась.

**Факт:** после исправления пропущенного звонка в приложении всё равно отсутствовали бы **$1.82962** остальных сентябрьских расходов. Сейчас разница с полным Twilio составляет **$2.00982**. Status `reported` означает только наличие хотя бы одной записи, а не полноту учёта.

**Исправление:** импортировать общий Twilio total и непересекающиеся категории. Хранить общие расходы аккаунта отдельно от атрибуции конкретным звонкам. Не добавлять account total к сумме Call prices — это разные представления одних расходов. Неприсвоенный остаток должен быть виден отдельной строкой.

### A4 · P1 · Проверка полноты usage может сообщать ложную полноту

**Воспроизведено действующей функцией:**

- Даны total=150, output=50 и отсутствующий input. Возвращается $0.001 за output, `unpricedMetrics=[]`. При таком единственном bucket админка сообщит `calculated`, хотя 100 токенов не оценены.
- Даны две duration-операции, но длительность известна только для одной: `usageRecords=2`, `durationSamples=1`, `durationSeconds=60`. Возвращается $0.017 без отметки пропуска второй длительности.

Код: [проверка duration](C:/Users/slavi/Desktop/www/callassist/apps/api/src/config/provider-pricing-policy.ts:91), [проверка input](C:/Users/slavi/Desktop/www/callassist/apps/api/src/config/provider-pricing-policy.ts:186), [вывод статуса](C:/Users/slavi/Desktop/www/callassist/apps/api/src/admin-operations.ts:199).

Кроме того, операции, у которых вообще нет usage-записи, не участвуют в usage buckets. `unpricedBuckets=1` на скриншоте обозначает общий Twilio bucket без локального тарифа. Это не одна потерянная операция и не счётчик полноты OpenAI. Даже полученные 37 цен Twilio не убирают этот статус, потому что actual и estimate оцениваются независимо.

**Исправление:** проверять полноту на уровне каждой ожидаемой платной операции до агрегации: известные/неизвестные usage, обязательные метрики, исход, применимый тариф, незавершённая операция. Отдельные состояния `complete`, `partial`, `pending`, `unavailable`, `free`. Не смешивать неизвестную цену и отсутствующий тариф. Сохранённый total использовать для проверки баланса модальностей. У beta accounting часть этих проверок уже строже; использовать единый механизм.

**Исправление:** показать начало достоверного покрытия, неизвестные операции и «расчёт по доступным данным». Импортировать исторические агрегаты Costs с явным источником и периодом. Не выдумывать задним числом токены отдельных звонков и не смешивать импортированный агрегат с локальными расходами без устранения пересечений.

### A11 · P2 · Сохранение Realtime usage не имеет восстановления после сбоя

**Факт по коду:** usage появляется на завершающих событиях, запись ставится в Promise-очередь процесса. При ошибке БД логируется ошибка и закрывается stream; это ограничивает дальнейший расход, но не восстанавливает уже начисленный. После `closed` события не обрабатываются. Падение процесса или потеря завершающего события могут оставить неполный ledger.

Код: [очередь](C:/Users/slavi/Desktop/www/callassist/apps/api/src/realtime/openai-realtime-bridge.ts:287), [response usage](C:/Users/slavi/Desktop/www/callassist/apps/api/src/realtime/openai-realtime-bridge.ts:784), [closed guard](C:/Users/slavi/Desktop/www/callassist/apps/api/src/realtime/openai-realtime-bridge.ts:903).

Конкретный объём потерь от этого механизма в текущих данных не установлен. Нужны durable ingestion либо обнаружение незавершённых responses и регулярная сверка провайдерских агрегатов. Не объявлять такую сессию финансово полной только по факту закрытия socket.

## 4. Что в текущей архитектуре сделано правильно

- Операции и usage отделены от денежных записей; raw ledger защищён от UPDATE/DELETE.
- Уникальные ключи операций, provider response/request IDs и cost IDs ограничивают повторную запись. В проверенной базе не обнаружено денежного дублирования Twilio connectivity.
- Неизвестный SKU не оценивается произвольным тарифом. Валюты хранятся отдельно; автоматической конвертации нет.
- Учитываются отдельные физические requests транскрипции и платные невалидные ответы с доступным usage. Успешные post-call chunks переиспользуются при повторе в той же generation.
- Текст, аудио, cached input и reasoning разделены достаточно для воспроизводимого расчёта известных данных.
- Защитный резерв beta — отдельная сущность. Его ancillary allowance $0.01/мин — защитная оценка, не импорт Twilio invoices и не основание заполнять отсутствующие фактические расходы.

## 5. UX-аудит предоставленных экранов

Это обзор трёх предоставленных статичных скриншотов и связанного UI-кода. Живой пользовательский путь, клавиатура, screen reader, zoom и адаптивное поведение в этой проверке не тестировались; утверждения о полной accessibility compliance не делаются.

1. **OpenAI usage — условно понятен.** Общая сумма и период заметны, но основной 30-дневный график и месячный виджет имеют разную временную основу. Для сверки необходимо зафиксировать один проект, период, UTC и время актуальности.
2. **Twilio usage — подходит для детализации с оговорками.** Строки «единицы / сумма» хорошо читаются. Иерархия содержит пересекающиеся категории, поэтому визуальная сумма групп не является способом проверить total. Usage summary — предварительная информация.
3. **Наша админка — требует переработки иерархии.** Основные деньги растворены среди повторяющихся fact-карточек. Неизвестные и неприменимые значения выглядят одинаково. Предупреждения не дают действия и не показывают масштаб пробела. Длинные цепочки `input / cached / cache write / output` трудно сопоставлять с числами, особенно при переносах. Две Realtime-карточки повторяют данные. Мелкие подписи и статусные плашки требуют отдельной проверки контраста и масштаба.

Рекомендуемый путь в новой админке:

1. **Сводка — главный экран.** Один период/UTC, источник каждой суммы, дата обновления и видимая полнота. До надёжного покрытия — отдельные суммы провайдеров, без ложного общего «итого».
2. **Раскрытие категории — детали по клику.** Сумма → компоненты → модель, единицы и формула → отдельные requests. Только применимые показатели. Общие Realtime requests считаются один раз.
3. **Сверка — отдельная вкладка/раскрытие.** Одинаковый scope: у провайдера / у нас / разница / объяснение / действие. Пропуски и поздние цены видны без чтения raw JSON.

В реализации disclosure должен быть настоящей кнопкой или `details/summary`, с `aria-expanded`, видимым focus, доступным названием и управлением Enter/Space. Боковая панель — с предсказуемым фокусом и закрытием; цвет дополняет текст, а не заменяет статус. Даты и суммы должны оставаться рядом и на узком экране.
