# План упрощения Live runtime

> Historical checkpoint, not the current runtime specification. As of 28 September,
> consent uses native `report_consent`, and `end_call` carries a reason without a
> scripted recap. See the [current runtime](live-unified-runtime.md) and
> [real-call review](live-call-review-2026-09-28.md). Results and pending items below
> describe the implementation at this report's date.


Дата: 2026-09-27. Ветка: `codex/live-unified-runtime`.
Статус: замена реализована на этой ветке; автоматические проверки пройдены, ожидается ручная приёмка через Twilio.
Текущее состояние и ограничения: [отчёт о реализации](live-managed-delegation-2026-09-27.md).
План заменяет направление дальнейшего развития собственного task controller.
Прежние отчёты остаются историей реализации и проверок, а не доказательством готовности новой схемы.

## Цель и границы

Live самостоятельно ведёт разговор; GPT-6 Luna вызывается через встроенную Responses delegation
для рассуждений и инструментов. Приложение управляет разрешениями, записью, действиями,
телефонией и учётом расходов. Одна Live-сессия и один голос на протяжении человеческого разговора.
Локальная проверка: Live, fallback=false. Выкладка только после ручного принятия владельцем.

Официальные основания:
- [Getting started](https://developers.openai.com/api/docs/guides/live): короткий разговорный промпт, подробные процедуры в backend.
- [Prompting](https://developers.openai.com/api/docs/guides/live-prompting): самостоятельные обычные ответы и уточнения.
- [Delegation and tools](https://developers.openai.com/api/docs/guides/live-delegation): managed Responses, функции приложения и ответственность за состояние.

## Что показал код до этой реализации

`live-conversation.ts` создаёт client delegation, собирает реплики и запускает `LiveTaskController`.
`unified-live-call.ts` запрещает самостоятельные ответы после согласия и воспроизводит решения
backend через controlled speech. Для appointment-планов даже обычный `speak` дополнительно
проходит `action_speech` и буферизацию. Это механизм последнего отказа продолжить разговор.
Успешные запросы провайдера не означают, что приложение пропустило ответ в телефонию.

## 1. Зафиксировать исходное состояние и проверить контракт

- Сохранить восстановимый checkpoint всех текущих изменений, включая untracked исходники;
  не включать секреты, записи, локальные БД и приватные отчёты. Не откатывать ветку целиком.
- Сверить точные события, параметры и ограничения с официальным API reference.
- Коротким реальным provider probe через production transport проверить managed delegation,
  возврат function result, обновление backend после согласия, usage, перебивание и closing.
- Responses mode выбрать при создании сессии: переключение client → responses на ходу
  не поддерживается. До согласия backend не получает план и не имеет action tools;
  обработчик приложения дополнительно отклоняет преждевременные вызовы.
- До удаления старого механизма доказать на probe, как разрешённое завершение связывается
  с реально воспроизведённым аудио. Ack контекста и Responses completion не являются
  границей речи. Не вводить выдуманный аналог Realtime `response.done`.
- Проверить момент начала автоматически делегированной работы относительно бюджетного
  допуска: нельзя заявлять строгий pre-request лимит, если событие приходит после старта.
  При необходимости резервировать ограниченный бюджет всей сессии и учитывать запросы в нём.

## 2. Заменить управление обычным диалогом

- В `OpenAILiveConversation`: `delegation.type=responses`, `gpt-6-luna`,
  `parallel_tool_calls=false`; обработка документированных response envelopes и tool results.
- Live получает короткие правила языка, формальности, перебиваний, задачи и делегирования.
  Backend получает полную execution projection неизменяемого утверждённого плана.
  Исходное задание и перевод для UI в runtime не передаются.
- После согласия и успешного запуска записи Live самостоятельно задаёт вопросы, уточняет,
  слушает и отвечает. Backend вызывается по потребности, а не после каждого фрагмента текста.
- Удалить `LiveTaskController`, `runLiveTask`, формат решений speak/wait/ignore/resume_closing,
  циклы исправления этих решений и повторную сборку истории для каждого запроса.
- Удалить обязательную семантическую проверку обычных реплик, запрет самостоятельного
  продолжения и ожидание application-controlled speech в основной беседе.
- Не переносить старый controller под другое имя. Оставить технические ограничения
  соединения, размера очередей, бюджета и времени звонка; они не выбирают следующую реплику.

## 3. Сохранить небольшой слой обязательных проверок

- Сохранить AMD/voicemail, подписанную привязку stream к попытке, PCMU 8 kHz,
  prewarm, immutable snapshot, приватность и application-owned consent.
- Сохранить работающую семантику согласия, DTMF и запрет записи/задачи до согласия.
  Не менять одновременно её классификатор и управление основным разговором.
- Сузить `LiveControlledSpeech` до действительно обязательных переходов, если требуется;
  убрать его из обычных вопросов и ответов. Проверка обязательного содержания disclosure
  не должна требовать побуквенного повторения произвольной разговорной реплики.
- Вынести проверки конкретных действий в небольшой dispatcher инструментов:
  схема аргументов, фаза, snapshot, полномочия, ограничения, актуальность и идемпотентность.
  Имена новых функций приложения определить при реализации, не выдавать их за API OpenAI.
- Сохранить журнал voice actions и migration 0085, шифрование, удаление и экспорт.
  Различать разрешено, предложение озвучено, собеседник подтвердил и результат внешней системы.
- Поправки получателя делают прежнее предложение неактуальным; дубликаты tool events
  возвращают сохранённый результат и не повторяют действие. Неясный результат не означает успех.
- В телефонной записи обязательство может создаваться самой речью. Проверка function call
  сама по себе не гарантирует контроль таких слов. До принятия проверить отдельную границу
  разрешённого обязательства и при необходимости защищать только эту реплику. Если managed
  delegation не позволяет сохранить требуемую защиту, явно зафиксировать ограничение;
  не маскировать его промптом и не возвращать проверку всего разговора.

## 4. Естественное завершение и воспроизведение

- Live кратко подводит итог существенных данных/договорённостей и прощается.
  Не повторяет каждый ответ; не спрашивает общего «Вы согласны со всем?».
  Подтверждение конкретного обязательства остаётся отдельным необходимым шагом.
- `end_call` запрашивает завершение. Приложение проверяет состояние и исполняет hangup
  только после воспроизведения соответствующего closing audio.
- Изолировать небольшой механизм playback: поколение вывода, очередь аудио, mark/clear,
  отмена closing при новой речи. Поздний/очищенный mark не разрешает hangup.
- Проверить поздние audio chunks, тишину в full duplex, ранний end_call и прерванный recap.
  Точный способ определения конца closing выбирается по проверенному протоколу в этапе 1;
  произвольный таймер не является доказательством доставки прощания.
- При разрыве или ограничении времени честно завершать/отмечать техническую ошибку;
  не объявлять успех и не переключать голосовой runtime незаметно.

## 5. Транскрипты, биллинг и админка

- Сохранять native Live transcripts с дедупликацией и timing; различать сгенерированное,
  отправленное и подтверждённое playback. Не выдавать невоспроизведённый текст за услышанный.
- Сохранить consent timeline, стабильную группировку UI и document scrolling завершённого звонка.
- Сохранить post-call transcription, автоматическую оценку и исправления бюджетных retry/reserve.
  Их смена не входит в этот рефакторинг.
- Учесть каждую managed Responses operation, включая failed/cancelled/late outcomes,
  отдельно от длительности Live; не дублировать usage при повторных событиях.
  Неизвестная стоимость остаётся неизвестной, а не нулевой.
- В admin/export оставить stage, IDs и причины ошибок без сырых промптов/аудио/секретов.
  Обновить обозначение версии runtime. Все пользовательские тексты — во всех семи UI-локалях.

## 6. Удаление старого кода и документация

- Удалить неиспользуемые controller/backend, их типы, опции, тесты внутреннего формата решений
  и probes, которые больше не проверяют production path. Поведенческие проверки перенести.
- Сохранить Realtime как отдельный driver. Live без fallback не создаёт Realtime-сессию.
  Совместимость старой явной fallback-настройки проверить отдельно; не включать её в новый путь.
- Не менять опубликованные/применённые миграции. Новая миграция — только при доказанной
  необходимости, аддитивная. Сам рефакторинг не требует новой таблицы.
- Сохранить независимые исправления компилятора, регистрации, повторного звонка,
  feedback, телеметрии и post-call pipeline.
- README, `.env.example`, runtime/deployment docs описывают один актуальный Live путь.
  Старые отчёты обозначить историческими, а не поддерживать несколько активных архитектур.

## 7. Приёмка

Автоматически проверить общий runtime, оба driver, PCMU, consent/отказ/условие/DTMF,
tool schema/authorization/idempotency, изменение предложения и поздние результаты,
interruption/mark/clear/hangup, disconnect, usage, приватность, transcript ordering и UI.
Не использовать безусловный mock `equivalent` как доказательство качества семантики.

Реальные provider integration проверки проходят через тот же bridge, что приложение.
Затем реальные Twilio-звонки: простой вопрос; интервью с шумом/паузами; допустимая запись;
запрещённый день; исправление времени; отказ; неизвестный ответ; прерванное прощание;
автоответчик; технический сбой. Семантическое согласие проверить на всех языках звонка.
Сравнить с baseline время answer → disclosure, consent → первый вопрос, задержки ответов,
количество делегаций/стоимость, корректность договорённостей и завершения. Не ограничиваться
одним диалогом Елены и не зашивать его фразы в runtime.

Полный suite: test, lint, typecheck, build и применимые deployment/migration/copy checks.
Финальный diff review: regressions, authorization, privacy, billing, races, dead code.
Критерии: обычный разговор не требует application approval каждой реплики; обязательные
проверки сохранены; нет повторных действий/ложного успеха/бесконечного зависания;
прерывание не приводит к hangup по старому mark; provider и локальные ручные тесты пройдены.
Ошибки моделей всё ещё возможны: эти проверки не являются гарантией для любого сценария.
Merge и production deployment — только после отдельного подтверждения ручного результата.
