Остальные события сохраняют прежнюю запись и обработку отказа: в частности,
`consent.failed`, `conversation.started`, `conversation.ended`, `disclosure.started`.
Они участвуют в lifecycle/system outcome и не ждут необязательную очередь.

Обязательные disclosure/consent receipts, recording admission, action/terminal journals,
provider accounting и transcript persistence не переводились в best-effort.
Зависший необязательный writer не порождает дополнительные параллельные записи.
Его очередь не является durable outbox: при завершении процесса её данные могут потеряться.
Отсутствие диагностики не означает успешную приёмку.

## Значение измерений

Новые события используют существующее имя `conversation.task`, `phase=diagnostic` и
строго типизированный `metadata.diagnostic`. Миграция БД не нужна.
Текст, transcript, аудио, task context и произвольные provider errors в них не сохраняются.
Экспорт имеет отдельный allowlist вложенных полей и отклоняет некорректные измерения.

| `kind` | Что измеряется | Что из этого нельзя заключать |
| --- | --- | --- |
| `startup` | `prepared`/`cold`, вызов Live start → ready; admission → передача required disclosure. Для отмены `not_released`, время выпуска `null`. | Это не pickup → первый слышимый звук и не подтверждение прослушивания. |
| `speech_render` | Полная application render pipeline; ожидание reservation + начальный journal; рендер; завершающий journal. На успехе отдельно headers, чтение полного body и PCM conversion. Operation ID связывает запись с обязательным журналом расходов. | `failed` относится к pipeline, включая journal failure; не заменяет provider outcome. Headers не являются первым аудиобайтом. |
| `consent_to_audio` | Решение consent → первая отправленная порция PCMU с речевой энергией, с источником `native`/`application`; отдельно recording admission и последующее ожидание. Также последняя локально наблюдаемая граница consent → отправка. Для DTMF граница `null`. | Локальная граница — время получения transcript/VAD события, не точное окончание произнесённого «да». Первый звук может быть acknowledgment или failure, не содержательным ответом. |
| `task_context` | От начала конфигурации task context до первого и последнего требуемого ACK; число исходных команд и UTF-8 bytes их JSON payload без `event_id`. | Это агрегат; не N последовательных RTT. Повторные отправки не включены в счётчики. ACK не доказывает выполнение инструкции моделью. Неполный набор ACK не создаёт успешную запись. |
| `audio_output` | При закрытии: отправленные порции/аудиодлительность, clear, максимум расчётной очереди, отдельно native объём/максимальная порция, cache hits/misses. | Очередь — локальная оценка, не измерение Twilio/handset. Большая порция не доказывает генерацию faster-than-realtime. Cache miss не равен начатому платному запросу. |

Старая `conversation.first_audio` сохраняет свою точку отсчёта после recording admission.
Измерения основаны на локальных часах процесса; отрицательные разности ограничены нулём.
Не следует сравнивать runs с коррекцией системных часов. Полный разбор DB/REST шагов
recording admission и акустическая матрица из A0 остаются следующей работой по измерению.

## Следующий шаг и откат

Акустический выигрыш в миллисекундах не заявляется: overlap подтверждён управляемыми
задержками тестов, но естественность речи и воспринимаемую задержку проверяют на согласованном
тестовом звонке. Начать с cold/prepared startup, отказа, короткого согласия, паузы без ответа,
обычного завершения и поправки во время farewell. При сравнении сохранять один и тот же
голос, модель, policy и сценарий, учитывать потерянную диагностику отдельно.

A4–A5 и эксперименты с consent, инструкциями/SpawnThinking, перебиваниями, streaming TTS,
fixtures и pacing в эту очередь не входят. Нельзя оценивать их как уже принятые улучшения.

Откат поведения выполняется при отсутствии активных звонков возвратом voice-изменений
и перезапуском API/worker. Расширенную схему чтения/экспорта diagnostic нужно сохранить,
пока БД содержит новые события. Полный checkout старого commit с чтением этих событий
не проверялся; отсутствие SQL migration само по себе не гарантирует совместимость старого reader.
Approved snapshots, settings и БД для отката этой очереди менять не требуется.

### Задержка: ожидающий запрос блокирует продолжение

| Время | Событие |

| 11:16:12.379 | Приходит transcript нового ответа абонента: через 96 мс после fallback. Версия входа меняется. |
| 11:16:12.500 | Начинается backend response: через 217 мс после fallback. Журнал не доказывает его причинную связь с отправленной командой. |
| 11:16:16.930–16.948 | Response завершён, `report_task_state=continue` принят. Результат инструмента готов, но продолжение удерживает ожидающий `response.create`. |
| 11:16:27.284 | Истекает 15-секундный таймаут старой команды (`ack_timeout`). После готового результата прошло ещё примерно **10,34 с**. |
| 11:16:27.732–32.073 | Следующий backend response: 4341 мс. |

Механизм в [live-conversation.ts](../../../apps/api/src/voice/live-conversation.ts):
`#acknowledgeBackendStart` связывает unscoped command с наблюдаемым response только
при совпадении текущих revisions. При позднем transcript это условие уже не выполнено.
`#flushContinuations` ждёт все pending `response.create`; старый запрос освобождается
по 15-секундному таймеру. Даже завершённый новый response не освобождает этот запрос.

Последовательность воспроизведена детерминированным тестом с fake timers и mock providers:
fallback → новый transcript через 96 мс → response через 217 мс → завершение через
4430 мс → принятый tool result → continuation только после таймаута fallback.
Проверено, что результат инструмента отправлен один раз и до таймаута второго
`response.create` нет. **Одинаковый результат на исходной и текущей реализации.**

Исходные `live-conversation`, `unified-live-call`, `openai-live-bridge`, `create-voice-runtime`
из commit `513c0217a754d9991151f60071926a03960af1f5` подключались через временные
отдельные модули к одному тестовому harness; остальные зависимости оставались текущими.
Оба прогона: 1 passed, остальные 347 тестов harness пропущены фильтром.
Это подтверждает наличие гонки в исходной оркестрации; **это не парное сравнение
реальных звонков и не доказательство отсутствия всех регрессий A0–A3**.
Временные исходники удалены после теста. Локальный воспроизводитель и логи:

### Начало разговора: симптом доказан, причина пока не установлена

После recording admission task context отправляется 18 командами, 17 419 UTF-8 bytes.
Первый ACK приходит через 220 мс, полный набор — через 1987 мс. Native audio к этому
времени уже открыт. Команда начала задачи уходит в 11:15:51.887, примерно через
1,4 с после первой отправленной порции со звуковой энергией.

Поздние instructions являются проверяемой гипотезой: GPT-Live допускает прерывание
текущей речи при `session.instructions.append`.
[Официальная документация GPT-Live](https://developers.openai.com/api/docs/guides/live-delegation).
Однако эти времена не доказывают, какая команда оборвала фрагмент и оборвало ли его
приложение вообще. В записи на канале абонента нет заметной речи до 6,86 с;
это ослабляет гипотезу обычного речевого перебивания, но не исключает артефакт
входящего WebSocket-аудио. Есть только агрегат `clearCount=6`, без времени и причины
каждого `clear`. Native transcript отмечен complete, но раннего фрагмента в нём нет.

### Связь с A0–A3 и решение по приёмке

- Звонок шёл по **prepared** path: изменение cold startup A3 не выполнялось.
- Closing содержал обычный результат: изменение no-evidence farewell A2 не выполнялось.
- Ошибок/потерь `LIVE_TELEMETRY_UNAVAILABLE` в журнале звонка не найдено.
- Scheduler, правила pending command/continuation и открытие native audio перед ACK
  существовали до A0–A3. В `live-conversation.ts` diff первой очереди добавляет измерения.
- Отсутствие ошибок телеметрии и воспроизведение гонки на исходном коде не заменяют
  реальную сравнительную проверку. Заявлять, что candidate улучшил разговор, нельзя.

**Приёмка остановлена на неудовлетворительном пользовательском результате.**
После жалобы runtime-код и конфигурация не менялись; локальные процессы продолжают
работать с A0–A3. Откат не выполнялся и исправление симптомов не заявляется.
Возврат исходной оркестрации сам по себе не устраняет воспроизведённую гонку.

### Скорректированный порядок исправления

1. **Сопоставление backend command и response.** Проверить и поддержать явный
   `response.event.client_event_id`: протокол предусматривает это необязательное поле,
   текущая обработка nested `response.created` его не использует. При точном совпадении
   нужно освобождать ожидание команды, сохраняя её исходные revisions и физическую
   занятость backend до завершения response. Старые tools не должны становиться свежими.
   [Схема GPT-Live primary WebSocket](https://developers.openai.com/api/reference/resources/live/primary-websocket).
   Наличие поля в проблемном звонке не сохранено: это направление исправления,
   а не уже доказанное решение именно этого случая.
2. **Измерить неоднозначный случай до смены таймаутов.** Сохранить ограниченную
   техническую последовательность IDs/timestamps: отправка fallback, revision change,
   `response.created`, наличие correlation ID, завершение run, ожидание/выпуск continuation.
   Без текста и аудио. Отдельно проверить случай, когда correlation ID отсутствует.
   Не считать любой новый native response подтверждением старой команды и не отправлять
   повторный запрос только из-за истечения короткого таймера: принятый запрос может
   ждать завершения текущего response.
   [Правила continuation в GPT-Live](https://developers.openai.com/api/docs/guides/live-delegation).
3. **Отдельно установить источник обрыва.** Для первых секунд после consent записывать
   время первой/последней переданной native порции, output gate transitions, instruction
   send/ACK, входящий activity start и каждый Twilio `clear` с причиной. После этого
   менять только подтверждённый механизм. Простое закрытие audio до всех ACK уже несёт
   риск потери начала ответа; исключение `clear` меняет обработку реальных перебиваний.
4. **Проверить лишние backend переходы после устранения ожидания.** Два последующих
   response заняли ещё около 9 с. Их необходимость требует разбора решений backend;
   один удачный `report_task_state` не даёт приложению права самостоятельно объявить
   выполнение задачи и вызвать `end_call`.
5. **Повторная приёмка с записью.** Сначала mock-регрессии exact/missing/mismatched
   correlation, поздний transcript, работающий backend после timeout, повторный terminal
   event, correction и appointment authorization. Затем согласованный звонок с теми же
   голосом, моделями, policy и сценарием. Измерять полный первый вопрос и паузу до итога,
   проверять отсутствие обрыва, повторов действий и преждевременного hangup.
   Переключение модели, streaming TTS и ослабление consent не объединять с этим исправлением.
