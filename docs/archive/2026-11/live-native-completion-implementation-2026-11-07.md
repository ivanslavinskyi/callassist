## Поведение и границы

Если Live произнёс заключение, но не делегировал `end_call`, host теперь может запустить внутреннюю проверку во всех профилях: general, book, confirm_existing, reschedule, cancel. Профиль сложной записи использует тот же механизм. Live сохраняет управление вступлением, вопросами, ответами и формулировкой прощания. Обычная речь не требует разрешения backend. Стартовый Live prompt и инструкция подготовки не менялись в рамках этого исправления.

Восстановление использует существующий `nativeReview`: developer input через `response.item.create`, затем явный `response.create`. Добавление текста само по себе не запускает backend. Это соответствует [GPT-Live delegation](https://developers.openai.com/api/docs/guides/live-delegation). Получение caption не означает окончания аудио: в этом протоколе нет output-audio-done; поэтому проверка воспроизведения сохранена. См. [Managing GPT-Live sessions](https://developers.openai.com/api/docs/guides/live-conversations). Пороги ниже — настройки приложения, не гарантии API.

| Ситуация | Запуск внутренней проверки |
| --- | --- |
| Наблюдаемый конец фразы похож на прощание | Через 400 мс без новой речевой активности |
| Другая формулировка или язык | Через 6 секунд тишины, однократно на неизменившийся эпизод входной речи |
| Запрос назначения воспроизведён и получен ответ, но результата нет | Существующая проверка результата через 2 секунды |
| Подтверждённое назначение без `end_call` | Через 2 секунды; известное прощание ускоряет проверку |
| Backend занят | Проверка ждёт события завершения его работы, без опроса таймером |

Список выражений прощания — только подсказка для ускорения. Слово, пауза и результат регулярного выражения сами по себе не разрешают отключение. Backend проверяет актуальное задание, реально произнесённые итог/благодарность/прощание, отсутствие нового вопроса и состояние назначения. Если Live ждёт ответа или ещё не закончил, review возвращается без инструмента и без сообщения для произнесения. После обычного вопроса долгая пауза всё ещё может стоить одного такого внутреннего review; нулевая дополнительная стоимость не обещается.

Один тихий review и одна ускоренная проверка разрешены для неизменившейся входной ревизии; ускорение может последовать за ранним отрицательным review. Новая речь сбрасывает таймер. Поздняя поправка делает старое решение недействительным. Уже принятое закрытие, отказ и закрытый controller исключают запуск. `backendIdle` только пробуждает отложенную проверку и не обнуляет счётчик ошибок backend.

## Защита и задержка

Host по-прежнему требует фактическую цитату заключения и последней реплики собеседника. Сравнение closing evidence теперь игнорирует пунктуацию и различия пробелов: backend иногда вставляет точки, отсутствующие в Live captions. Слова, регистр, отрицания и числовые токены не исправляются. Изменение фамилии и подмена времени остаются различиями. Проверки цитат назначения и его полномочий не ослаблялись.

После принятого `end_call` остаются существующие 1000 мс спокойного аудиохвоста, телефонный playback mark/ACK и 350 мс для поздней поправки. Нет дополнительного ожидания ответного прощания. Если оно всё же прозвучало, свежая реплика требует актуализации решения; это может добавить backend round trip. 400 мс — срок начала проверки, а не обещание положить трубку за 400 мс. Задержка модели и доставки mark также входит в итоговое время.

## Телеметрия

Добавлены `closing.backend_review` с причиной/ревизией/профилем и однократное `completion.review_deferred`. Сохраняются события результата инструмента и `closing.playback`: mark_sent, mark_acknowledged, cancelled, drained. Descriptor содержит версию, recovery thresholds и `traceDrainMs`.

Обнаружено, что прежний trace timeout 2,5 секунды мог обрезать `session.closed`, пока backend завершал продолжение после инструмента. Сбор trace после отключения media согласован с существующим 15-секундным grace period Live transport. При `session.closed` trace завершается немедленно. Отсутствие подтверждения по дедлайну честно даёт `complete:false`, `sessionClosed:false`, `drainTimeout:true`. Это отдельный период после отбоя, он не удерживает телефонное соединение. Поздние backend события после закрытия не получают права исполнять действия. При отказе trace и остальные данные удаляются по прежнему протоколу.

## Разночтение фамилии в транскрипте и PDF

В исследованном реальном звонке `spokenIdentities.representedPerson.original` и `.spoken`, вступление и startup содержат **Slavinskyi**. В исходном output transcript событии от Live уже появляется **Slavinsky**. Латинское написание здесь не менялось функцией транслитерации. `call-result-panel` передаёт отображаемые segments в `buildDerivedTranscriptPdfDefinition`; тот переносит `segment.text` в PDF. Старый `buildFinalTranscriptPdfDefinition` также использует исходный текст сегментов. PDF не является местом первичной замены.

По captions без прослушивания нельзя установить, изменилось произношение или только текстовое представление. Форма и замороженная исходная identity остаются правильными. Усиление prompt не даёт детерминированной гарантии написания в аудиотранскрипции.

Универсальное дальнейшее решение:

1. Использовать identity из утверждённого snapshot как единственный источник точного имени для реквизитов, action records, календаря и структурированных результатов. Произносительное написание использовать исключительно в речевом контексте. Отдельно проверить границу `NativeAppointmentCall`, где сейчас передаётся речевая проекция `context.brief.representedPerson`: для кириллицы она может отличаться от original.
2. Сохранять raw Live transcript и его provenance. Не подменять распознанную речь глобальной нечёткой заменой похожих фамилий.
3. Если требуется исправленное представление текста, хранить отдельную версию с entity reference, canonical spelling, исходным span и происхождением исправления. Неоднозначные совпадения оставлять без автоматической подмены. UI, копирование и PDF должны использовать одну проекцию и показывать, что текст уточнён по данным задания.
4. В текстовые summary/translation prompts передавать общую таблицу точных имён. Структурированные поля собирать по entity id, а не восстанавливать из свободного текста модели.
5. Проверить разные алфавиты/транслитерацию, падежи, дефисы и апострофы, двух людей с похожими фамилиями, упоминание третьего лица и явную поправку собеседника. Совпадение букв в отчётных реквизитах можно гарантировать; произношение и свободную транскрипцию — только проверять, а не обещать их безошибочность.

Этот блок фиксирует расследование и следующий самостоятельный объём работ. Переписывание транскриптов и изменение источника appointment identity не входят в данное исправление завершения.
