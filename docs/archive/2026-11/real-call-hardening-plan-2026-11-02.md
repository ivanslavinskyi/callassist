## 1. Цель и порядок принятия решений

Сохранить достигнутый результат: приложение получает согласие, ведёт естественный
разговор, оформляет одну разрешённую запись, получает подтверждение и корректно
завершает звонок. Устранить доказанные ошибки представления и затем — только при
достаточных доказательствах — конкретные ошибки управления разговором.

При конфликте целей порядок такой:

1. Сохранность согласия, границ записи, разрешений и единственности действия.
2. Успешность разговора, правильная реакция на поправки и отсутствие ложного успеха.
3. Непрерывность речи, отсутствие новых перебиваний, повторов и зависаний.
4. Корректность итогов и полнота диагностики.
5. Сокращение задержек, числа запросов и стоимости.

Более быстрый звонок не считается улучшением, если он чаще пропускает ответы,
объявляет неподтверждённую запись или преждевременно завершает разговор.
Нет обязательства менять рантайм ради закрытия всех пунктов: недоказанная причина
может остаться открытым расследованием с сохранением рабочего поведения.

## 3. Неприкосновенные свойства рабочей базы

Сверять с текущим [engineer guide](../../engineer-guide.md), исходниками и тестами.
[Октябрьский план стабилизации](../2026-10/live-runtime-stability-plan-2026-10-04.md)
содержит исторические этапы, включая уже заменённые решения; не применять их заново.

- Один native Live-сеанс для обычного диалога. Не вводить новый оркестратор,
  проверку каждой реплики другой LLM, автоматический ASR или второй voice runtime.
- Приложение владеет consent, recording admission, protected commitments и closing.
  Сохранить оба режима согласия, действующие settle/deadline, DTMF, AMD и fallback.
- Ни запись, ни сохранение recipient transcript не начинаются до разрешённой границы.
  Обязательное disclosure подтверждается актуальным playback mark.
- Сохранить действующий opening после recording admission и обработку ранней речи.
  Не возвращать ожидание всех context ACK перед открытием native audio.
- Approved snapshot, конкретный слот, provider scope и финансовые ограничения
  остаются авторитетными. Не выдумывать недостающие факты.
- `uncertain` означает возможную доставку: дальнейшая проверка касается того же
  слота; нельзя автоматически повторить бронирование или выбрать другой слот.
- `delivered` не означает `confirmed`; требуется последующее содержательное
  подтверждение. Шум, «угу», исправление адреса и разрешение продолжить не заменяют его.
- Один владелец backend-работы; timeout не даёт права дублировать неоднозначно
  принятую команду или отпускать физически занятую сессию.
- Завершение — после актуального подтверждения воспроизведения. Старый/очищенный
  mark, завершение модели или инструмент сами по себе не разрешают hangup.
- Существенная поправка во время прощания возвращает разговор в работу;
  сохраняются абсолютные deadlines и ограниченные восстановления.
- Честные gaps/uncertainty сохраняются. Не улучшать метрики подавлением предупреждений.

  на каждый turn или обязательный `report_task_state` на обычный ответ.

Приёмка: нет обращений к отсутствующему наблюдателю, выдуманной DOB/истории визитов,
обещаний callback; текущий вопрос не теряется; нет роста лишних tools или задержки.
Mock-тесты доказывают routing, но не естественность речи: для этого нужна отдельная
контролируемая разговорная проверка. Без воспроизведения — только результат
расследования, без широкого переписывания промпта.

### E. Паузы, ACK и backend ownership

Локальный результат: `#acknowledgeBackendStart` теперь узнаёт scoped continuation
по delegation + точному predecessor response независимо от актуальности старого
контекста. Исходные revisions сохранены для отклонения устаревших tools. Unscoped
команды, таймеры и физическая занятость backend не ослаблены. В paired mock replay
ожидание решения после поправки сократилось с 15001 до 5600 мс; ожидание готового
continuation после завершения старого — с 15000 до 0 мс. Это не измерение ускорения
реального звонка. Исторический экспорт не содержит причинной связи всех команд
с delegation, поэтому причины всех трёх ACK timeout остаются открытыми.

- [ ] Разложить ожидание: конец речи → native реакция; settlement → decision due;
  due → dispatch; dispatch → start/ACK; tool → continuation; TTS → audio release → mark.
- [ ] Проверить уже существующие metadata/logging; добавить только недостающие
  bounded counters/events без блокирующих записей в обработке каждого audio frame.
- [ ] Различать causal ACK, ambiguous backend start, реальную физическую работу,
  устаревшую команду и ошибку текущего владельца. Число warnings не является KPI само по себе.
- [ ] Воспроизвести overlap native delegation/application request, delayed/missing
  ACK, поздний completed/error, новый recipient turn при занятом backend, disconnect.
- [x] Исправлять только установленное лишнее ожидание/потерю continuation.
  Не сокращать 15-секундный timeout, grace/quiet windows или VAD «на глаз».
- [x] Не освобождать lease по локальному timeout и не повторять response.create,
  если нет доказательства, что предыдущая команда отклонена.

Приёмка: максимум один физический владелец; нет потерянных continuation,
двойных tools и orphan callbacks; поздний timeout не завершает новый успешный
разговор; актуальный неисправный запрос имеет конечный путь восстановления.
Уменьшение конкретной паузы подтверждается paired replay, а не суммой длительностей
моделей (они могут перекрываться). Если причина не найдена, параметры сохраняются.

### F. Завершение без ненужного повтора

Исследование: одно принятое `end_call`, одна TTS generation, два playback generation.
Входящий всплеск в WAV даёт расчётный restart 08:35:34.774–34.793 UTC при смещении
20-мс сетки; наблюдаемый restart — 08:35:34.787. Новый recipient transcript и
второй terminal tool в этом интервале отсутствуют. Это согласуется с fallback
после acoustic interruption, а не с дублем решения модели. PCM-анализ не отличает
шум от короткой речи и не заменяет отсутствующие transport events.

- [x] Различить duplicate keep_closing/end_call, pending render, acoustic pause,
  короткое подтверждение и существенную поправку. Существующая идемпотентность
  активного playback уже реализована; не считать её отсутствие причиной без проверки.
- [x] Воспроизвести последовательность с двумя closing generations и установить
  фактическую причину отмены первого проигрывания.
- [ ] Сначала исправить лишний restart, если он доказан. Не игнорировать входящую
  речь глобально и не завершать звонок по успешному end_call без playback receipt.
- [ ] Возобновление с позиции внутри аудио, сокращённое прощание после прерывания
  или новая политика barge-in требуют отдельного дизайна и доказательств; не входят
  автоматически в небольшой fix.

Решение: runtime не менять ради подавления воспроизведённого защитного fallback.
Повтор после очищенного playback нужен до актуального mark; убрать его без новой
политики значит рискнуть потерей итоговой речи или поправки. Существующий тест
усилен проверками единственного TTS/terminal decision, отсутствия лишней делегации
и точного 900-мс ожидания; добавлены короткий всплеск, поздняя поправка и абсолютный
deadline при повторных acoustic interruptions. Разговорная приёмка и изменение
политики повторного аудио остаются открытыми. Следующий независимый этап — G.

Матрица: шум без текста; «да/спасибо/до свидания»; новая дата или отмена; длинная
поправка; repeated keep_closing во время render; old/cleared/duplicate mark;
render failure; разрыв соединения; непрерывные прерывания до абсолютного deadline.

Приёмка: нет лишнего restart без причины; существенная поправка всегда сохраняет
возможность продолжить; нет нового преждевременного hangup; один terminal decision
не меняется от дубля; сохраняются конечные deadlines и лимит восстановления.

### G. Частичное воспроизведение и наблюдаемость

- [x] Отдельно представить requested/rendered/released/acknowledged/interrupted,
  reason, generation, mark и границы времени. Проверить существующие playback
  contracts, native capture, composer, storage и export allowlist до расширения.
- [x] Не добавлять полный requested text в transcript как полностью услышанную речь.
  Если точный слышимый префикс неизвестен, явно сохранять это ограничение.
- [x] Сохранять `coverage: partial` при реальном пробеле; не выдумывать recipient
  reply из исходящего audio или заранее известного скрипта.
- [x] Диагностика не меняет live scheduling и не требует дополнительного ASR.
  Новые поля совместимы со старыми экспортами и отсутствующими значениями.
- [x] Проверить redaction, consent boundary, retention/deletion и размеры экспорта.

Результат: optional `conversation.task.metadata.playback`, одна terminal snapshot
на попытку с timestamps, outcome, reason, markId и owner. Нет текста, аудио или
вычисленного heard prefix; `revision` связывает generation, mark — transcript receipt.
Запись не блокирует playback/hangup, ошибки не закрывают звонок. Старые события
читаются без дополнения вымышленными полями. Следует существующей retention
технических `call_events` после удаления содержимого. При crash или ошибке записи
snapshot может отсутствовать; это неизвестность, не доказательство успешной доставки.

Приёмка: прерванная application-фраза объяснима в диагностике; подтверждённый
playback представлен один раз; pre-consent recipient content не появляется;
старые записи читаются; новые события не добавляют ожиданий в voice path.

### H. Подготовка недостающих фактов

- [x] Для записи в клинику предложить необязательные сведения: DOB и был ли уже
  визит. Допустимы «не знаю» и «не передавать»; без этих данных звонок не блокируется
  автоматически, поскольку исследованный звонок достиг цели и без них.
- [x] В approved facts передавать только явно предоставленное и разрешённое;
  отсутствие ответа не означает «первый визит» или отказ сообщить данные.
- [x] Не собирать медицинские подробности, не требуемые задачей. Проверить отображение
  пользователю и approval snapshot, локализацию и отсутствие влияния на другие задачи.

Приёмка: подготовка помогает ответить на реальные уточнения, но не добавляет
обязательный опрос, не меняет действующие snapshots и не выдаёт неизвестное за факт.

Локальный результат H: раскрываемая подсказка рядом с существующим полем разрешённой
информации; пользователь сам вводит сведения или явное «не знаю»/«не передавать»
по нужному пункту. Подсказка не копируется в факты и не классифицирует задачу.
Проверены UI markup на всех семи локалях, неизменность пустых/заполненных полей,
доступность подготовки другой задачи, approval и старые snapshot hashes.
Проверки compiler используют контролируемые ответы провайдера; это не приёмка
поведения живой модели. Подробности и команды — в записи реализации.

## 5. Проверки и критерии «не ухудшить»

Для каждого diff выбрать проверки по затронутому поведению. Примеры команд
из корня репозитория (запуск при реализации, не выполненная приёмка этого плана):

```powershell
corepack pnpm --filter @callassist/api exec vitest run src/text-processing/summary-calendar.test.ts src/text-processing/summary-workflow.test.ts
corepack pnpm --filter @callassist/api exec vitest run src/voice/live-appointment-copy.test.ts
corepack pnpm --filter @callassist/api exec vitest run src/voice/unified-live-call.test.ts src/voice/openai-live-bridge.test.ts
corepack pnpm --filter @callassist/api typecheck
corepack pnpm --filter @callassist/contracts test
```

Перед выпуском voice-изменения — полный соответствующий voice/authorization/
consent/transcript набор, typecheck и build затронутых пакетов. DB/integration
проверки, если требуются изменением, запускать только в выделенной одноразовой БД
через существующие isolated scripts. Сначала проверить их актуальный интерфейс;
не направлять тесты на рабочую или production БД.

Обязательные контрольные сценарии для voice diff:

1. Простой вопрос/ответ и завершение без appointment.
2. Чистое бронирование с известными фактами, один подтверждённый слот.
3. Два предложенных слота, выбран один; missing DOB; вопрос о первом визите.
4. Перебивание protected request и status-only recovery того же слота.
5. Неоднозначный ответ, отсутствие подтверждения, отказ, поправка даты/времени.
6. Оба consent режима, отрицание/коррекция ответа, ранний/поздний transcript,
   AMD inconclusive и recording failure.
7. Closing: шум, acknowledgement, существенная поправка, ошибки render/marks.
8. Command concurrency: late ACK/error, занятый backend, disconnect, timeout.

Сначала deterministic replay с контролируемым порядком событий и fake timers.
Для недетерминированного поведения модели — не менее пяти одинаково организованных
пар baseline/candidate на критический сценарий с фиксированными настройками и
отдельными результатами каждого прогона. Это ограниченная приёмочная выборка,
не статистическое доказательство production надёжности. Новые вариации/сбои
добавляются в набор; бесконечный повтор успешных проверок не нужен.

| Показатель | Условие допуска |
| --- | --- |
| Consent/authorization/duplicate booking | Ноль нарушений во всём наборе; любое нарушение блокирует выпуск |
| Успешность | Нет нового провала сценария, который baseline выполнял; причины расхождений разобраны |
| Речь/turn-taking | Нет новой потери вопроса, обрезанного opening, служебной реплики, лишнего повтора или пропущенной поправки |
| Latency | Для целевой паузы есть улучшение; для остальных этапов нет систематического ухудшения в paired run |
| Runtime waits | Нет новых timeout/deadline/fatal состояний, потерянных продолжений или параллельных владельцев |
| Closing | Нет преждевременного hangup; нет новой задержки/повтора; actual mark остаётся обязательным |
| Итог | Нет ложного achieved; подтверждённый слот не теряется из-за невыбранного offer |
| Затраты | Для B/C нет новых вызовов моделей; для D–F нет необъяснённого роста запросов |

В deterministic replay непредусмотренное дополнительное ожидание — дефект.
В живых прогонах до оценки candidate зафиксировать разброс baseline; повторяемый
рост задержки более чем на 1 секунду или 20% (что больше) на неизменяемом этапе —
триггер расследования и задержки выпуска, а не «допустимая регрессия». Более мелкое,
но заметное пользователю ухудшение также требует разбора. Не смешивать cold/warm
TTS, разные модели, сетевые условия и версии prompt. Не заявлять p95 по пяти звонкам.

## 6. Выпуск и откат

1. Первоначально фиксировался только план. Последующим поручением разрешена
   реализация A/B/C; её локальные результаты записаны отдельно. Production rollout,
   реальный звонок и пересчёт исторических результатов не выполнялись.
2. На этапе реализации сначала закончить локальный diff и доказательства, затем
   выполнять выпуск в рамках действующей авторизации пользователя и runbook.
   Сам документ не создаёт нового обязательного запроса разрешения для каждой правки.
3. Выпускать B и C независимо. D/E/F — по одному изменению поведения с собственным
   сравнением и обратимым release; не менять одновременно модель и управление сессией.
4. Первый разговор после voice patch — с согласованным тестовым получателем и
   синтетической задачей; не звонить повторно в клинику и не создавать реальную запись
   ради проверки. Внешние платные прогоны выполнять только в разрешённом объёме.
5. Подготовить возврат предыдущего приложения/конфига до выпуска; проверить
   совместимость старых artifacts и новых optional fields. Не вводить feature flags
   без нужды; если существующий переключатель подходит, зафиксировать его scope.
6. Не перезапускать сервис посреди активных звонков ради rollout/rollback:
   использовать предусмотренный runbook drain/допуск новых попыток. Аварийный
   инцидент обрабатывать по действующему operational runbook.
7. Откатить конкретное изменение при нарушении инвариантов, новом ложном успехе,
   повторной записи, потере поправки, существенном ухудшении речи/задержек или
   невозможности подтвердить корректность новой диагностики. Сохранить evidence.
8. Не откатывать историю реальной записи в клинике и не повторять её автоматически.
   Не переписывать feedback, assessment/transcript revisions и не пересылать результат
   владельцу повторно без отдельного решения о такой операции.

## 7. Что сознательно вынесено за рамки первых изменений

- Замена `gpt-live-1`, delegation-модели, TTS-модели или voice.
- Новый orchestration layer, automatic recording ASR, глобальная настройка VAD.
- Уменьшение таймеров только потому, что в одном разговоре была долгая пауза.
- Ослабление subsequent confirmation и защиты от повторной записи.
- Подавление gap/timeout telemetry ради «чистого» отчёта.
- Оптимизация compilation streaming, summary retry и billing reconciliation.
  Зафиксированные сбои остаются отдельными задачами, не смешиваются с voice patch.
- Автоматический пересчёт всех старых итогов или повторная отправка писем.
- Универсальное сокращение каждого уточнения: некоторые уточнения здесь
  правильно не позволили принять возможность бронирования за готовую запись.

## 8. Формат завершения каждого этапа

Заполнить отдельную запись реализации со ссылкой из этого документа:

- этап, статус и commit;
- воспроизводимый дефект и минимальное изменение;
- сохранённые инварианты и затронутые/незатронутые компоненты;
- команды проверок, результат, условия и ограничения;
- baseline/candidate измерения, если менялось live-поведение;
- сведения о контролируемой разговорной проверке, если она выполнялась;
- rollout/rollback и оставшиеся вопросы.

Пункт отмечается выполненным по проверенному результату, а не по наличию кода.
Начинать реализацию с A, затем B и C. Решение о D–F принимать по собранным
доказательствам; сохранение нынешнего рабочего поведения допустимо и предпочтительно
непроверенному «улучшению».

## 9. Продолжение после no-call smoke — состояние 2026-11-02

Два найденных backend-дефекта воспроизведены в полном in-memory runtime и
минимально исправлены в инструкциях/схеме tools. Закрыт локальный этап
«reproduce → fix → regression»: 22 сохранённых candidate outputs, 27 runtime
replays, итоговая регрессия 947 тестов. Подробная история вариантов и результатов
в [отчёте](voice-no-call-results-2026-11-02.md#продолжение-воспроизведение-и-минимальные-исправления).

Открыт допуск к выпуску: корректная production voice conversation с output fence,
оценкой слышимых реплик и end-to-end задержек. Ни этот replay, ни первоначальный
client-handoff smoke не закрывают этот пункт. Повторного звонка в клинику нет.
Общий резерв разрешённого бюджета $5 — $4.83; дальнейших платных запросов на
этом шаге нет. Сервисы не перезапускались, production не обновлялся.
