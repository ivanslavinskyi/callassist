В рамках этой проверки производственный код, настройки рантайма и рабочие данные не менялись; добавлены диагностические тесты и этот отчёт. Настоящие телефонные звонки не выполнялись.

## Вывод

Основная архитектура новой парадигмы реализована, но считать эксперимент целостным и стабильным пока нельзя. Открыты не только прослушивание и публичная бета: повторная проверка выявила воспроизводимые дефекты транспорта и завершения, зависание продолжений backend и несогласованные границы инструментов. Предыдущая формулировка готовности переоценивала завершённость P5/P6/P8.

Не требуется возвращаться к управлению каждым ходом со стороны приложения. Нужно довести небольшой слой транспорта, состояния действий и завершения; согласовать подготовку, Live и backend; затем проверить полный разговор с настоящей моделью и телефонным аудио.

## Что уже соответствует замыслу

- Отдельный `NativeLiveV2Call` запускает `gpt-live-1` с Responses delegation; backend по умолчанию `gpt-6-luna`. Это GPT-Live, а не перенос эксперимента на Realtime API.
- В выбранном v2 нет application TTS для вступления и обычного завершения, consent→task handoff и периодического принятия решения после каждого ответа. Старые методы остались в общем транспорте для совместимости, но native-сессии обходят task scheduler.
- Утверждение связывает первоначальную цель, контекст, факты, уточнения, подготовленный план и appendix. Обычные факты доступны сразу; appendix выдаётся только по существующему ID, не расширяет полномочия.
- Новая подготовка действительно заменяет старое вступление «после согласия»: проверен конечный system prompt после всех `.replace`, а не только исходные шаблоны. В нём нет инструкции считать дисклеймер уже произнесённым.
- Учтены язык, обращение, тон, выбранная причина помощи, имя и произношение, AI identity. Причина `none` не превращается в выдуманное объяснение.
- Завершение в Live и compiler относится к представляемому человеку, содержит главный результат, благодарность и прощание. Не требуется полный пересказ или дополнительный итог от backend перед речью.
- Реализованы book / confirm_existing / reschedule / cancel, существующая запись, условия, альтернативы, цена и время окончания. Подтверждение хранится как заявление собеседника, а не как независимо проверенная запись в календаре.
- Есть журнал действий с проверкой ревизии, идемпотентность, запрет слепого повторного бронирования и состояние неопределённости. `objective_resolved` для action-задачи требует confirmed.
- Запись начинается с соединения, отказ имеет приоритет, очистка защищена durable-состоянием и запретом поздних записей. Consent evidence не подделывается.
- Подробный trace вынесен в ограниченную асинхронную очередь и отдельный PostgreSQL pool: max 2, statement timeout 2500 ms. Сохраняются текст, инструменты и события, для аудио — агрегированные метаданные. Manifest отражает потери и незакрытую сессию.
- Readers исторических версий сохранены. Повторное чтение локальной копии production-истории прошло без ошибок.

## Воспроизведённые дефекты

В `.tools/native-consistency-audit-20261106/` сохранены тесты, логи и синтетические prompt snapshots. Тесты характеризации намеренно подтверждают существующее нежелательное поведение: их зелёный результат **не является приёмкой продукта**.

### A1. Незавершённый function call блокирует дальнейшие продолжения — высокий приоритет

Код: [live-conversation.ts](../../../apps/api/src/voice/live-conversation.ts), `#nativePendingCalls`, обработка `response.output_item.added`, terminal events и `#flushContinuations` (строки 855, 922, 993, 1029 на момент проверки).

Воспроизведение: первый response объявляет function call, затем заканчивается `response.incomplete`. Следующее независимое делегирование успешно вызывает `end_call`, результат отправляется через `response.item.create`, но `response.create` не отправляется. Незавершённый call ID остаётся в общем pending set. Положительный контроль без первого incomplete-response отправляет continuation.

Проблема не ограничена формулировкой prompt. `backendFailed()` в native controller только пишет trace и не задаёт дальнейший путь восстановления. Аналогичные terminal/timeout ветви требуют отдельного покрытия.

Исправление: учитывать незавершённые calls по response/delegation, явно завершать их жизненный цикл и иметь ограниченное восстановление. Нельзя просто очищать общий Set и считать провайдер готовым: требуется согласовать pending calls и допустимый continuation по протоколу. Не исполнять неполные аргументы и не повторять уже совершённое действие. Проверить incomplete до/после item.done, failed, cancelled, timeout, поздние terminal events и продолжение следующего задания.

### A2. Ответное «спасибо, до свидания» срывает нормальное отключение — высокий приоритет

Код: [native-live-v2-call.ts](../../../apps/api/src/voice/native-live-v2-call.ts), `transcript()` / `end_call`; [live-native-closing.ts](../../../apps/api/src/voice/live-native-closing.ts), `cancel()` / `request()`.

Воспроизведение: ассистент уже произнёс итог и прощание, end_call принят, отправлен playback mark. Собеседник отвечает «Thank you, goodbye». Controller отменяет closing и стирает сведения о произнесённом прощании. Повторный end_call принимается, но без ещё одной речи ассистента не может завершиться; через 30 секунд срабатывает `LIVE_NATIVE_CLOSING_TIMEOUT`.

Это противоречит инструкции не повторять прощание. Нужно различать подтверждение завершения и содержательное возобновление задачи, сохранять уже доставленный заключительный эпизод. Поправка даты, новый вопрос и отказ должны по-прежнему иметь приоритет. Семантику нельзя подменять списком слов «спасибо/пока».

### A3. Любая прежняя речь может считаться заключительным эпизодом — высокий приоритет

Код: [live-native-closing.ts](../../../apps/api/src/voice/live-native-closing.ts), `request()` берёт `#recent`, проверяя только `at > 0`.

Воспроизведение: поданы 100 ms голосового аудио и caption «One moment, I will check that». Через 10 секунд принят запрос завершения. После quiet tail, mark ACK и 350 ms guard observer сообщает `drained`, хотя итог/благодарность/прощание не поступали.

Это показывает недостаточность условия хоста, а не доказывает, что модель в каждом звонке вызывает инструмент преждевременно. Нужна связь end_call с конкретным заключительным эпизодом и его воспроизведением. Нельзя принимать за такую связь response.completed, любой caption или произвольную паузу. При этом уже произнесённый корректный итог должен оставаться пригодным после медленного backend-ответа.

### A4. Теряется входное аудио во время допуска потока — высокий приоритет

Код: [native-live-v2-call.ts](../../../apps/api/src/voice/native-live-v2-call.ts), асинхронный `#message(start)` и ветка `media && #admitted`.

Воспроизведение: искусственно задержано разрешение `transitionAnswering(...kind: admit)`. Два аудиопакета, пришедшие за это время, не доходят до Live и не воспроизводятся после допуска; следующий пакет проходит. В это окно входят обращения к repository и переходу состояния.

Нужна ограниченная очередь ранних пакетов с сохранением порядка и последующей передачей только после успешной проверки привязки. Отклонённый, чужой или просроченный stream не должен попадать в модель. Проверить медленную БД, немедленное приветствие человека, поздний start, повторное подключение и переполнение очереди. Это потенциальный источник потери первых слов собеседника; происхождение ранее услышанного пользователем обрыва ответа этим тестом не установлено.

### A5. Схема инструментов разрешает то, что транспорт отвергает — средний приоритет

Код: [native-appointment.ts](../../../packages/contracts/src/native-appointment.ts), [native-appointment-call.ts](../../../apps/api/src/voice/native-appointment-call.ts), [live-conversation.ts](../../../apps/api/src/voice/live-conversation.ts) строки 866/891.

Воспроизведено: schema-valid proposal с девятью разрешёнными цитатами по 2000 символов превышает транспортные 16 000 символов. Схема допускает до 24 таких условий, дополнительные альтернативы и quotes. Для result разрешены две цитаты по 8000, уже без учёта JSON envelope.

Нужен общий бюджет для schema, сериализованного tool payload и backend output. Для обычных действий сохранять компактные доказательства. Для очень сложных — ограниченные структурированные ссылки на наблюдения/условия, если это доказуемо сохраняет смысл. Не лечить проблему молчаливым усечением фактов или цитат; согласовать ошибки и восстановление, чтобы допустимый сложный сценарий не закрывал весь звонок.

## Промпты, backend и границы состояния

### B1. Backend budget и реальные API-пробы не совпадают

В рабочем [live-conversation.ts](../../../apps/api/src/voice/live-conversation.ts) задано `max_output_tokens: 512`, включая reasoning. Предыдущий `.tools/probe-native-actions.mjs` использовал 2048 и выполнял только подготовку плюс session.start→session.close. Он не исполнял delegated prepare/result/end_call.

Поэтому утверждение «4/4 API-пробы» доказывает допуск этих стартовых пакетов, но не достаточность 512 токенов для сложного действия. Это установленное расхождение проверки, а не экспериментально измеренная частота переполнений. В сочетании с A1 усечение особенно опасно.

Вынести backend configuration в один builder для рантайма и проверок; подобрать конечный бюджет по небольшим и максимальным допустимым действиям, reasoning и латентности. Не назначать число 2048 автоматически только потому, что оно было в старой пробе. Проверить и корректность, и incomplete-rate.

### B2. Live prompt следует упростить, сохранив полный стартовый контекст

Измерен фактический результат builder на синтетических задачах, совместимых с approval 7:

| Вариант | Live instructions | Backend instructions с данными | Startup JSON |
| --- | ---: | ---: | ---: |
| Информационный | 4575 символов / 677 слов | 2853 символа | 2033 байта |
| Простой appointment | 5423 символа / 789 слов | 5394 символа | 2327 байт |

Это не подсчёт токенов и не измерение задержки. Размер сам по себе не доказывает проблему, но Live получает подробную процедуру prepare→readback→record→status_check, повторённую в backend. При этом раздел Delegation содержит общее условие «careful reasoning or a tool», без явного перечня capabilities и полных рекомендуемых labels.

[Официальное руководство prompting](https://developers.openai.com/api/docs/guides/live-prompting) рекомендует короткую разговорную политику, подробный workflow в backend, конкретные условия делегирования, сохранение трёх policy headings и структуры Backend tools / Generate / Do not generate. Это рекомендация по prompting, а не ошибка схемы API.

Целевой Live prompt должен определять:

1. Кто звонит, кого представляет, язык/тон/обращение и источник утверждённых данных.
2. Краткое вступление, выбранную причину помощи, запись/транскрипцию, readiness и переход к цели.
3. Свободную беседу на основе данных; условное раскрытие фактов; реакцию на значимые перебивания.
4. Точный список доступных возможностей для этой задачи: окончание, отказ/удаление, optional appendix, разрешённая appointment operation.
5. Конкретные причины Generate `<|SpawnThinking|>`: действие, результат действия, существенная поправка к текущему действию, сложное рассуждение, отказ, завершение. Не делегировать известные факты, простые уточнения и обычные acknowledgments.
6. Короткий итог о представляемом лице, благодарность и прощание. Не объявлять успех неподтверждённого действия.

Полные факты и условия остаются в startup data. Сокращение поведенческой инструкции не означает сокращение пользовательского задания. Чисто технические процедуры проверки цены, альтернатив, журнала, result errors и recovery принадлежат backend/host.

### B3. Bootstrap вступления не совпадает с рекомендуемым рецептом

В `session.input` сейчас только user JSON; `NATIVE_V2_START` — отдельная общая англоязычная commentary после media admission. Developer message с теми же greeting instructions отсутствует. Native prompt требует readiness без явного исключения для человека, уже пригласившего продолжать или начавшего отвечать по делу.

Нужен один локализованный opening contract, общий для preview, startup и единственного запуска речи; явно учесть уже полученную readiness, перебивание дисклеймера и вопрос «по какому вопросу?». Для prewarm необходимо сохранить условие media-ready, чтобы вступление не прозвучало до подключения телефона. Нельзя механически добавить «начни немедленно» в pre-dial сессию.

Документированный рецепт — developer greeting в startup и однократная такая же commentary; ACK не доказывает произнесение. Если требуется точная обязательная формулировка уведомления, документация отдельно описывает instructions.append. Выбор проверяется на аудио; ещё один безусловный append может создать дубль или перебить речь. [GPT-Live sessions](https://developers.openai.com/api/docs/guides/live-conversations)

### B4. Воспроизведение действия не сообщается обратно ожидающему backend

`record_appointment_result` может вернуть `playback_pending` с указанием дождаться playback observation. У `NativeAppointmentCall.Ports` есть `changed`, но `NativeLiveV2Call` его не подключает. Mark ACK меняет журнал, однако backend не получает соответствующее обновление состояния. Он может узнать его только через последующую попытку инструмента.

Это установленный разрыв механизма уведомления, а не доказательство, что каждый быстрый ответ зависнет. Нужен событийный результат ожидания либо адресное обновление `actionId/episode/revision/status` на границе действия. Без опроса на каждом ходе, без повторного вопроса человеку и без новой речевой команды. Проверить раннюю реплику подтверждения, задержанный/старый mark, clear, отказ, отключение и конкурирующее делегирование.

### B5. Freshness пока привязана к фрагментам речи, а не к изменению задания

Каждый непустой input transcript delta повышает общий epoch. Нормальные prepare/result/end_call сравнивают epoch начала backend-run с текущим. Даже продолжение той же фразы или короткое подтверждение способно сделать результат устаревшим; ожидание acoustic silence не обновляет сохранённый epoch.

Такой консервативный барьер защищает от применения старой поправки, но может создавать лишние циклы в full-duplex беседе. Отдельно `record_appointment_result` требует `reply.start >= spoken.end`. Временные границы transcript-фрагментов не являются временем отдельных слов, поэтому быстрый ответ с перекрытием может быть отвергнут.

Нужно определить свежесть на границе конкретного действия/заключительного эпизода, не убрать её совсем. Сохранить запрет эффекта после существенной поправки или отказа, но дать модели естественно обрабатывать продолжение фразы и backchannels. Протокольные тесты должны подавать нарезанные и запаздывающие deltas, а не только законченные предложения с идеальными timestamps. Рекомендации по сборке текста и независимости transcript/playback: [GPT-Live sessions](https://developers.openai.com/api/docs/guides/live-conversations).

### B6. Ожидания в tool path и обработка отказов backend

Кроме A1, обычные native tools ждут response.completed и общей очереди `#writes`, включающей сохранение транскрипта и provider accounting. Исключение — приоритетный stop_and_discard, исполняемый уже на output_item.done. Обычная речь не ждёт этой очереди, но подготовка действия, фиксация результата и отключение — ждут.

Это место измерения и потенциальной оптимизации, а не разрешение убрать durable journal. Отделить необходимые записи до эффекта от необязательного accounting/телеметрии. Для ошибок определить исход «повторить безопасную проверку / сообщить неопределённость / завершить», вместо trace-only. Выполнение разрешённых calls уже после item.done допустимо при сохранении всех fences и идемпотентности; continuation должен учитывать каждый pending call. [GPT-Live delegation](https://developers.openai.com/api/docs/guides/live-delegation)

### B7. Остальные вопросы консистентности

- **Набор capabilities подготовки.** Подготовка сохраняет требования external delivery, runtime запрещает обещать недоступную отправку. Явно различить просьбу собеседнику отправить документ и обещание отправки самим ассистентом; проверить review/clarification, не объявлять все delivery-сценарии неработающими.
- **Цена и финансовые условия.** Общий compiler текст запрещает new financial terms, native authority допускает явно заданный maxTotalPrice. Разъяснить разницу между согласованной стоимостью услуги и разрешением оплаты/депозита; добавить отрицательные и положительные примеры.
- **Единый prompt composition.** Сейчас native compiler получается regex-заменами большого legacy prompt. На проверенном тексте старое consent-правило удалилось корректно. Для дальнейших изменений лучше явная композиция общих и версионированных native-блоков с тестом конечной инструкции.
- **Язык примеров.** Русское «Анна записана…» встроено в английскую инструкцию для всех локалей. Противоречие не доказано, но лучше локализованный пример либо универсальное правило субъекта, с проверкой неизвестного рода.
- **DTMF.** Общий `keypad()` трактует 1/2 как yes/no, хотя native вступление не предлагает такую механику; этот ввод не проходит через native `transcript()` и не даёт тех же observations. Решить, поддерживается ли DTMF в этом эксперименте, и согласовать обработку.
- **Размер startup.** Новая форма ограничивает context 4000 символами, старые данные читаются с прежними лимитами. Проверка session.start до набора номера — верный fail-closed барьер. Но общий максимум facts/context/plan не гарантированно укладывается в документированные 8192 токена input; нужны граничные задания и понятная ошибка до звонка. Не считать 120 KB локального byte-bound эквивалентом provider token budget.
- **Descriptor.** Есть compilationHash, promptHash Live, briefHash и локальный sourceDigest. Отдельные backend/tool/config hashes, budget и trace policy не закреплены явно, sourceDigest необязателен. В текущем локальном запуске digest установлен; при восстановлении и будущем rollout нужна проверяемая полная идентичность поведения.
- **Review UI.** NativeAppointmentDetails показывает операцию, интервалы, альтернативы, условия и price/finish limits. Общие ограничения maxAppointments=1 и financialPolicy в самом компоненте явно не показаны. Закрепить однозначное отображение объёма полномочий, особенно разрешённой стоимости без права произвести платёж.

## Порядок завершения

### 1. Закрыть воспроизводимые дефекты без расширения полномочий

A1 → A4 → совместно A2/A3. Для каждого заменить характеризацию дефекта на проверку правильного поведения в штатном наборе. Сохранить положительный контроль и отрицательные сценарии: чужой stream, correction, refusal, duplicate/late tool result, old mark. Не менять одновременно модель, голос и таймеры, чтобы видеть причину эффекта.

### 2. Зафиксировать один контракт подготовки, Live и backend

Составить общую таблицу capabilities и ошибок, построить короткие Live instructions, детальные backend instructions и локализованный opening из согласованных блоков. Данные задачи остаются полными. Проверить конечные prompts на native v2 и native actions, все assistanceReason, formal/informal, разрешённое переключение языка, нейтральный род, отказ на вопрос и отказ от разговора. Поднять версии изменённого поведения; старые утверждения и readers не переинтерпретировать.

### 3. Замкнуть действие и recovery

Уведомлять backend о необходимых границах playback/journal без polling. Согласовать размер tools и output budget. Разделить action authority, фактическую доставку речи и результат со слов собеседника. Сохранить status_check того же предложения и запрет отдельной отмены старого приёма при переносе. Проверить, что restored uncertain/confirmed state доходит до модели при восстановлении; одно наличие журнала этого не доказывает.

### 4. Прогнать настоящий Live→backend→host цикл на синтетических сценариях

Один builder конфигурации для runtime и harness. Проверять не только session.started: реальное делегирование, аргументы, результат, continuation и произнесённый итог. Набор: простой информационный ответ, все четыре appointment operations, условия/альтернативы/цена/finish deadline, неизвестные данные, недоступное действие, отказ, исправление после подтверждения, incomplete, ранняя/поздняя реплика. Фиксировать бюджет, incomplete-rate, stale/retry count и лишние delegations. Никаких внешних бронирований для этих тестов.

### 5. Парная локальная акустическая приёмка

Взять 10–15 фиксированных сценариев из P7/P8, повторить при одинаковой модели/голосе/телефонном маршруте. Сравнить с зафиксированным контролем. Раздельно измерить: соединение→первый звук; readiness→цель; конец содержательного ответа→итог; конец прощания→hangup. Прослушать начало и конец, не делать вывод по transcript. Не объявлять ускорение по числу удалённых проверок или зелёным unit-тестам.

Отдельно проверить «спасибо/до свидания», настоящий новый вопрос, кашель, короткий backchannel, подтверждение с перекрытием, раннее приветствие человека и медленную БД. Appointments остаются экспериментом с открытой P8-приёмкой; наличие опции в локальном рантайме не означает разрешение на публичный rollout.

### 6. Проверить эксплуатационное завершение

Trace load/backpressure, завершение записи/удаления, поздние callbacks, rollback для новых звонков без поломки новых readers и purge workers. После изменений повторить compatibility на исторической копии и новые schema 9/approval 8 fixtures. Бету рассматривать только после этих результатов.
