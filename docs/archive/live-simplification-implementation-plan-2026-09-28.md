# План упрощения и стабилизации Live

Дата: 28 сентября 2026. Статус: три пункта реализованы в рабочей копии; автоматические и ограниченные синтетические проверки выполнены. Production не обновлялся.

[Отчёт реализации и границы проверки](live-simplification-implementation-2026-09-28.md). Отметки ниже относятся к коду; разговорная матрица не объявляется полностью пройденной.

Основание: [аудит инструкций и последующие уточнения пользователя](live-prompt-audit-2026-09-28.md). Этот документ фиксирует следующий объём работ и заменяет открытые варианты из аудита. Исторические планы прежних Live-реализаций не являются дополнительным списком задач.

## Цель и выбранный подход

Стабилизировать существующие звонки и упростить создание плана. Live ведёт разговор, выбирает формулировки, учитывает ответы и решает, когда нужна помощь backend. Существующий managed Responses backend разбирает задачу и вызывает инструменты. Приложение исполняет реальные действия, управляет записью и доставкой аудио.

Реализация состоит из трёх пунктов:

1. Надёжное завершение звонка.
2. Достоверные реплики и упрощённые настройки плана.
3. Естественное вступление с вопросом об удобстве.

Не входят в работу: новая система оценок звонка, панели и метрики, классификация каждой реплики, собственный планировщик разговорных ходов, смена моделей/телефонии, новые каналы доставки результата, переписывание legacy Realtime. Не добавлять миграции БД ради удаления элементов формы.

Сохранить работающие функции: явное согласие и запуск записи, существующие языки и голоса, утверждение плана, ограниченные полномочия на встречу, защиту от повторного действия, расшифровку и итог, AMD/voicemail, учёт использования. Существующие незакоммиченные изменения не откатывать и не подменять исторической реализацией.

## 1. Надёжное завершение звонка

### Решение

Сохранить свободное прощание Live и существующий `LiveClosingSpeech`. Сузить его задачу до окончания произносимой реплики и подтверждения воспроизведения. Проверка прощания не решает заново, достигнута ли цель, и не оценивает допустимость будущих действий.

Это минимальное изменение текущей архитектуры. В Live WebSocket нет отдельного speech-done события. Поэтому удалять контроль завершения аудио и отключать по первой паузе нельзя. В нормальном пути остаётся одна проверка законченного прощания; новые проверки обычных реплик не добавляются.

### 1.1. Один источник команды на прощание

- [x] В `live-managed-tools.ts` сохранить небольшой контракт `end_call({ reason })`: без recap, списка доказательств от модели и текста обязательного прощания.
- [x] Сохранить серверные проверки текущего состояния и необходимых подтверждений встречи.
- [x] После принятия `end_call` вернуть фактический результат `closing_authorized` и выполнить обычный managed function-result цикл: `response.item.create`, затем `response.create`.
- [x] Backend должен закончить эту делегацию кратким фактическим результатом, без второго инструмента, речевого сценария, приветствия и собственного прощания.
- [x] В основном Live-промпте задать единственное правило: после разрешения backend естественно завершить разговор; кратко подтвердить полезный результат, только если это ещё нужно; попрощаться и затем слушать до отключения.
- [x] Удалить конкурирующую команду `Finish naturally now` из `UnifiedLiveCall.#requestClosing()`. Приложение здесь включает контроль вывода, а не запускает ещё один разговорный ход.
- [x] Не запускать проверку неполного acknowledgment, пока ожидается продолжение принятого `end_call`. Использовать уже отслеживаемый lifecycle соответствующей backend-делегации; его завершение разрешает проверку, но не заменяет доказательство воспроизведения аудио.
- [x] Ошибка этого backend-продолжения должна попадать в существующий ограниченный путь завершения с ошибкой, а не игнорироваться из-за `phase === closing`.

Таким образом обычное подтверждение вроде «понял» может прозвучать до завершения backend, но не считается законченным прощанием и не запускает преждевременное отключение.

### 1.2. Упростить смысл проверки

- [x] В `live-semantic-gate.ts` удалить из closing policy общий запрет на объявление дальнейшей работы.
- [x] Проверять только: закончена ли реплика прощания, нет ли незаконченной фразы, вопроса или явного ожидания ответа/продолжения текущего разговора.
- [x] Не добавлять сюда план, бизнес-правила, оценку достоверности обещаний или повторное определение результата звонка. Достоверность обеспечивается контекстом и инструкциями пункта 2.
- [x] Сохранить проверку актуальности вывода и уникальный Twilio mark. Новое исходящее аудио или отмена воспроизведения делают старое подтверждение непригодным для отключения.

### 1.3. Убрать тупик отрицательного решения

| Результат | Действие приложения |
| --- | --- |
| Завершённое прощание (`equivalent`) | Дождаться актуального playback mark и завершить звонок |
| Реплика продолжается (`incomplete`) | Продолжить принимать речь; проверить обновлённую реплику после её остановки, без повторного запроса по тому же тексту |
| Ассистент явно ждёт ответа (`different`) | Снять ожидание отключения, вернуть управление текущей беседой Live; следующий end_call будет новым разрешением |
| Проверка недоступна/неопределённа либо завершение не продвигается | Одна короткая завершающая реплика через существующий механизм controlled speech, затем playback mark и отключение |

- [x] Восстановление ограничить одной попыткой на один непрерванный цикл закрытия. Использовать `#say`/`LiveControlledSpeech`, не создавать отдельный recovery-controller.
- [x] Аварийная завершающая реплика содержит только вежливое прощание на языке звонка. Она не повторяет результат и не обещает действий. Обычно этот путь не вызывается.
- [x] Для этой известной короткой реплики использовать проверку полного ожидаемого текста и playback mark без нового сетевого классификатора. Если воспроизведение не подтверждено, ограниченно завершить технический сбой, не отмечая его успешным прощанием.
- [x] Удалить нынешнее поведение «получили отрицательное решение и молча ждём остаток 30 секунд». Имеющийся общий дедлайн оставить только последним пределом, не штатным выходом после отказа проверки.
- [x] Не более одного запроса проверки одновременно. На непрерванное прощание — максимум две проверки реально изменившегося текста, включая отменённые запросы; затем один ограниченный fallback. Начальные значения оставить рядом с существующим контроллером: 700 мс для кандидата на окончание, до 6 секунд для проверки, 3 секунды сверх рассчитанной очереди для playback mark. Fallback ограничить 8 секундами; его запуск не продлевает общий дедлайн закрытия.
- [x] Если проверка вернула `incomplete`, а нового текста/голоса нет 2 секунды после результата, перейти в единственный fallback. Новая реплика не должна создавать проверку по прежнему содержимому.

Это не гарантия идеального распознавания любого аудио: короткий fallback — явный компромисс для технического отказа. Его роль — завершить звонок без длинной немой паузы, а не перепроверить беседу ещё одной моделью.

### 1.4. Прерывания

- [x] Сохранить немедленную отмену pending hangup и старого playback mark при входном голосе: нельзя оборвать поправку собеседника.
- [x] Убрать из автоматической инструкции предположение, что любой звук является correction/question. Передавать Live только факт отмены закрытия и требование учесть услышанное.
- [x] Live различает «спасибо», вопрос и поправку в контексте. Никакого отдельного классификатора благодарностей или словаря фраз.
- [x] После существенной поправки — продолжить текущую задачу и запросить новое разрешение завершения. После благодарности — не перезапускать задачу и не повторять длинный итог; допустим короткий естественный ответ.
- [x] Поздний результат старого backend/классификатора и mark от очищенной очереди не закрывают возобновившийся разговор.

### Файлы и критерии готовности

Основные файлы: `apps/api/src/voice/live-conversation.ts`, `live-managed-tools.ts`, `unified-live-call.ts`, `live-closing-speech.ts`, `live-controlled-speech.ts`, `live-semantic-gate.ts` и их существующие тесты.

Готово, когда последний воспроизведённый сценарий завершается без прежнего таймаута; все результаты проверки имеют ограниченный выход; прощание не обрывается; managed continuation не порождает вторую конкурирующую речь; поправка отменяет старое отключение; отказ проверки не запускает цепочку модельных перепроверок.

## 3. Естественное вступление с вопросом об удобстве

### Решение

Сохранить вопрос об удобстве как разговорную инструкцию, а не обязательный дословный текст, который приложение должно распознать и одобрить. Разделить обязательное согласие на запись и обычное вступление по цели.

### 3.1. Согласовать компилятор и представление плана

- [x] В compiler prompt убрать требование снова представлять инициатора после disclosure. Его имя уже названо до согласия.
- [x] Описывать цель кратко, без повторного приветствия, анонса списка вопросов и комментариев о внутренних процедурах.
- [x] На этом этапе сохранить форму объекта `opening` для совместимости. Его поля — предложенные формулировки для preview/legacy, а не обязательный сценарий native Live. Не добавлять новый параллельный объект opening policy в БД.
- [x] `readinessQuestion` в сохранённом плане может оставаться примером, но native runtime не должен произносить его через exact-speech и не проверяет совпадение.
- [x] В preview убрать обещание дословного воспроизведения, если такое есть. Условия и цель остаются предметом утверждения пользователя.
- [x] Обновить версию компилятора по существующей схеме версионирования. Новые правила применяются к новым компиляциям, старые snapshots не пересчитываются массово.

### 3.2. Передать разговорный переход Live

Целевая инструкция:

> После согласия на запись и подтверждённого запуска записи кратко объясни цель, не повторяя представление. Спроси, удобно ли сейчас поговорить, и дождись ответа. Если собеседник уже явно предложил продолжать или сразу отвечает по цели звонка, продолжай без повторного вопроса. Если ему неудобно, уважительно заверши разговор. Выбирай естественную формулировку на языке звонка и соблюдай установленное обращение.

- [x] После успешного `startRecordingAfterConsent` включить task context/backend и передать эту краткую инструкцию одним переходом.
- [x] Удалить для native Live вызов `#say()` со склейкой `recipientAddress + purposeStatement + readinessQuestion` и зависимость допуска обычного разговора от playback mark этой склейки.

## Порядок реализации

1. **Контекст и настройки из пункта 2.** Сначала нормализация, compiler и проекции; затем форма и совместимость. Это устраняет причины выдуманных обещаний до изменения закрытия.
2. **Вступление из пункта 3.** Убрать конфликтующие обязательные формулировки и проверить переход consent → recording → conversation.
3. **Завершение из пункта 1.** Согласовать native continuation, сузить проверку и добавить один ограниченный выход из сбоя. Проверить вместе с новым вступлением и правилами речи.
4. **Один итоговый прогон и документация.** Обновить актуальное описание runtime, сверить форму и провести разговорные проверки. Это этап приёмки трёх пунктов, не четвёртая продуктовая функция.

Каждый пакет должен быть обозримым diff. Не откладывать исправление обнаруженной регрессии до финального прогона. Если native continuation требует добавления нового планировщика или проверок каждого хода, остановить расширение решения и пересмотреть сам конфликт инструкций; дополнительный orchestration framework не входит в этот план.

## Проверка реализации

### Автоматические проверки на существующей базе

| Область | Существенные проверки |
| --- | --- |
| Defaults/роли | user/admin получают neutral/formal, superadmin override сохраняется; скрытые draft-значения не влияют; idempotency использует одинаковый нормализованный вход |
| Совместимость | Старая история читается; deliveryInstruction не теряется/не дублируется; новая копия не использует старый hash после изменения |
| Контекст | Live получает условия и ограничения; хранение в приложении не превращается в обещание внешней передачи |
| Opening | Нет exact-speech проверки обычного вступления; consent/recording gate сохранён; immediate answer не теряется; assistanceDisclosure сохранён |
| Closing | Все решения проверки имеют выход; нет повторной проверки прежнего текста; одна recovery-попытка; stale/cleared mark не завершает звонок; backend continuation не создаёт второе закрытие |
| Existing actions | Встреча остаётся в пределах разрешения; требуется последующее подтверждение; прерывание/повтор инструмента не создают повторную договорённость |

Использовать существующие unit/integration harnesses. Моки проверки прощания подтверждают переходы кода, но не качество решения реальной модели. Не выдавать их за доказательство естественной речи.

После локальных проверок изменённых пакетов выполнить один полный релевантный прогон workspace tests, typecheck/lint и build. Не повторять полный прогон без новых изменений или ошибок. Проверить форму на обычной и superadmin-роли, на узком экране и в основных UI-языках. Не добавлять snapshot-тесты каждой строки текста ради покрытия.

### Небольшая разговорная приёмка

Использовать существующие Live probes и разрешённые тестовые звонки. Не создавать новую платформу eval. Начать с русского и немецкого, затем кратко проверить остальные доступные языки звонка на общих правилах и локализованном fallback.

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Простой информационный ответ | Естественное acknowledgment допустимо; нет выдуманной передачи/заказа; короткое завершение |
| Несколько вопросов и условие | Live учитывает обязательные пункты и условный follow-up, не завершает после первого ответа |
| Передача нейтрального сообщения | Передаётся содержание задачи; не появляется обещание последующего контакта |
| Просьба к собеседнику отправить документ | Сохраняются исполнитель, адресат и условия; ассистент не заявляет о своей отправке |
| Встреча | Нет заявления о бронировании до необходимого результата; сохранены существующие границы полномочий |
| «Не знаю» или отказ | Не выдумывается результат; разговор заканчивается уважительно |
| «Удобно» / «неудобно» / ответ сразу по цели | Нет повторного представления; вопрос готовности не превращается в жёсткий дополнительный опрос |
| Благодарность при прощании | Нет перезапуска задачи и длинного повторного итога |
| «Подождите, я ошибся» при прощании | Отключение отменяется, поправка учитывается, старый mark не действует |
| Ошибка/неопределённость closing check | Нет прежней немой паузы до 30-секундного timeout; срабатывает единственный ограниченный выход |

Последний реальный сбой использовать как регрессионный пример, но проверять то же правило на других темах. Отдельно различать текст native transcript и реально услышанное в телефоне. Звучание, отсутствие обрыва и паузы проверяются по аудио/живому звонку, не только по тексту.

## Источники проектных решений

- [Prompting GPT-Live](https://developers.openai.com/api/docs/guides/live-prompting): короткий разговорный prompt, естественные формулировки и acknowledgments, отдельная delegation policy.
- [Delegation and tools](https://developers.openai.com/api/docs/guides/live-delegation): managed Responses, функция → результат → продолжение backend, разделение инструкций и фактов.
- [Managing sessions](https://developers.openai.com/api/docs/guides/live-conversations): управление контекстом, disclosure и отличие acknowledgment команды от воспроизведения.
- [WebSockets](https://developers.openai.com/api/docs/guides/voice-websockets?api=live): непрерывное аудио и отсутствие отдельного события конца голосовой реплики.

Выбранные лимиты recovery и изменения формы — проектные решения Callassist, а не требования OpenAI. Их проверяют при реализации. Фактический объём и результаты реализации указаны в связанном отчёте; полный разговорный и акустический приёмочный прогон остаётся отдельным шагом.
