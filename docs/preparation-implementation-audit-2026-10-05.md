# Повторный аудит задержек подготовки плана

Исторический аудит до реализации масштабируемой подготовки. Выводы и ссылки на
номера строк ниже относятся к указанной базе, не к текущему main. Последующая
реализация описана в [runtime](preparation-runtime.md): освобождение тел,
cooldown/deadline handling, SSE и ролевые workers уже реализованы. Этот документ
сохраняет исходные доказательства, а не список всех текущих дефектов.

Дата: 2026-10-05. Проверен исходный код на базе `6d82c9b`, предоставленный
экспорт и локальное воспроизведение поведения. Код приложения при аудите
не менялся. Это аудит задержек и восстановления подготовки, не повторная
полная сертификация всех правил безопасности планов.

## Вывод и пересмотр приоритетов

Для устранения рассмотренной задержки полный предыдущий план избыточен
как обязательный первый этап. Данные не указывают на недостаток воркеров:
очередь заняла 0,131 секунды. Главный вклад — один запрос генерации,
прерванный нашим таймером на 35 секундах, и следующий успешный запрос на 7 секунд.

Обнаружены три конкретных дефекта обработки сбоев и один усилитель повторной
работы. Они требуют небольших целевых изменений и тестов. Однако ни один
из них не доказан как причина отсутствия первого ответа в этом инциденте.
Причина исходного ожидания всё ещё неизвестна; нельзя объявить найденную
утечку тела ошибки объяснением случая, где HTTP ошибка вообще не приходила.

Рекомендуемый первый этап: исправить освобождение HTTP ответов, обработку
Retry-After и границы ожидания БД; дополнить существующие метаданные запроса
и проверить фактический service tier. Если после этого задержка сохраняется,
добавить ограниченную потоковую диагностику только генерации. Админка моделей
и Fast mode остаются отдельным продуктовым улучшением; масштабирование —
отдельной работой по измеренной очереди и конкурентной нагрузке.

## Подтверждённые дефекты

### Ошибочный HTTP ответ не освобождается

При `response.ok === false` compiler не читает и не отменяет `response.body`.
Таймер запроса к этому моменту очищается, после чего запускается следующая
попытка. Незавершённое тело старого ответа остаётся открытым.

Код: `apps/api/src/brief-compiler/brief-compiler.ts:509`, `:552`, `:558`.
Локальное воспроизведение использовало настоящий Node fetch и HTTP сервер
на loopback: первый ответ 503 отправлял заголовки и незавершённое тело,
остальные запросы успешно завершали подготовку. К моменту готовности плана
первый ответ всё ещё не был закрыт клиентом.

Это может увеличивать количество занятых соединений и мешать их переиспользованию
после ошибок. Undici прямо требует читать или отменять тело ответа;
полагаться на сборщик мусора для освобождения соединения нельзя.
[Документация Undici](https://github.com/nodejs/undici#garbage-collection).

Исправление: явно отменять ненужное тело или ограниченно читать необходимые
поля ошибки в пределах дедлайна, гарантируя освобождение во всех ветках.
Не начинать неограниченное чтение тела 503 в качестве исправления.
Правильный локальный образец уже есть:
`apps/api/src/text-processing/openai-text-processor.ts:117`.

Отношение к инциденту: дефект подтверждён, но в рассматриваемой подготовке
ошибочный HTTP ответ не наблюдался. Поведение других запросов процесса
до этого окна неизвестно, поэтому связь не доказана.

### Retry After игнорируется при повторе

После 429, 408, 409 и 5xx выполняется немедленный transport retry;
`Retry-After` не разбирается и не передаётся в durable scheduler.
Если обе попытки неудачны, следующая попытка worker использует обычную
экспоненциальную задержку, начинающуюся с 5 секунд.

Код: `apps/api/src/brief-compiler/brief-compiler.ts:573`, `:990`,
`apps/api/src/call-service.ts:1600`, `apps/api/src/jobs/durable-job.ts:100`.
Проверка с HTTP 429 и `Retry-After: 30` зафиксировала два запроса на одной
и той же отметке тестовых часов вместо ожидания 30 секунд.

При реальном ограничении квоты такие повторы расходуют бюджет и создают лишнюю
нагрузку. Особенно заметно это станет при нескольких одновременно работающих
подготовках. Исправление: учитывать срок провайдера и небольшой jitter,
передавать ожидание scheduler, не занимая serial lane долгим sleep.
Если повтор не помещается в оставшийся срок подготовки, завершать её
предсказуемо, не отправляя заведомо преждевременный запрос.

Уже существуют `parseTextRetryAfter` и `DurableJobExecutionError.retryAfterMs`.
Для исправления не нужен новый распределённый планировщик. При решении
переносить повтор в worker нужно отдельно учитывать повторение всей генерации,
описанное ниже.

Отношение к инциденту: HTTP 429 не было; это профилактика усиления сбоев,
а не объяснение первого 35-секундного ожидания.

### Общий дедлайн не прерывает ожидание БД

`beforeProviderRequest` ожидается до создания AbortController, а
`afterProviderRequest` ожидается без собственной границы времени.
Абсолютный срок проверяется между запросами, но сам по себе не прерывает
зависший callback. Пул call repository задаёт `max: 10`, без локальных
`statement_timeout` и `lock_timeout` для этих транзакций. Ограничения роли
или сервера PostgreSQL в этом аудите не получены.

Код: `apps/api/src/brief-compiler/brief-compiler.ts:465`, `:494`, `:1033`;
`apps/api/src/storage/postgres-call-repository.ts:581`, `:1252`, `:1848`.

Два воспроизведения:

- При deadline 1 секунда незавершённый reservation callback удерживал compiler
  и через 121 секунду тестового времени; внешний запрос ещё не отправлялся.
- Если запись результата финальной moderation занимала 2 секунды при deadline
  1 секунда, compiler возвращал успешную компиляцию после этого срока.

Это означает, что 120 секунд сейчас не являются жёсткой верхней границей всего
серверного пути. В единственной линии подготовки долгое ожидание БД также
задерживает следующих пользователей. Heartbeat может продолжать продлевать
lease, если для него БД доступна, поэтому lease timeout не заменяет deadline.

Исправление: определить ограниченные сроки ожидания пула, блокировок и SQL
операций в пути подготовки; применять SQL cancellation/rollback и проверку
актуальности публикации. Простого Promise.race недостаточно: он может оставить
транзакцию исполняться после того, как приложение считает её отменённой.
Финансовое резервирование и публикация должны сохранить идемпотентность.

Отношение к инциденту: резервирования здесь занимали 5–58 мс, общий остаток
локального времени мал. Дефект не объясняет измеренную задержку.

## Усилители задержки и ограничения диагностики

### Поздний сбой запускает всю подготовку заново

Compiler выполняет цепочку input moderation → generation → language audit →
output moderation. Успешный кандидат хранится в памяти до окончания цепочки.
Если финальная moderation не проходит обе transport попытки из-за временной
ошибки, durable retry вызывает `compile()` снова с самого начала.

Код: `apps/api/src/call-service.ts:1531`, `:1600`;
`apps/api/src/brief-compiler/brief-compiler.ts:201`, `:305`.
Проверка настоящего CallService с in-memory repository и подставным HTTP
транспортом дала последовательность из 9 внешних операций: пять в первой
попытке с двумя 503 на финальной проверке и четыре во второй. Генератор и
проверка языка отработали дважды, хотя их первый результат был пригодным.

Это текущая гранулярность восстановления, а не доказанная причина данного
инцидента. Сохранение кандидата по стадиям может убрать лишнюю генерацию,
но потребует связать его с input, compiler version и lease, шифровать и удалять
по существующим правилам. Поэтому такой checkpoint не включать автоматически
в самый маленький transport fix; сначала оценить частоту именно поздних сбоев.
Обязательную финальную проверку пропускать нельзя.

### 35 секунд являются нашей границей наблюдения

`defaultGenerationRequestTimeoutMs = 35_000` и AbortController в compiler
создают код `OPENAI_RESPONSE_TIMEOUT`. Этот код не является ответом OpenAI
и не доказывает, что провайдер сам отказал по таймауту.

Код: `apps/api/src/brief-compiler/brief-compiler.ts:32`, `:495`, `:533`.
В тестовом сценарии первый исправный ответ был готов через 36 секунд,
но compiler отбросил его на 35-й секунде и получил результат повтора только
на 42-й. Это подтверждает возможность усиления задержки выбранным порогом,
но не означает, что реальный прерванный запрос завершился бы на 36-й секунде.

Слепо повысить таймаут до 60 секунд — значит дольше ждать настоящие зависания.
Слепо снизить — значит чаще отбрасывать нормальные медленные ответы.
Нужны наблюдения прогресса и распределения задержек с учётом прерванных запросов.
Переключение таймаута само по себе не установит исходную причину.

### Service tier не фиксируется явно и не сохраняется

В payload генерации отсутствует `service_tier`; в сохранённом результате
нет фактического tier ответа. По OpenAI API отсутствие этого параметра
означает `auto`, то есть обработку согласно настройке проекта; обычное значение
проекта по умолчанию — `default`.
[Параметры Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create).

Код: `apps/api/src/brief-compiler/brief-compiler.ts:375`, `:582`.
Проверить настройку проекта и сохранять фактический tier — небольшой шаг,
который полезен до построения админки. Если выбран Standard, его следует
фиксировать явно. Доказательств, что текущий проект использует Flex или другой
режим, нет; это проверяемая неизвестная, а не найденная причина.

### Последовательная очередь усиливает чужую задержку

Один процесс сейчас выполняет один `brief_compilation` за раз. Если один
пользователь ждёт провайдера 35 секунд, следующий может ждать свободную линию.
При этом другие типы jobs уже разделены по линиям; транскрипция не занимает
ту же линию, что генерация плана.

Код: `apps/api/src/jobs/durable-job-worker.ts:180`,
`apps/api/src/call-service.ts:239`. В данном trace очередь была короткой.
Сначала нужно измерить её при одновременных подготовках. Если она станет
основной проблемой, начать с ограниченного числа слотов в одном процессе
и тестов конкурентности. Размножение полного worker опаснее: его initialize
вызывает восстановление звонков и создаёт дополнительные пулы.

### Проверка десяти одновременных подготовок

После вопроса о конкурентной нагрузке дополнительно проверен текущий CallService
с одним worker, десятью разными пользователями, in-memory repository,
реальным compiler и управляемыми задержками подставного HTTP транспорта.
Все подготовки созданы одновременно, общий срок каждой — 120 секунд.
Входная moderation, language audit и выходная moderation занимают по 1 секунде;
генерация занимает указанную долю полного времени. Repairs отсутствуют.

| Сценарий | Успешно | Ошибки | Публикация последнего успешного плана |
| --- | ---: | ---: | ---: |
| 10 с на весь план, генерация 7 с | 10 | 0 | 100 с |
| 14 с на весь план, генерация 11 с | 8 | 2 | 112 с |
| Обычно 10 с на план, но первая генерация сначала ждёт таймаут 35 с | 8 | 2 | 115 с |

Ошибки последних подготовок вызваны истечением оставшегося срока выполнения.
Это доказывает ограничение serial lane при такой форме нагрузки, но не измеряет
производительность VPS или OpenAI. Звонки и перевод для просмотра в этот
синтетический прогон не включены. Файл проверки:
`.tools/runtime/preparation-concurrency-2026-10-05.test.ts`.

Если десять одновременно пришедших подготовок являются целевой нагрузкой,
ограниченная параллельность подготовки нужна отдельным ближайшим этапом.
Устранение причин индивидуальных задержек само по себе этого ограничения
не решает. Начинать можно с нескольких слотов текущего процесса и проверки
очереди, общего request budget и ресурсов; внедрение всей схемы нескольких
ролей и хостов для первого увеличения параллельности не обязательно.

В production режиме external голосовые сессии обслуживает процесс API;
они не занимают compile lane. Переводы планов, summaries и другие текстовые
артефакты делят отдельную последовательную линию worker. Поэтому после
завершения нескольких разговоров review новых планов может ждать за summaries.
Процессы разделены, но CPU, память хоста, PostgreSQL, денежный бюджет и
применимые квоты провайдеров общие. Гарантия отсутствия влияния требует
совместной нагрузочной проверки, которой здесь не было.

Для звонков действует один активный разговор на пользователя, глобальный
`maxConcurrentCalls` из beta controls и проверка бюджетов при старте.
Десять одновременных звонков требуют разных пользователей, подходящего
значения этого лимита и доступного бюджета; настройка лимита не подтверждает
аппаратную ёмкость. Источники: `apps/api/src/storage/postgres-call-repository.ts:4833`,
`:4964`; `apps/api/src/index.ts:59`; `apps/api/src/call-service.ts:192`.

## Какие простые объяснения не подтвердились

| Гипотеза | Что проверено |
| --- | --- |
| Скрытый sleep перед генерацией | В критическом участке его нет; временная шкала сходится с HTTP ожиданиями |
| Периодический таймер очереди на 35 секунд | Poll worker 1 с; 35 с принадлежат таймеру HTTP попытки |
| SDK делает незаметные повторы | Здесь прямой Node fetch, OpenAI SDK в пути нет; повторы явно написаны в compiler |
| Ожидание транскрипции в общей линии | Для compiler выделена отдельная линия |
| Браузер добавляет 35 секунд | Poll после 10 секунд идёт каждые 2 с; основной интервал уже измерен на сервере |
| Долгий DB reserve в инциденте | Наблюдаемые резервирования 5–58 мс |
| Повторная генерация из-за качества | В данном случае `repairNumber = 0`; повтор был транспортным |
| Каждый запрос получает новую схему генерации | Схема генерации — константа; динамична схема language audit, который здесь прошёл за 1,34 с |
| Поломанный prompt cache | Успешный повтор почти целиком cached; исходный запрос не имеет usage, поэтому его cache state неизвестен |
| Сервер обязательно генерирует 20 тысяч токенов | Это верхний лимит; успешный повтор выдал 416, а расход прерванного запроса неизвестен |

`max_output_tokens: 20_000` велик для простого плана, но по имеющейся выборке
нельзя доказать, что именно он вызывает ожидание. Снижать его следует по
распределению полных успешных ответов, включая сложные сценарии и reasoning,
иначе появятся incomplete ответы и новые repairs. Сам prompt уже просит
компактный JSON, а reasoning и verbosity установлены в low.

## Уменьшенный объём первого изменения

1. Перенести проверенные приёмы HTTP обработки из text processor в compiler:
   освобождение тела ошибки, bounded чтение ответа и разбор Retry-After.
   Добавить поведенческие regression tests для этих веток.
2. Ограничить ожидание БД и проверить deadline перед публикацией с безопасной
   отменой SQL. Не считать истечение таймера доказательством rollback.
3. Расширить существующие `request_metadata` и `response_metadata`: requested
   и actual tier, настройки генерации, версия кода/профиля, bounded error code,
   Retry-After и время сохранения результата. Сохранить совместимость старых
   записей и существующее ограничение 2048 байт на объект. Отдельную систему
   хранения и таблицу на каждый токен не создавать.
4. Проверить настройку service tier проекта. На новых случаях сопоставлять
   этап, transport attempt, worker attempt, очередь и границу таймаута.
5. Если этих данных мало, включить за флагом SSE только для генерации и repair:
   сохранить ранний response ID, первое событие, первый output и terminal status.
   Оставить окончательную публикацию после всех проверок. Это ограниченная
   диагностическая работа, независимая от админки и масштабирования.

После этого выбирать дальнейший шаг по результату:

| Наблюдение | Следующий шаг |
| --- | --- |
| БД или локальная очередь доминирует | Исправление конкретной блокировки или ограниченное увеличение слотов |
| Ответ приходит, но генерация долго продолжается | Сравнение модели, reasoning, Fast и размеров ответа на наборе качества |
| Нет раннего ответа при быстрой локальной отправке | Сопоставление client request ID у провайдера и проверка сетевого пути; ранний ID может отсутствовать даже со streaming |
| Много 429 или 5xx | Корректное ожидание, общий бюджет запросов и квот; дополнительные воркеры способны ухудшить ситуацию |
| Сбои сосредоточены на поздних проверках | Возобновление с сохранённого кандидата вместо полной повторной генерации |
| Растёт конкуренция пользователей и очередь | Этап ёмкости из большого плана с ограничениями БД и защитой звонков |

## Выполненная проверка и её пределы

Прошли 214 существующих тестов в 12 файлах: compiler, его таймауты и диагностика,
создание compiler из env, durable worker, CallService, language audit,
workflow перевода, text processor, клиентский API, сохранение подготовки
и отображение её времени. Дополнительно прошли 6 локальных audit probes
и 3 сценария очереди для десяти пользователей. Итого 223 теста в 14 файлах.

Audit probes сохранены в игнорируемом файле
`.tools/runtime/preparation-latency-audit-2026-10-05.test.ts`. Они фиксируют
текущее поведение, включая дефекты, и не должны стать regression tests
с ожиданием этих дефектов после исправления. При реализации ожидаемые
результаты нужно заменить на правильное поведение и перенести проверки в suites.

Команда запуска probes из корня репозитория:

```text
node apps/api/node_modules/vitest/vitest.mjs run --config apps/api/vitest.config.ts .tools/runtime/preparation-latency-audit-2026-10-05.test.ts
```

Локальная среда: Windows, Node v24.9.0; предоставленная версия Node на VPS —
v22.23.2. Реальный сетевой probe обращался только к loopback. Проверка
повторного запуска CallService использовала in-memory repository; отсутствие
SQL timeouts установлено по коду, не экспериментом с production PostgreSQL.
Живые запросы к платному API и нагрузочные тесты VPS не выполнялись.

Поэтому аудит позволяет сузить работу и воспроизводимо исправить несколько
дефектов, но не назвать точную причину первого медленного ответа OpenAI.
