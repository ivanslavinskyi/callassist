# План: единый транскрипт, естественные реплики и быстрое завершение Live

Дата: 28 сентября 2026. Статус: реализован на текущей ветке; локальные миграции и CMS-публикации применены. Фактические изменения, уточнение контракта времени, результаты проверок и оставшаяся приёмка описаны в [отчёте реализации](live-transcript-implementation-2026-09-28.md). Чеклист ниже сохранён как исходная спецификация. Production не обновлялся.

Это отдельный следующий этап после [реализованного плана упрощения](live-simplification-implementation-2026-09-28.md). Он состоит ровно из трёх продуктовых пунктов. Миграции, CMS, переводы, PDF, проверки и выпуск входят в эти пункты и обеспечивают их согласованность.

## Основание и границы

В звонке 28 сентября, 18:39:58–18:40:53 Europe/Zurich, использовались Live, compiler 6, neutral/formal и новый механизм завершения. Нативная расшифровка сохранила один ответ, повторная расшифровка записи — другой, включая отсутствующую в первой версии неуверенность. Пользователь подтвердил, что Live-транскрипт точнее. Ошибка повторного распознавания попала в итоговое резюме. Аудио в ходе исследования независимо не прослушивалось.

В репликах ассистента остались «проверю ваш ответ» и «проверю дальнейшие шаги». При этом согласие принято с первой попытки, запись началась после согласия, `end_call` принят один раз, одна closing-проверка завершилась успешно и отключение произошло по playback mark. От принятия `end_call` до playback_complete — 6,797 с; closing-проверка — 1,922 с. Первое число включает речь, backend и проигрывание, а не измеряет тишину.

Цель: сохранить правильно распознанный разговор через всю цепочку результата и сделать речь естественнее, используя штатный Live. Не создавать сравнение двух моделей на каждом звонке, отдельный арбитр транскриптов, новую систему оценки качества, оркестратор каждого разговорного хода или новую панель метрик. Не обещать безошибочность Live. Legacy Realtime и реальный резервный путь распознавания записи сохраняются.

### Что установлено в коде

| Область | Текущее состояние и следствие для реализации |
| --- | --- |
| Сохранение Live | `live-conversation.ts` пишет отдельные фрагменты с session/event ID и временем с начала сессии. После `close()` общий `#closing` прекращает обработку transcript events; очередь `#writes` асинхронна. Нельзя просто скопировать текущий массив в момент телефонного завершения: можно потерять хвост. |
| Допуск текста | `unified-live-call.ts` ограничивает сохранение речи получателя после согласия; проверенное вступительное раскрытие ассистента может сохраняться до согласия. Текущий допуск зависит и от фазы в момент доставки события, поэтому поздние фрагменты требуют проверки по времени исходного аудио. |
| Источник результата | `final_transcripts` связан с `call_recordings`; `final_transcript_revisions` хранит неизменяемый зашифрованный источник. `completeFinalTranscript` создаёт ревизию и запускает резюме. |
| Производные данные | Перевод, резюме, доказательства результата и ссылки на сегменты связаны с `revisionId` и `sourceHash`. Это полезный механизм, его следует использовать для обоих источников. |
| Оценка и кредит | `postgres-call-assessment-store.ts` использует ревизию транскрипта и assessment из summary-v3. Подмена только UI оставит неверную оценку/резюме и может затронуть расчёт кредита. |
| Фоновая обработка | `recording.completed` ставит `final_transcription` в durable queue. У job есть lease, поколения, bounded retry и защита от повторной публикации. |
| Хранение аудио | Успешная финальная транскрипция выставляет `delete_after` и ставит `recording_retention`. При исключении ASR этот шаг нельзя потерять. |
| Бюджет | При допуске звонка резервируется `postcall:<attemptId>` для повторного ASR. Его освобождение связано с завершением обработки; сохранённые затраты и незавершённые provider operations нельзя списать как нулевые. |
| Интерфейс | `live-call.tsx` по умолчанию показывает «финальный» текст, а Live — «предварительный». `CallResultPanel` принимает immutable revision и сохраняет выбор оригинал/перевод по её ID. |
| Язык результата | `taskContentLanguage` отделён от UI locale и call locale. Автоматическое резюме учитывает `call_attempts.content_language`. Это различие необходимо сохранить. |
| PDF и копирование | `final-transcript-export.ts` и `derived-transcript-export.ts` используют два пути, включая legacy. В описании сейчас утверждается происхождение из записи. |
| CMS | Страницы и коллекции хранят опубликованные снимки в БД. Изменение JSON-переводов или seed само по себе не исправляет существующие публикации. Исторические публикации защищены от изменения. |
| Выкат | `scripts/shprohli-vps-release.sh:candidate_gate` отклоняет изменённый каталог миграций. Обычный restart/release не применит новую схему и CMS-контент автоматически. Нужен описанный ниже выпуск с миграциями. |

## 1. Единый сохранённый транскрипт на основе Live

### 1.1. Принять один простой контракт источника

- [ ] Сохранить существующую сущность итогового транскрипта и immutable revisions. Внутренние имена `finalTranscript`, таблиц и существующих API можно оставить: final будет означать зафиксированную версию после разговора, а не обязательно повторное распознавание аудио.
- [ ] Добавить явное происхождение `live_native | recording_asr` в итоговый объект и ревизию; обеспечить его передачу в snapshot, события, admin, JSON-экспорт и PDF. Отсутствующее поле в исторических payload трактовать как `recording_asr`, не переписывая зашифрованные ревизии и их hashes.
- [ ] Для новых попыток сохранять политику выбора источника: native Live без гибридного fallback использует live-first; Realtime, гибридный runtime и старые попытки без новой политики — прежний путь. Выбирать по фактически запущенному runtime, а не по текущему значению env при выполнении фоновой задачи.
- [ ] Фиксировать завершённость сбора нативного текста одним небольшим durable-признаком на попытке/сессии. Достаточно версии политики, session ID, статуса сбора и причины неполного завершения; не создавать отдельную систему оценок уверенности.
- [ ] Все потребители используют одну текущую immutable revision. Не выбирать Live для UI, ASR для summary и третий текст для PDF. Повторное ASR не может автоматически вытеснить уже опубликованную нативную версию.

### 1.2. Сначала исправить завершение сбора Live

- [ ] Разделить прекращение разговорных действий и завершение приёма данных. После `session.close` не отправлять новое аудио, инструменты или инструкции, но принимать относящиеся к завершившемуся аудио поздние transcript deltas до `session.closed` в пределах существующего timeout.
- [ ] Для поздних фрагментов использовать путь «только сохранение»: не вызывать interruption, `end_call`, восстановление разговора или изменение consent. Закрытая сессия не должна оживать из-за позднего текста.
- [ ] Перед отметкой завершённости дождаться очереди сохранения фрагментов. Ошибка записи, аварийный обрыв или истечение close timeout дают явный неполный сбор, а не ложный статус complete. Успешный ответ по usage сам по себе не является доказательством сохранения текста.
- [ ] Применять границу согласия по времени исходного фрагмента, а не только по моменту его доставки. Реплики получателя до согласия, в том числе поздно пришедшее согласие, не включать в результат/перевод/экспорт. Для пересекающего границу фрагмента не выдумывать пословное обрезание текста.
- [ ] Использовать имеющиеся данные о допуске/отмене аудио ассистента. Не включать заведомо подавленные реплики как услышанные собеседником; не переносить в транскрипт backend commentary или внутренние tool outputs. Сохранение текста Live не объявлять доказательством точного проигрывания каждого слова.
- [ ] При обычных прерываниях сохранять реальные фрагменты и поправки, а не переписывать ответ задним числом. Если существующие данные показывают существенную потерю доставки/сбора, использовать резервную расшифровку записи. Не добавлять mark на каждое слово или реплику.

### 1.3. Собрать источник детерминированно, без ещё одной модели

- [ ] Вынести небольшую общую функцию сборки нативных фрагментов в доступный API/web модуль. Не использовать DOM-группировку как источник данных.
- [ ] Сохранять raw deltas без перефразирования, грамматического исправления и нормализации смысла. Дедупликация — по session/event ID, не по совпадению текста. Повторённые слова могут быть реальными.
- [ ] Склеивать фрагменты каждого говорящего в их исходной последовательности, сохраняя пробелы; использовать native timing для размещения групп, допуска перекрытий и поздней доставки. При одинаковых интервалах сохранять устойчивый исходный порядок. Не смешивать слова двух говорящих.
- [ ] Не переносить UI-порог 1500 мс в доказательство окончания реплики. Он может остаться правилом отображения; завершение источника определяется завершением сбора сессии.
- [ ] Явно закрепить шкалу времени сохранённого транскрипта: начало согласованной записи/разговорной части. Нативные значения относительно начала Live-сессии преобразовывать через сохранённый session start и recording start. Не отображать секунды сессии как секунды аудиофайла. При недостоверной привязке использовать nullable timing ревизии, а не выдуманный `0:00`.
- [ ] Устранить различие контрактов времени: `SourceSegment` уже допускает null, `FinalTranscriptSegment` пока требует числа. Расширить последний контракт совместимо и обработать null в обоих export paths, admin и API; старые числовые значения сохранить. Не получать ложные таймкоды при преобразовании через legacy final object.
- [ ] В канонический источник включать разговор после согласия. Проверенное служебное раскрытие до согласия и системное событие согласия остаются в существующей диагностике/timeline, но не превращаются в реплику получателя или основание успеха задачи.
- [ ] Создавать стабильные segment IDs, sourceHash и source metadata через существующий механизм ревизий. Для новых версий hash должен отражать выбранный источник и содержимое; старые hashes не пересчитывать. Результат повторного запуска с теми же данными не создаёт новую ревизию.

### 1.4. Использовать существующую фоновую задачу

- [ ] Переиспользовать `final_transcription` как задачу подготовки сохранённого текста. Не добавлять второй параллельный оркестратор: worker выбирает сборку native либо существующий ASR.
- [ ] Пробуждать задачу также по завершению нативного сбора, используя уже созданную после согласия запись `call_recordings`. Не ждать появления доступного аудиофайла для готового native-текста. Авария загрузки/хранения файла не должна сама по себе скрывать успешно сохранённый разговор.
- [ ] Применить таблицу выбора ниже. Проверки — технические статусы существующих данных, не дополнительная семантическая оценка.
- [ ] Завершать задачу атомарно: итоговый объект, immutable revision, current pointer, постановка summary, правила retention и событие обновления. Обе реализации repository — PostgreSQL и in-memory — имеют одинаковый контракт.
- [ ] Оставить lease/generation/idempotency. При гонке `recording.completed`, завершения Live и рестарта worker публикуется одна версия. Поздний callback записи не запускает ASR поверх готового native-результата.
- [ ] В сохранённом резервном ASR убрать обнаруженное противоречие prompt: один и тот же запрос сейчас называет вход и полным разговором, и изолированной репликой. Разделить краткие описания full-file и utterance input, сохранив запрет додумывать/переводить речь. Не считать эту правку гарантированным исправлением конкретной ошибки распознавания и не вводить автосравнение с Live.

| Состояние | Результат |
| --- | --- |
| Новый native Live, согласие/запуск записи подтверждены, сбор закрыт и сохранён, есть допустимый текст | Сборка `live_native`, без вызова audio transcription. |
| Сбор ещё завершается | Ограниченное ожидание в существующей durable queue; UI сообщает о сохранении текста. Ни сравнения моделей, ни бесконечного polling. |
| Native-сбор отсутствует/оборвался/не сохранён, аудио доступно | Один существующий путь `recording_asr` с прежними bounded retries и budget policy. |
| Native неполон и аудио отсутствует | Честное состояние недоступного результата; доступные live-фрагменты можно читать как неполные. Не выдавать их за полный источник и не подтверждать успех по их отсутствию. |
| Нет согласия, voicemail без основного разговора, неответивший звонок | Сохранить существующие правила результата и возврата кредита; не создавать фиктивный пустой успешный транскрипт. |
| Исторический звонок / Realtime / гибрид | Сохранить старый источник и действующий ASR-путь. |

### 1.5. Резюме, оценка и перевод

- [ ] `TextArtifactService`, `CallTextRepository`, `postgres-call-text-store` и memory-store получают одинаковую ревизию независимо от её происхождения. Проверки актуальности используют revision ID/hash как сейчас.
- [ ] Автоматический summary остаётся на языке исходного задания, зафиксированном для попытки (`content_language` / taskContentLanguage). UI locale и язык разговора не подменяют этот язык. Явно выбранные пользователем языковые настройки сохраняются.
- [ ] Перевод строится из исходной ревизии, а не из summary и не из уже переведённого текста. Сохраняются segment IDs, роли, доступные времена и связь с источником. Для смешанной речи сохраняется действующая capability `source=*`.
- [ ] Сохранить существующие ограничения генерации, отключение провайдера, статусы queued/failed/stale и bounded retries. Готовый исходник остаётся доступен при недоступном переводе или summary.
- [ ] Оценка разговора/цели и ссылки на доказательства используют ту же ревизию. Сохранить правила согласия, различие «получен содержательный ответ» и «цель достигнута», привязку к утверждённому плану и единственность списания/возврата кредита.
- [ ] Новая ревизия делает старые производные данные неактуальными через существующий механизм. UI не показывает summary одной ревизии поверх текста другой. Не пересчитывать уже закрытые расчёты кредита задним числом.

### 1.6. UI, копирование, PDF и остальные потребители

- [ ] После звонка показывать один основной раздел «Транскрипт разговора» с оригиналом и переводом на язык задания. Во время звонка сохранить потоковое отображение. Для native-source не противопоставлять тот же текст как «предварительный» якобы более точному «финальному».
- [ ] Исторические и резервные ASR-результаты остаются читаемыми. Второй существующий текст, если он есть, допустим как дополнительный источник, но без заявления о его большей точности и без новой панели сравнения.
- [ ] В `CallResultPanel`, `call-result-projection`, `use-call-text-artifacts` сохранить выбор оригинал/перевод, evidence links, кеширование по ревизии, восстановление после reload и отказ от устаревших ответов запросов.
- [ ] Проверить обновление snapshot/revision после SSE `final_transcript.updated`: новый источник и связанные данные должны появляться без ручного reload. Не передавать событием один объект, оставляя `finalTranscriptRevision` прежним.
- [ ] Исправить оба пути экспорта: обычный `final-transcript-export.ts` и `derived-transcript-export.ts`, включая copy text, оригинальный и переведённый PDF, названия файлов, заголовки, описания источника, даты и предупреждения. Файл должен содержать ровно отображаемую ревизию/перевод.
- [ ] Для native писать «Сохранён из расшифровки во время разговора»; для ASR — «Получен из записи разговора». Не называть Live-текст дословной проверенной записью. При отсутствии времён скрывать их. Сохранить PDF layout, кириллицу, диакритику, переносы и ссылки/идентификаторы источника.
- [ ] Обновить пользовательские статусы: «Сохраняем транскрипт» для native; «Распознаём запись» только для ASR; никаких ложных ошибок записи при успешно сохранённом native-тексте. Кнопка retry повторяет выбранный путь и не заменяет исправный источник скрытым ASR.
- [ ] Проверить feedback о точности текста, историю звонков, admin inspector, lifecycle projection, account JSON-export, удаление данных звонка/аккаунта, rotation encryption keys. Они должны читать/удалять все новые поля, не восстанавливать удалённый текст отложенным job и не терять происхождение.

### Приёмка пункта 1

Главный сквозной тест: native распознал ответ A, резервный ASR в fixture содержит ответ B. При здоровом native-пути ASR вообще не вызывается; UI, перевод, summary, assessment, копирование и оба PDF используют A и одну ревизию. После повторного callback/reload результат не превращается в B.

Обязательные дополнительные случаи: позднее последнее слово после `session.close`; DB write failure; рестарт между сбором и публикацией; двойной callback; отменённая речь; совпадающий текст разных событий; перекрытие говорящих; фрагмент до consent, доставленный после него; consent-only и voicemail; технически неполный native с доступным/недоступным аудио; retention 0/7/30; удаление данных во время job; старый Realtime/гибрид; старый ASR PDF; перевод на язык задания при другом UI/call locale; неактуальный перевод не попадает в текущий экспорт; однократное списание/возврат.

## 2. Короткие согласованные инструкции и естественные подтверждения

### Что исправить

Правило «не озвучивать внутреннюю обработку» уже есть. Вместо накопления запретов нужно сократить и согласовать `buildLiveInstructions`, consent/task stage appends, `consentBackendInstructions`, `managedBackendInstructions` и tool-result instructions. В последнем звонке consent continuation ещё выполнялся, когда приложение уже включило task stage; это подтверждённое перекрытие по времени, но причинность конкретной лишней фразы не доказана.

- [ ] Составить одну короткую карту владельцев инструкций: базовый Live prompt — роль/язык/тон, backchannels/interruption/delegation; stage append — текущий переход; backend — подробные правила задачи и инструменты; tool result — только факт/статус.
- [ ] Сохранить рекомендуемые заголовки `Backchannel policy`, `Interruption policy`, `Delegation policy` и условия делегирования. Убрать дублирование подробных appointment-процедур из общего разговорного промпта, сохранив обязательное делегирование до обязательств. Детальные ограничения остаются в backend и проверках приложения.
- [ ] Сделать позитивную инструкцию поведения: после принятого согласия и запуска записи сразу перейти к цели; при обычном ответе естественно подтвердить услышанное; внутреннее решение о завершении не требует рассказа о проверке.
- [ ] Разрешить «понял», «записал», «фиксирую» и аналогичные естественные формулировки. Не вводить словарь запрещённых фраз, regex-фильтр реплик или дополнительный сетевой классификатор.
- [ ] Краткое повторение существенного результата допускается, когда помогает обнаружить ошибку; даты, имена, числа и условия не терять. Не заставлять повторять каждый ответ или каждый раз запрашивать подтверждение. Реальную неуверенность собеседника сохранять; обычную паузу/слово-паразит не превращать автоматически в новый опрос.
- [ ] Обещания будущего действия привязаны к реальному исполнителю, полномочию и возможности; запись информации не означает отправку, заказ или обратный звонок. Естественное acknowledgment и подтверждение внешнего действия остаются разными вещами.
- [ ] Consent continuation сообщает только результат решения и не предлагает отдельную произносимую реплику. Task-stage instruction задаёт текущую задачу без конкурирующих устаревших указаний. Не добавлять задержку вступления ради окончания всех внутренних запросов, если запись уже разрешена и запущена.
- [ ] Сохранить «Вам удобно продолжить?» как смысловую инструкцию. Не повторять вопрос после приглашения продолжить/ответа по задаче и не повторять представление. «Неудобно» обрабатывать в рамках существующих stop/refusal правил.
- [ ] Closing tool-result и backend continuation содержат краткий фактический исход и разрешение завершения, без команды «проверить дальнейшие шаги», готового сценария речи или второго прощания.
- [ ] Проверить `#say` для обязательного раскрытия и recovery: ожидание ответа не запрещает нужную backend delegation. Не вернуть уже устранённый конфликт «молчать до следующей команды приложения».
- [ ] При правках не добавлять семь независимых длинных промптов: сохранять единые правила, существующий параметр языка и короткие локализованные элементы там, где они действительно необходимы.

### Приёмка пункта 2

Использовать существующие голосовые harnesses и короткие разрешённые provider probes. Проверить русский/немецкий разговор: простой ответ, несколько обязательных вопросов, неизвестный ответ, отказ, неудобно, немедленный ответ вместо readiness, исправление при прощании, благодарность, разрешённая встреча. Успех — сохранён смысл и полномочия, нет обязательного озвучивания внутренних проверок, повторного представления/прощания и выдуманного следующего действия. Формулировки не обязаны совпадать с эталонной строкой.

Мок-тесты подтверждают маршруты и ограничения; естественность речи проверяется реальным аудио отдельно. Не объявлять один удачный звонок гарантией для всех сценариев.

Не удалять молча существующий migration gate и не оставлять CMS-миграцию необязательной ручной памяткой.
- [ ] В выпуск должны входить обе миграции: данные/политика транскрипта и новая CMS-публикация. Номера выделяются по актуальному каталогу в момент реализации. Старые checksums остаются прежними.
- [ ] Не допускать одновременной обработки новых native-результатов старым worker. Additive-схема должна оставаться читаемой старым кодом, но это не делает произвольный downgrade безопасным: до возобновления звонков проверить reader defaults, источник UI/PDF и поведение старого worker.
- [ ] План отката: закрыть допуск звонков, сохранить новые ревизии/задания/ledger; не откатывать БД удалением колонок/данных. Использовать совместимый релиз с отключением новой политики для последующих попыток. Если возвращается прежний пользовательский текст CMS, публиковать новую ревизию из истории; не редактировать опубликованную и не возвращать старые обещания при работающем новом runtime.
- [ ] Проверка результата выпуска: здоровый native-звонок не создаёт ASR-операций; одна ревизия используется в оригинале, переводе, summary, assessment и PDF; retention запланирован; старый звонок читается; все семь public locales показывают новый смысл после cache revalidation. HTTP health сам по себе не подтверждает это.

Production rollout и реальные вызовы не выполняются при составлении этого плана. При реализации подготовка к выпуску входит в работу; конкретный production-запуск выполняется в рамках авторизации на выкат.

## Документация Live, использованная при проектировании

- [Managing GPT-Live sessions](https://developers.openai.com/api/docs/guides/live-conversations): нативные фрагменты, приблизительные session-relative времена, раздельный учёт текста/аудио/backend, graceful close. Детерминированная сборка не превращает текст в пословное доказательство проигрывания.
- [Prompting GPT-Live](https://developers.openai.com/api/docs/guides/live-prompting): короткие разговорные инструкции, естественные acknowledgments, отдельная delegation policy, подробные процедуры в backend.
- [Delegation and tools](https://developers.openai.com/api/docs/guides/live-delegation): штатный цикл function output/continuation, краткие фактические результаты, измерение latency и поддерживаемые настройки reasoning.

Выбор native-first, схема финализации и миграция CMS — решения приложения. Документация не гарантирует превосходство Live-транскрипта над любым ASR и не предписывает удалять резервный путь.
