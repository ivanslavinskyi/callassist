## Что добавлено

Для каждого нового запроса компилятора сохраняется ограниченный JSON
`provider_operation_results.response_metadata` (миграция `0101`):

- время резервирования запроса в БД и фактический оставшийся timeout;
- timestamp dispatch (null, если запрос не был отправлен) и размер подготовленного тела запроса в байтах;
- смещения от dispatch: создание HTTP-запроса, начало записи в socket,
  завершение отправки тела, получение заголовков;
- длительность чтения и разбора JSON-ответа;
- фаза сбоя (`before_dispatch` / `before_headers` / `response_body`) и разрешённый сетевой код;
- опциональные числовые `openai-processing-ms` и остатки rate limits.

Транспортные события Node/Undici связываются с конкретным запросом через
`AsyncLocalStorage` и `WeakMap`. Наблюдатели синхронные, без дополнительных
сетевых запросов или записей в БД. После окончания попытки поздние события
игнорируются. Трафик вне вызовов компилятора не собирается.
События соединения, которые нельзя однозначно привязать к HTTP-запросу,
не используются. При отсутствии событий поля остаются `null`.

Существующий экран `/admin/calls/preparations/<id>` показывает:

- начальную очередь, общее время и сумму измеренных provider requests;
- попытки фонового задания, их результаты и промежутки между попытками;
- этап, модель, transport retry, repair и generation;
- подробные измерения транспорта и промежутки между запросами;
- client/provider request IDs, HTTP status, входные, cached, выходные и
  reasoning tokens из уже существующего журнала usage.

Client request ID уже передавался через `X-Client-Request-Id`; теперь его
можно прочитать рядом с измерениями, в том числе при таймауте без ответа.
Экспорт телеметрии включает новые технические поля с проверкой схемы.
Новые diagnostics не содержат текстов плана, сырых headers, URL, ключей,
сообщений исключений, stack traces или аудио. Старые данные не дополняются
предположительными значениями. Прежние retention/access rules сохранены.

## Как читать следующий медленный случай

1. Большая начальная очередь или gap между worker attempts — задержка
   исполнения/повтора фонового задания. Это отдельный интервал, не время LLM.
2. Большое `reservationMs` — ожидание локального резервирования в БД.
   Если общий deadline истёк за это время, `failurePhase=before_dispatch`
   и `dispatchedAt=null`: запроса к провайдеру не было.
3. Большой интервал до `socketWriteMs` — запрос ещё не начал запись в socket:
   возможны пул соединений, соединение, TLS или локальная задержка.
4. Тело отправлено быстро, заголовки пришли поздно — ожидание после отправки.
   Это уже исключает длительную локальную отправку, но не различает внутреннюю
   очередь OpenAI и сетевое ожидание/потерю ответа.
5. Заголовки пришли быстро, `bodyReadMs` велик — задержка чтения/разбора тела.
6. HTTP 429/5xx и коды сети различаются; остатки rate limits и необязательное
   processing time дают дополнительный контекст, но сами по себе не доказывают
   причину таймаута. Для расследования на стороне провайдера нужны request IDs.

Offsets пересекаются: их нельзя складывать. Gap после предыдущего ответа
может включать journal write, validation/repair preparation и worker retry;
он не объявляется целиком временем БД. Полное время фоновой попытки может
закончиться позже публикации плана.

Диагностика заканчивается публикацией плана. Отдельная review translation
и задержка polling/отрисовки браузера могут добавляться после этого.
Отсутствие OpenAI processing header означает «неизвестно», а не 0 мс.
Без ответа провайдера нельзя гарантировать точную внутреннюю причину его
ожидания; с новыми данными можно существенно точнее локализовать задержку.

Для проверки достаточно создать новый план. Звонок для этого не нужен.
По ID подготовки можно открыть админку и сопоставить новые поля с журналом
попыток; старые подготовки показывают только ранее сохранённые измерения.
