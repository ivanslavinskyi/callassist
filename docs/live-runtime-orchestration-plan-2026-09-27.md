# Live: единое управление диалогом для беты

> Historical checkpoint, not the current runtime specification. As of 28 September,
> consent uses native `report_consent`, and `end_call` carries a reason without a
> scripted recap. See the [current runtime](live-unified-runtime.md) and
> [real-call review](live-call-review-2026-09-28.md). Results and pending items below
> describe the implementation at this report's date.


Дата: 27 сентября 2026. Ветка: `codex/live-unified-runtime`.
Статус: согласован и реализован на текущей ветке; ручная приёмка и deployment ещё впереди.
Проверки и ограничения: [отчёт о реализации](live-client-implementation-2026-09-27.md).
Ниже сохранено исходное обоснование; «сейчас» в разделе аудита относится к коду до реализации.

## Решение

Перевести Live на официальный `delegation: { type: "client" }`. Сохранить GPT-Live-1
единственным голосом и источником live-транскрипции, GPT-6 Luna — текстовым backend
через Responses API, `parallel_tool_calls=false`, `store=false`. Один контроллер
приложения владеет запуском backend, актуальностью решений и переходами задачи.

Это осознанное изменение режима: сейчас используется управляемый OpenAI режим
Responses delegation; предлагается client delegation с самостоятельными Responses
запросами. Это не переход на Realtime и не новая модель озвучивания.

Проверить жизнеспособность на настоящем аудио до массовой переделки. Client delegation
даёт контроль, но не обещает меньшую задержку или безошибочную семантику.

## 1. Что подтверждено аудитом

Проверены transport, unified lifecycle, controlled speech, semantic consent,
appointment authorization, provider usage, хранение событий, тесты и probes.
Рабочее дерево содержит незакоммиченные изменения предыдущих итераций; их сохранить.

| Наблюдение | Причина/ограничение в коде | Последствие |
| --- | --- | --- |
| Последний немецкий звонок: ответ получен, затем около 40 секунд без речи; нет delegation/end_call | `provideRecipientEvidence` добавляет контекст, но обычная реплика не запускает backend; deadline начинается только после запуска | Ни следующий шаг, ни завершение не гарантированы |
| В более раннем звонке прерванное завершение зависло | `#interruptedClosing` в bridge и closing-state в lifecycle управляют одной ситуацией отдельно; backend может завершиться без нужного routing tool | Голос остаётся подавленным, хотя задача backend закончилась |
| При формальном обращении появилось «du» | `addressingStyle` и tone есть у backend, но отсутствуют в `buildLiveInstructions` | Инструкция одной модели не задаёт стиль другой |
| Проверка завершённой записи опирается на более позднюю реплику/DTMF | Bridge проверяет время/epoch после авторизации; смысл подтверждения остаётся в prompt | Любая новая реплика не должна считаться подтверждением конкретного времени |
| Вторая проверка appointment блокируется после первой авторизации | Не разделены разрешение варианта и уже отправленный запрос | Защита от второй записи нужна, но её нельзя применять к простому обсуждению вариантов |
| `session.update` отправляется без проверки положительного ack | Нет корреляции готовности с `session.updated` | Дополнительный пробел наблюдаемости; не доказанная причина последнего зависания |
| Controlled speech проверяется после передачи аудио в Twilio | Класс прямо реализует transition gate, не pre-playback filter | Нельзя обещать, что неправильная фраза вообще не прозвучит |
| Зелёные unit/probe не поймали отсутствие delegation | Один тест ожидает отсутствие backend после 16 секунд; probe сам посылает `response.create` и текст | Проверяется обработка уже начавшейся работы, а не аудио → полезное действие |

Основание по последнему звонку: [отдельный разбор](live-missing-delegation-review-2026-09-27.md).
Он сопоставляет execution snapshot, оба транскрипта, ledger и события. Аудио в этом
разборе отдельно не прослушивалось. Stream stop не устанавливает, кто положил трубку.

Конкретные блюда, имена, «всё верно» и другие фразы нужны только как тестовые данные.
Они не становятся условными ветками production runtime.

## 2. Почему этот режим

| Вариант | Оценка для SHPROHLI |
| --- | --- |
| Только добровольная Responses delegation со стороны Live | Простая интеграция; не обеспечивает вызов контроллера после значимого ответа — это уже воспроизведено |
| Добровольная delegation плюс дополнительные ручные `response.create` по таймерам | Два инициатора одной работы; сложнее исключить гонки, дубли и несовпадающие версии контекста |
| Client delegation, один контроллер приложения | Явное владение работой и проверками; требует собственного контекста и измерения задержки — рекомендуемый вариант |

OpenAI описывает client delegation для собственного backend и application-owned
контекста: [Delegation and tools](https://developers.openai.com/api/docs/guides/live-delegation).
Разделение голосовой части и прикладных проверок согласуется с
[migration guide](https://developers.openai.com/api/docs/guides/live-migration).
Выбор для SHPROHLI — наш инженерный вывод, не утверждение, что OpenAI рекомендует
один режим всем приложениям.

## 3. Ответственность компонентов

| Компонент | Единственная область ответственности |
| --- | --- |
| `OpenAILiveBridge` | WebSocket, официальный протокол, PCMU, native transcripts, ack/error/close и usage; без управления задачей |
| Новый `LiveTaskController` | Сериализованная обработка событий, запуск Luna, версии контекста, разрешённые переходы и дедлайны |
| Новый `LiveTaskBackend` | Responses request/response, строгая схема решения, cancellation, usage; не исполняет эффекты сам |
| Сборщик реплик | Исходные native deltas, timestamps, версии накопленного контекста; отдельно от группировки пузырей UI |
| `UnifiedLiveCall` и playback-компонент | Twilio admission/AMD, согласие, запись, выдача/очистка аудио, отметки проигрывания и hangup |
| Действующие policy/repository/services | Immutable approval, валидация полномочий, идемпотентность, сохранение, reconciliation и расчёты |

Это модули внутри текущего API, без нового сервиса, очереди или универсального
workflow-фреймворка. Общий интерфейс voice runtime и Realtime backend сохраняются.

Контроллер хранит несколько независимых состояний: фазу звонка, факты/ожидаемый ответ,
текущую работу backend и воспроизведение. Не смешивать «человек заговорил», «изменил
просьбу», «отменил действие» и «отменил проигрывание» в один флаг interrupted.

## 4. Один путь обработки значимой реплики

1. Принимать native input/output deltas с исходным текстом и временными диапазонами;
   дедуплицировать по идентификаторам событий, не по совпадению слов. Отображение UI
   не определяет границы бизнес-реплики. Повторённое человеком слово сохраняется.
2. Локальная речевая активность и короткая тишина дают кандидата на обработку.
   Они не доказывают конец мысли, согласие или обращение к агенту.
3. Накопленная новая реплика и `session.delegation.created` поступают одному
   планировщику. Для одной версии контекста они объединяются в одну работу;
   отсутствие события delegation не блокирует обработку ответа.
4. Одновременно выполняется максимум один запрос принятия решения. Новые данные
   обновляют ожидающую версию. Поздний ответ учитывается в usage, но не разрешает
   устаревшее действие. Все события, включая callback async-операций, проходят через
   один сериализованный обработчик.
5. Luna получает утверждённый план на языке звонка, текущую задачу, заданный вопрос,
   подтверждённые факты, последние реплики обеих сторон и незавершённую операцию.
   Известные произнесённые служебные фразы тоже входят в контекст.
6. Строгое решение описывает наблюдения, ссылки на реплики, следующий шаг и при
   необходимости конкретное предложение/подтверждение. Возможны ответ, вопрос,
   уточнение, ожидание, посторонняя речь, проверка действия, завершение.
7. Код проверяет схему, актуальность, права и предусловия. Только принятое решение
   обновляет состояние и возвращается в Live. Ошибка схемы не превращается в успех.

«Не знаю», отказ и ответ сразу на несколько вопросов — полноценные результаты.
Для информационного звонка не требуется положительный ответ на каждый вопрос,
чтобы корректно завершить попытку. Открытый разговор не становится жёстким опросником.

Реплики о детях, речь на фоне и длинные паузы разбираются в контексте заданного вопроса.
При сомнении — одно конкретное уточнение; нельзя обещать идентификацию говорящего
по обычному монофоническому телефонному аудио.

Протокол: использовать `session.commentary.append` для краткого принятого результата,
`session.thinking.append` для актуальных фактов и `session.instructions.append` для
правил поведения. Коррелировать ack с `client_event_id`, обрабатывать ошибки.
Не выдавать ack за факт произнесения. В client mode не посылать Live `response.create`
или `response.item.create`: запросы Responses выполняет `LiveTaskBackend`.
Детали контекста и ограничения событий:
[официальное руководство](https://developers.openai.com/api/docs/guides/live-delegation).

## 5. Голос, язык и естественность

Frontend получает язык звонка, разрешённый fallback языка, формальность и тон
непосредственно из snapshot при старте. Backend использует тот же источник.
Первое имя, бытовая тема или неформальная речь собеседника не меняют утверждённое обращение.

Live сохраняет естественное слушание и короткие уместные реакции. Содержательный
следующий шаг приходит от контроллера. Не требовать повторения каждого ответа,
не превращать каждое «понятно» в запрос подтверждения. Не добавлять отдельный
LLM-вызов ради литературного пересказа результата Luna.

Для обычных реплик — прямой PCMU поток с проверками по native transcript. Для
критичных высказываний, способных оформить запись или заявить её успех, — отдельное
ограниченное окно воспроизведения с проверкой до передачи аудио в Twilio.
Самостоятельная речь модели не является разрешением действия в приложении.

Сегментация критичного аудио, поздний transcript, пауза внутри фразы и продолжение
после удержанного звука — обязательная техническая проверка первого этапа. Буфер
ограничен по времени/размеру; позднее разрешение отменённого сегмента игнорируется.
Не распространять медленную предварительную проверку на весь бытовой диалог.

Это компромисс: realtime-мониторинг не может отозвать уже услышанное, а буферизация
добавляет задержку. Прямо проверять фактически проигранное аудио и не объявлять
семантический классификатор безошибочным. Основание:
[Server-side controls, speech before playback](https://developers.openai.com/api/docs/guides/voice-server-controls?api=live).

## 6. Согласие, запись и внешние действия

Сохранить работающую семантическую классификацию согласия на всех языках звонка,
имя заказчика в initial disclosure, проверку доставки disclosure и consent-gated
recording. Отказ/отзыв согласия имеют приоритет. До согласия не сохранять текст
ответа и аудио в диагностический журнал; технический результат проверки допустим.

Отделить пять фактов: вариант предложен; разрешён политикой; запрос реально отправлен;
получатель подтвердил; результат независимо проверен внешней системой. Сейчас
`check_appointment` проверяет полномочия, а не обращается к календарю организации.
Подтверждение собеседника — сообщение получателя, не проверенная запись в чужой БД.

Предложение имеет ID/версию и полные дату, время, timezone, услугу и адресата.
Подтверждение связано с этим предложением и реально заданным вопросом. Новая реплика
сама по себе недостаточна: нужны семантика и ссылка на её контекст. Неопределённость,
условие или исправление не дают перехода в confirmed.

Сохранить детерминированные проверки окон, timezone/DST, услуг, адресата и финансовых
условий. Можно обсуждать и повторно проверять варианты до первого обязательного
запроса. После возможной отправки запроса — проверять его статус, не оформлять второй.
Текущая политика разрешает одну запись; перенос/отмена/вторая запись не получают
авторизацию вследствие этого рефакторинга. Для них нужны отдельные approved capabilities.

Идемпотентность строится по бизнес-операции и snapshot, не только по model call_id.
До первого критичного исходящего аудио фиксировать intent; после mark — доставку;
при обрыве/clear хранить неопределённость, а не утверждать, что действия не было.
Даже mark не доказывает, что сотрудник внёс запись. Не обещать exactly-once для
действий человека на другом конце телефонного соединения.

Минимальное необходимое durable-хранение: журнал критичных action intents с уникальным
ключом, версией, состоянием и зашифрованными данными предложения/подтверждения.
Предлагается одна additive-таблица с FK на attempt; имя/номер миграции выбрать по
актуальной последовательности при реализации. Обновление — транзакционно с проверкой
версии. Подключить удаление/retention, экспорт пользовательских данных и ротацию ключей.
Обычные реплики и каждый VAD-frame туда не дублируются.

`call_events` подходят для обезличенных переходов, но не для полного чувствительного
контекста: metadata не зашифрованы, журнал имеет ограничения размера/неизменяемости.
Не использовать provider ledger вместо состояния задачи. Для беты не вводить
автовосстановление разговора после падения процесса: завершить повреждённую попытку
через reconciliation, сохранить неопределённый результат и не повторять действие автоматически.

## 7. Завершение и восстановление

После достаточного результата: один краткий пересказ сути → короткая возможность
поправить → прощание → подтверждённое проигрывание → hangup. Резюме допускает
естественный пересказ, не обязано перечислять каждый ответ. Не спрашивать общее
«согласны со всем?» без необходимости подтвердить конкретное действие.

Если результат не достигнут — так и сказать, завершить с правильным outcome.
Техническое сохранение в SHPROHLI не становится вопросом к получателю или критерием
успеха разговора. Сохранение данных проверяет приложение отдельно.

| Событие во время завершения | Реакция |
| --- | --- |
| Короткое подтверждение/благодарность | Продолжить прощание, не повторять всё резюме |
| Исправление факта | Отменить старое завершение, обновить факты, кратко подвести исправленный итог |
| Новый вопрос | Ответить в разрешённых пределах и затем завершить |
| Просьба подождать | Явное ограниченное ожидание, без одновременного таймера hangup |
| Посторонняя речь/шум | Не менять договорённость только из-за звука; сомнение обработать контекстно |
| Просьба закончить | Коротко попрощаться, без принудительного полного резюме |
| Потеря провайдера | Записать технический исход и закрыть телефонную линию; не заявлять успешное прощание |

Один контроллер владеет ограничениями времени по фазам. Ожидание человека,
backend, воспроизведения и восстановления — разные причины, видимые в telemetry.
После значимой реплики всегда имеется работа или определённое ожидающее состояние
с пределом времени. Завершённый backend не может оставлять бессрочный audio mute.

Повтор чистого reasoning-запроса допустим ограниченно; повтор внешнего эффекта
при неизвестном результате запрещён. Для беты: максимум одна автоматическая
повторная попытка backend после transient failure и ограниченное число уточнений
одного неразрешённого вопроса. При исчерпании — понятное неполное завершение.
Точные временные бюджеты централизовать и подобрать по измерениям, не разбрасывать
новые 10/30/45-секундные таймеры между bridge и lifecycle.

Playbacks имеют свои ID/поколения. `clear` отменяет очередь и связанные ожидания;
возвращённый после clear mark не разрешает hangup. Сохранить `prepareAgentHangup`
и durable reconciliation. Ни backend completion, ни тишина не заменяют playback.
У Live нет `response.done` для речи:
[Managing sessions](https://developers.openai.com/api/docs/guides/live-conversations).

## 8. Задержка, UI, админка и деньги

Считать отдельно answer→AMD, AMD→Live ready, ready→disclosure audio,
recipient turn→backend start, backend duration, accepted result→audible response,
recap→hangup. В последнем звонке AMD занял 6.042 секунды из 7.849 до disclosure:
переделка delegation не уберёт эту часть сама по себе. Сохранить раннюю подготовку
Live, не произносить consent как человеку до разрешающего результата AMD.

Инициализировать reusable Responses client/соединения заранее; сохранять стабильную
часть контекста для caching, объединять новые фрагменты и не запускать Luna на каждый
пакет. Измерять содержательный ответ, а не только быстрое «угу». Не повышать платный
service tier без измеренного эффекта и отдельного решения о стоимости.

Native transcript остаётся live-представлением. Служебные произнесённые фразы,
событие согласия и частично проигранные/отменённые сегменты показывать честно;
сгенерированное, но отброшенное не выдавать за услышанное. Состояние UI не управляет
прогрессом задачи. Существующие final transcription и автоматическая оценка остаются.

Добавить в admin timeline/runtime export: версию контроллера, фазу, причину ожидания,
turn/task revision, backend request IDs, stale-result reason, playback/clear/mark,
основание завершения. Метаданные без сырого диалога, секретов и pre-consent текста.
Новые пользовательские сообщения — во всех существующих локалях UI.

Provider ledger: Live duration и каждый Responses request отдельно, включая
отменённые/устаревшие/ошибочные. При неизвестном usage — unknown, не ноль; без двойной
записи расходов как managed и standalone delegation. Закрытие ждёт final usage
ограниченное время; потеря финального события отражается как incomplete.
Правила списания credits не менять этим рефакторингом.

## 9. Что заменить, а не нарастить

- Удалить из Live bridge managed Responses orchestration после успешной замены:
  ручные продолжения плюс автономные делегации, независимые closing-recovery таймеры,
  отдельное владение `#interruptedClosing` и глобальное подавление аудио без состояния.
- Заменить Live-specific branching в огромном Realtime prompt отдельными короткими
  frontend/backend instructions. Общие policy-факты получать из одних pure builders.
- Заменить epoch-only подтверждение appointment объектом предложения и evidence.
- Оставить транспорт Twilio/PCMU, semantic consent, deterministic authorization,
  approved snapshot, ledger, post-call jobs и проверенное hangup reconciliation.
- Не вводить списки бытовых фраз, самостоятельного агента-надсмотрщика, постоянную
  вторую ASR или ещё один слой LLM для перефразирования каждого ответа.

## 10. Этапы и критерии приёмки

1. Зафиксировать воспроизводимые failures текущей реализации и baseline аудио,
   latency/cost. Добавить production-bridge probe с синтетическим аудио и настоящими
   Live events: никакой инъекции готового `end_call` или `response.completed`.
2. На изолированной локальной конфигурации проверить client mode, естественный
   ответ, single-owner scheduling, native transcripts, appends/ack, перебивание,
   Twilio playback и проверку критичного сегмента. Не оставлять в финальном runtime
   два экспериментальных orchestration пути. Если latency/качество неприемлемы —
   остановить переход и разобрать измерения до переписывания остального.
3. Реализовать reducer/controller и Responses backend, затем подключить существующие
   consent/recording/closing. Добавить необходимые action intents и адаптер telemetry.
4. Удалить заменённые механизмы, проверить diff на races/privacy/billing, актуализировать
   конфигурацию и deployment instructions. Realtime selection/regression tests сохранить.
5. Полный test/lint/typecheck/build, PostgreSQL integration, native audio probes,
   ручные Twilio звонки на локалке. Deployment после утверждения пользователя;
   Live без runtime fallback. Откат релиза — между звонками, не переключение модели
   посреди разговора.

| Группа | Обязательные сценарии |
| --- | --- |
| Простые задачи | Один вопрос; неизвестный ответ; отказ; несколько фактов в ответе; задача уже решена |
| Сложные | Длинное интервью; консультация в рамках approved scope; неполные данные; изменение ответа |
| Appointment | Окно/таймзона/DST; предложение альтернативы; условия оплаты; согласие/отказ/исправление; неизвестный исход первого запроса; запрет второй записи/неразрешённого переноса |
| Согласие | Разные естественные формулировки; условное согласие; отрицание; отзыв; шум; перебитый disclosure |
| Full duplex | Длинная фраза с паузой; overlapping speech; фон/обращение к детям; hold; поздняя transcription delta |
| Завершение | ACK; исправление; новый вопрос; просьба закончить; просьба подождать; повтор/потеря mark; clear в гонке с mark |
| Backend/provider | Нет native delegation; дубли delegation; late/stale result; invalid output; rate limit; timeout; WebSocket loss; shutdown в момент intent |
| Языки | Все поддерживаемые языки звонка и локали UI; formal/informal; оба голоса; язык задания отличен от языка звонка |
| Учёт | Usage после отмены/обрыва; неизвестный final usage; идемпотентное начисление расходов/credits; export без утечки данных |

State-machine tests проверяют перестановки событий и инварианты, включая отсутствие
бессрочного pending/mute, неподтверждённого перехода в успех и повторного эффекта.
Реальные модельные прогоны повторяются с перефразировками и отдельными сценариями,
не использованными при настройке prompt. Тесты настоящего аудио дополняют, а не
заменяют детерминированные проверки.

Условия выпуска: все детерминированные проверки green; нет критических нарушений
разрешений/повторов/неправильного hangup в сценарной матрице; нет воспроизводимого
бесконечного ожидания; приемлемые измеренные p50/p95 задержки и расходы относительно
baseline; ручное подтверждение естественности разговора и короткого резюме.
Порог производительности зафиксировать после baseline до сравнительного прогона,
чтобы не подбирать его задним числом под результат. Зелёные tests без реального
аудио не считаются подтверждением готовности voice runtime.

## Границы обещаний

Код может гарантировать ограниченность ожидания, проверку разрешений, отклонение
устаревших решений и отсутствие автоматического повторения неопределённого эффекта.
Правильное понимание любой человеческой реплики и безупречную спонтанную речь модели
гарантировать нельзя. Ошибки должны приводить к уточнению или честному неполному
результату, а не к ложному успеху, молчанию до ручного отключения или второй записи.
