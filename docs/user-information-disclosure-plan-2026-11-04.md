# Универсальная передача пользовательских сведений

Дата: 4 ноября 2026, Europe/Zurich.
Статус: минимальное исправление реализовано и проверено локально; поведенческая
приёмка в реальном разговоре остаётся за пользователем.

## Принятое решение

По уточнению пользователя применён минимальный вариант без нового контракта,
миграций, дополнительных состояний разрешения, запросов к моделям или изменения
разговорного цикла. Первоначальное предложение о передаче полного исходного
корпуса и новом версионированном контракте заменено этим решением.

Все сведения, введённые для задания, разрешены к передаче указанному собеседнику
по необходимости выполнения задачи. Не нужно отдельно разрешать каждый факт.
Компилятор не должен создавать запрет, blocking issue, stop condition или risk
category только из-за того, что предоставленные сведения персональные.
Явное пользовательское указание не сообщать значение либо сообщить его при
определённом условии сохраняет силу. Отсутствующие значения нельзя выдумывать.
Передача сведений не даёт разрешения на новые внешние действия.

## Реализация

Единый текст правила находится в
`apps/api/src/voice/supplied-information.ts` и используется компилятором,
инструкциями Live и инструкциями backend. Общая формулировка исключает
расхождение между тремя участниками.

Компилятору отдельно указано сохранять сведения из facts, objective, context и
clarification answers в существующих полях плана на языке звонка. Не добавлены
списки чувствительных категорий, распознавание конкретных фраз или отдельные
ветки для даты рождения, клиники либо других сценариев.

Сохраняется существующий путь: пользовательский ввод → подготовка и перевод →
проверка языка → утверждённый снимок → Live/backend. Исходные тексты остаются
в исходном задании и аудите. Голосовой контекст получает уже переведённые значения;
имена, адреса и идентификаторы сохраняют точное написание. Дополнительный корпус
исходных текстов в разговор не передаётся.

Схемы, хеширование, история, повторные попытки, stop conditions и разрешения
на внешние действия не изменены. Ранее подготовленные планы не переписаны:
для ручной проверки следует подготовить новое задание через обычную форму.

## Проверки

- 482 теста API в восьми файлах: компилятор, утверждение, целостность снимка,
  языковой аудит, контекст исполнения, полный тестовый голосовой рантайм,
  PostgreSQL история и итоговая оценка.
- TypeScript API: успешно. Проверка типов web также прошла во время работы;
  конечное исправление не меняет web и контракты.
- Сквозная проверка с подставным провайдером: русский objective/context и английский
  исходный факт преобразуются в немецкий план, проходят review/approval и доходят
  до обоих голосовых контекстов. Исходные формулировки в них отсутствуют.
- Проверено наличие единого правила в фактических инструкциях Live и backend,
  сохранение явных пользовательских ограничений в инструкциях и отсутствие
  дополнительных запросов при подготовке.

Mock и регрессионные тесты подтверждают интеграцию и сохранение существующего
поведения кода. Они не доказывают, что реальная модель всегда правильно применит
новую инструкцию. Устранение отказа и естественность ответа должны быть проверены
в ручном разговоре. Платные модельные прогоны и реальные звонки агентом не выполнялись.

## Локальное включение и ручная приёмка

API и worker перезапускаются совместно после проверки отсутствия активных звонков
и задач. Тоннель и пользовательская база сохраняются. Текущие PID, версия исходников
и адрес тоннеля находятся в `.tools/runtime/hardening-local-2026-11-02/state.json`.

Для проверки создать новый план с нужными сведениями. Собеседник запрашивает
известное значение или его часть. Ожидается прямой ответ на языке звонка без
дополнительного согласия и продолжение задачи. Отдельно проверить явный запрет
пользователя и неизвестное значение. Результат внешнего действия считается
достигнутым только после его обычного подтверждения.

При повторении дефекта сначала сохранить подготовленный план, инструкции и
транскрипт. Не маскировать проблему добавлением частных условий. Расширение
архитектуры допустимо только после отдельного доказательства, что минимальная
правка недостаточна; автоматического production-выпуска нет.
