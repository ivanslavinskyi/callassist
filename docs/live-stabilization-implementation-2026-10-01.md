# Live v5: завершение беседы и календарный результат

Дата: 1 октября 2026 года. Ветка: `codex/live-unified-runtime`.
Основание: [аудит звонка](live-runtime-completion-audit-2026-10-01.md) и
[утверждённый план](live-stabilization-implementation-plan-2026-10-01.md).
Изменение реализовано; новая ручная приёмка на телефоне ещё требуется.

Последующая приёмка v5 обнаружила регрессию транскрипта и языковой контекст;
см. [исправление v6 и уточнённый аудит](live-transcript-language-fix-2026-10-01.md).
Этот документ описывает историческую реализацию v5.

## Что исправлено

В исходном звонке приложение завершило соединение после обычного подтверждения
адреса. Старый путь мог принять такой хвост речи за завершение прощания. В v5
принятый `end_call` сохраняет решение с кратким итогом, наблюдениями собеседника,
причиной, состоянием действия и привязкой к попытке/утверждённому snapshot.
Существующий renderer озвучивает итог и локализованное прощание одним конечным
аудиофрагментом с выбранным голосом. Только подтверждение его актуального Twilio mark
разрешает подготовить и выполнить отключение. Завершение backend response, тишина
или обычная реплика не являются подтверждением доставки финала.

При прерывании mark отменяется. Ответное прощание сохраняет решение, содержательная
поправка возвращает разговор в рабочую фазу. Разрыв со стороны собеседника отменяет
ожидающее завершение; отрицательный результат durable hangup preparation не отмечается
как успешное отключение ассистентом. Повтор после сбоя сохраняет тот же фактический
итог. Две попытки делят один предел 30 секунд. Недоставленный финал не получает
фиктивного playback receipt. Отказ в согласии, автоответчик и технический отказ
сохраняют короткие окончания, соответствующие своей политике.

Старая реализация `live-closing-speech.ts` удалена. Владелец lifecycle остаётся
`UnifiedLiveCall`; новый агент или параллельный координатор не добавлен.

Проблема «неизвестно, входит ли 3 октября в следующие две недели» возникла в post-call
summary: его вход не содержал уже известных окон и даты попытки. Новый
`SummarySourceContext` проходит цепочку artifact → transcript revision → attempt →
approved compilation. Он содержит неизменные окна, timestamp исходного звонка и
подтверждение действия для конкретного slot. Контекст шифруется и фиксируется до
генерации, одинаково для chunks, compaction, повторов и второго языка.

Тот же существующий structured summary request извлекает кандидатов даты/времени,
статус высказывания, citations и явные исправления. Чистая функция
`evaluateAppointmentCalendar` проверяет принадлежность утверждённому окну, границы,
зону и DST; она используется также realtime validator. Дополнительных календарных
LLM-запросов, tools или этапов orchestration нет. Поздний worker не использует
сегодняшнюю дату вместо времени исходной попытки.

Для fixture 01.10.2026, Europe/Zurich, «следующие 14 дней без пятниц, 09:00–18:00»:
03.10.2026 в 11:00 → `within`; исключённая пятница или 18:01 → `outside`.
Обе границы допустимы: окна ограничивают время **начала** включительно.

## Доказательства и сохранность истории

- Summary payload v3 отделяет вычисленный календарный результат от слов собеседника.
  Provider не может прислать готовый доверенный calendar verdict. Проверка источников
  и повторное вычисление выполняются перед публикацией, в том числе для cached chunks.
- Membership в расписании, reported confirmation и подтверждение application action
  остаются разными фактами. Составное пользовательское условие не становится выполненным
  только из-за правильной даты. `goal=achieved` ограничивается обязательной проверкой
  appointment authority и соответствующего подтверждённого действия.
- UI, копирование и PDF используют общую projection. Вычисленная строка показывает
  выбранную дату/время и утверждённое окно; журнал действия отображается отдельно.
  Календарная строка не получает certainty, предназначенную для слов собеседника.
- Новый generator — `summary-v4:grounded-v3`; legacy payload v2 и summary-v3 читаются.
  `fixedAssessment` требует совпадения источников, версии и context hash.
- Новая оценка сохраняется в immutable assessment revision. Отображение использует
  её, исходное billing evidence остаётся отдельным. Повторная публикация не списывает
  и не возвращает кредит повторно.
- Исторические звонки, transcript, approvals и summaries автоматически не пересчитаны.
  Старый результат звонка с Еленой остаётся историческим. Новая ревизия для него —
  отдельная явно запрошенная операция, а не побочный эффект запуска API.
- Миграции 0090/0091 добавляют context, assessment revisions и terminal decisions.
  SQL разрешает первичную фиксацию context до completion и запрещает подмену; redaction
  и encryption rotation сохранены. Account export включает новые записи, удаление
  редактирует encrypted payload. Общий inventory содержит 24 ciphertext families.

## Остальные исправления runtime

Полезные backend message items учитываются из deltas и `output_item.done`, даже если
финальный `response.output` пуст. Новый ответ сбрасывает просроченное ожидание старой
реплики; silent audio packets не считаются полезной речью. Локальный timeout запрещает
старые эффекты, но не освобождает физически ещё работающий provider run. Неопределённый
run заканчивается ограниченным failure path вместо наложения новых команд.

Отклонённый appointment request удерживает output до уточнения. Временный
`unconfirmed_details` не разрешает немедленное `cannot_proceed`. После неопределённой
доставки действует status-only reconciliation того же exact proposal, максимум три
попытки; противоречащая этому инструкция повторного booking удалена.

Итого проверено 2 167 уникальных тестов: полный прогон 2 165 плюс две дополнительные
voice-регрессии. Тесты не выполнялись на рабочей базе. Ранний прогон выявил несовместимость
account export schema, старые test expectations и immutable SQL trigger; они исправлены,
повторный полный прогон прошёл. Исходные семь runtime-диагностик переведены в регрессии
желаемого поведения, контрольный случай сохранён.

Provider eval проверяет RU/DE/FR/IT/EN, дату словами, явное исправление даты, неоднозначное
предложение и инструкцию внутри transcript. Пять однозначных случаев дали `within`;
неоднозначный не получил выдуманный успех. Это ограниченная проверка извлечения смысла,
а не доказательство распознавания любого возможного разговора. Запуск:
`ALLOW_BILLABLE_EVAL=true` и `corepack pnpm --filter @callassist/api eval:summary-calendar`.
Harness: `apps/api/src/text-processing/summary-calendar.eval.ts`; он не делает звонков.

## Локальная активация и следующий звонок

Кандидат активирован локально 01.10.2026 в 11:39 Europe/Zurich; проверка в 11:40
подтвердила совпадение source manifest, 91 migration/checksums, API live/ready и web HTTP 200.
Через текущий Twilio tunnel приватный API вернул 404, неподписанный webhook — 403.
Исходящие звонки и расходование бюджета включены, необходимые credentials присутствуют.
Активных звонков и queued/running summaries старого generator — 0. Точные PID, URL,
commit и source manifest находятся в `.tools/runtime/stabilization-state.json`.
Секреты и временный tunnel URL в Git не сохраняются. Исходящий звонок не выполнялся.

Профиль: Live `live-managed-v5`, fallback=false, auto hangup=true, embedded worker;
existing Live/backend models и выбранные голоса сохраняются. Новых env flags нет.
Приложение: `http://localhost:3000/ru`. Полный каталог — 91 migration; старый локальный
legacy tombstone может делать число записей ledger на одну больше каталога.

Для ручной приёмки:

1. Создать и утвердить свежий appointment plan с указанным выше периодом. После согласия
   на запись предложить 3 октября в 11:00, подтвердить обязательные детали и запись.
2. Дождаться краткого итога и целого прощания. Ассистент должен отключить соединение
   после их воспроизведения. Проверить terminal decision → mark → playback_complete →
   durable hangup и инициатора окончания.
3. Проверить итог, copied text и PDF: дата соответствует расписанию; application
   action state соответствует журналу, а не автоматически повышен из calendar membership.
4. Отдельными звонками проверить ответное «до свидания», поправку во время финала,
   ранний разрыв собеседника и отказ. Повторить акустическую проверку обоих голосов.

Recording-ASR fallback сохранён для application-rendered task speech: наличие TTS
playback mark не выдаётся за полную native transcription. Естественность перехода
Live/TTS, слышимость целого прощания и p95 latency требуют реальной записи.
Цели ≤3 с до terminal audio и ≤1 с от mark до hangup пока не измерены.
Production rollout не выполнялся; [порядок выпуска и rollback](deployment-preflight.md#schema-release-0090-0091).
