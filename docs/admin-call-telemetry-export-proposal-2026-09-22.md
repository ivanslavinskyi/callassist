# Выгрузка телеметрии звонков из админки

Дата: 2026-09-22. Исходное предложение после исследования кода. Основная выгрузка реализована локально; актуальные состав, ограничения, отличия и запуск описаны в [инструкции реализации](admin-call-telemetry-export.md). Новые runtime descriptors и привязка live-сегментов остаются отдельным последующим этапом.

## Решение

Добавить в Admin → Calls кнопку **Export telemetry**: выбор периода, обязательная причина доступа, фоновое создание файла и скачивание. Основной формат — ZIP с JSON Lines и небольшими обычными JSON-файлами для описания и сводки. Полный текстовый экспорт доступен superadmin. Запрос не вызывает Twilio/OpenAI и не запускает повторную транскрипцию или оценку.

Единица анализа — попытка звонка (`call_attempts.id`), с привязанным заданием (`call_briefs.id`), точным исполненным планом, транскрипциями и всей сохранённой технической историей. Данные подготовки, включая ошибки до появления звонка, входят отдельным разделом.

Первую версию сделать на существующих PostgreSQL, Fastify и внешнем worker, без Redis и обязательного нового облачного сервиса. Временный результат хранить зашифрованными ограниченными частями в PostgreSQL с TTL. Файловое хранилище абстрагировать: при росте объёма его можно заменить приватным object storage без изменения API и формата.

## Граница «всей телеметрии»

Выгружаем все доступные сохранённые данные выбранной области через явную схему полей. Не делаем `SELECT *`: новые столбцы, секреты и служебные токены не должны автоматически появляться в скачиваемом файле.

| Раздел архива | Состав |
| --- | --- |
| `calls.jsonl` | Задание, владелец-ID, языковой контекст, профиль, разрешённые факты, цель, контекст, статусы и timestamps, ссылки на текущие версии. Имена/телефон и тексты присутствуют только у неудалённых данных в полном экспорте. |
| `attempts.jsonl` | Все попытки выбранных заданий; `selectedInPeriod` отличает целевые попытки от контекста. Provider IDs, статусы, начало/конец, причины, ограничения, compilation/receipt IDs, исполненный snapshot и hash. |
| `events.jsonl` | Все сохранённые `call_events` выбранных заданий, включая события подготовки до периода и постобработку после него. Сохранять и `occurredAt`, и время записи `createdAt`; порядок внутри задания — `sequence`. |
| `plans.jsonl` | Все сохранённые версии compilation, approvals, review receipts и policies, связи/hash, исходный и показанный при согласовании текст. |
| `transcripts.jsonl` | Сохранённые live-сегменты, текущее состояние final ASR, сохранившиеся `post_call_transcription_chunks` и **все** final revisions: текст, роли, segment IDs, тайминги, язык/модель там, где сохранены, источник и revision/hash. Различать виды записей через `recordType`. |
| `text-artifacts.jsonl` | Переводы, summaries, review/clarification artifacts; их статусы, ошибки, source revision/hash, язык, generator version, payload и сохранившиеся промежуточные chunks. |
| `recordings.jsonl` | Согласие, время, длительность, каналы, provider IDs, состояние записи/удаления и retention. Аудиобайлы в первую версию не входят. |
| `assessments.jsonl` | AI-оценка разговора и достижения цели, evidence, evaluator version, deadline, source/plan hashes. Не смешивать с ручной оценкой. |
| `feedback.jsonl` | Все feedback/outcome revisions, происхождение оценки, категориальные значения и сохранившиеся комментарии. |
| `provider-operations.jsonl` | Операции, результаты и исходный usage; supplements и effective usage отдельно обозначены. Requested/actual model, request/response IDs, duration, HTTP/error codes, raw usage, pricing version, reported cost и расчётные суммы с основанием. |
| `jobs.jsonl` | Связанные задания, поколения, попытки, повторы, ошибки и действия админов по ним. Не экспортировать работающие capability/lease-токены. |
| `preparations.jsonl` | Создание/перекомпиляция, статусы, ошибки, timestamps, язык и связи. В том числе неуспешная подготовка без `call_brief_id`. Отдельные операции/расходы таких подготовок тоже включаются. |
| `credits.jsonl` | Только связанные резервы/списания/возвраты кредитов и spending reservations, с исходными основаниями. Не вся финансовая история пользователя. |
| `audit.jsonl` | Связанные approval requests и application audit, job admin events, evidence удаления/чтения. Поля и metadata проходят отдельный allowlist; сохранённый старый audit не должен восстанавливать удалённые provider IDs/тексты. |
| `provider-billing.jsonl` | Контекст сверки: имеющиеся account/project totals по пересекающимся UTC-дням с явной областью действия. Не распределять их произвольно по звонкам и не складывать с ledger. |

Во всех записях есть `schemaVersion`, `recordType`, исходный ID и доступные foreign keys. Денежные значения bigint/micros выдавать десятичными строками + currency; неизвестные значения — `null`, а не ноль. Не выводить длительность аудио из длительности всего звонка без отдельной отметки о расчёте.

Записи дедуплицировать по источнику и ID. Связи строить не только по `provider_operations.call_brief_id`: учитывать preparation, target brief при перекомпиляции, attempt, recording, text artifact и job. Иначе часть подготовки/ASR/переводов выпадет. Связанные сущности читать отдельными пакетами: один большой JOIN всех one-to-many таблиц размножит события и стоимость.

### Что исторически восстановить невозможно

- SSE `CallEvent` и durable `DurableCallEvent` — разные сущности. Промежуточные transcript deltas не являются сохранённым replay-журналом.
- В `transcript_segments` нет `call_attempt_id`; историческую связь нельзя объявлять достоверной по одной близости timestamp. Экспортировать `scope: call`, `attemptId: null`, `attribution: unavailable`, если прямой связи нет.
- `call_recordings` сейчас уникальна по brief; `beginRecording` отклоняет вторую запись этого задания. Это **не** архив нескольких записей/попыток. Не приписывать существующую запись всем попыткам.
- Текущая `final_transcripts` изменяется при повторном ASR, но успешные ревизии сохранены отдельно. Метаданные старой ASR-операции нужно связывать по сохранённым ключам, а не подставлять текущую модель во все ревизии.
- Input preparation обнуляется после завершения по ограничению таблицы. Исходный ввод неуспешной подготовки часто уже отсутствует.
- Полные websocket frames, точные прежние runtime prompts/настройки всех сессий и каждый низкоуровневый сбой не составляют единого сохранённого журнала. Наличие request ID или версии compilation не доказывает наличие полного запроса модели.
- Аудио после retention и пользовательского удаления не возвращается; текст может сохраняться после удаления только аудио. Удаление звонка и удаление аудио различаются.
- Provider usage может отсутствовать после транспортной ошибки; billing поступает поздно. Такие пропуски не исправляются экспортом.

В manifest и записях обозначать причины: `not_captured`, `legacy_unattributed`, `pending`, `not_applicable`, `deleted`, `retention_expired`, `unknown`. `complete` означает полный экспорт доступных источников, а не полную запись всего происходившего в сети.

Ошибка чтения/расшифровки существующего payload или неподдерживаемая версия не равны отсутствующим историческим данным: генерация завершается ошибкой с безопасным кодом и ID источника. Нельзя молча пропускать такие строки и публиковать успешный экспорт. Пустой набор, напротив, является корректным результатом с нулевыми счётчиками.

## Период и интерфейс

Кнопки: **Today**, **Yesterday**, **Last 7 days**, **Last 30 days**, **Previous month**, **Custom**. Показывать фактические начало/конец и `Europe/Zurich`; сервер вычисляет границы в IANA-зоне, хранит UTC. Last 7/30 days — текущий местный день до момента запроса плюс предыдущие 6/29 календарных дней. Previous month — полный предыдущий календарный месяц. Custom — выбранные даты включительно для пользователя, исключительная следующая полночь для API. Дни перехода DST не равны обязательно 24 часам.

Основная выборка: `attempt.started_at >= from AND attempt.started_at < to`. Начатый до полуночи звонок относится ко дню начала, даже если завершился позже. История связанного задания читается целиком до snapshot, поэтому ASR/summary следующего дня не теряются. Несмежные выгрузки могут иметь общие контекстные строки; их ID и `selectedInPeriod` позволяют корректно объединять данные.

По умолчанию включать самостоятельные подготовки, созданные в периоде, даже если попытки звонка нет. Также включать все подготовки выбранных звонков вне периода. Отдельные счётчики: целевые попытки, контекстные попытки, задания, самостоятельные подготовки. Summary по звонкам считает только целевые попытки; стоимость общего контекста подготовки не приписывает каждой повторной попытке.

Экспорт не наследует незаметно status/locale-фильтры таблицы: окно явно показывает «All calls in this period». Позднее можно добавить видимый режим текущих фильтров с отдельным контрактом. Причина — тот же диапазон 3–500 символов, можно предложить готовый редактируемый текст для анализа качества.

После создания отображать статус, фазу, обработанные сущности/размер и кнопку отмены; процент показывать только при известном знаменателе. Закрытие вкладки не отменяет работу. Список собственных недавних экспортов позволяет вернуться и скачать файл повторно до TTL. После готовности — число звонков, наличие незавершённых данных, размер, срок доступности и Download.

## Формат

```text
shprohli-telemetry_<from>_<to>_<export-id>.zip
  manifest.json
  summary.json
  README.txt
  schema.json
  data/calls.jsonl
  data/attempts.jsonl
  data/events.jsonl
  data/transcripts.jsonl
  data/... остальные разделы ...
```

JSON Lines: UTF-8, один JSON-объект в строке, переносы внутри текстов экранируются JSON-сериализатором. Подходит для последовательного чтения Python/аналитикой без загрузки архива в память. Не следует обещать, что любой AI-интерфейс примет ZIP или месячный объём: после распаковки можно выбрать конкретные файлы/звонки. CSV/PDF не подходят как основной формат вложенных версий, событий и evidence. Для одиночного звонка впоследствии можно добавить обычный `call.json` на тех же DTO.

`manifest.json`: версия формата, export ID, requestedAt, snapshotCapturedAt, generatedAt, UTC-границы и timezone, правило отбора, export generator/build version, версии схем, режим данных, список источников/исключений, количества, SHA-256 и размеры каждого data-файла, признаки неполноты исходных данных. Build экспорта не обозначать как build исторического звонка.

`summary.json`: количество попыток и исходов, consent/failure stages, доступность live/final/summary, pending processing, latency и длительности только при наличии измерений; число образцов и доля неизвестных. Раздельные actual/calculated/unknown costs и валюты. Отдельно факт разговора, AI goal assessment и пользовательский feedback. Сводку вычислять из тех же экспортированных строк.

## Согласованность, исполнение и хранение

1. POST валидирует запрос и права, применяет лимиты, атомарно создаёт export request + job + audit. Идемпотентность по `(actorId, requestId)`; другой payload с тем же ID возвращает conflict.
2. Добавить `telemetry_export` в durable jobs с отдельным `export_id`, FK, target constraint, lease fencing и ограниченными retry. Обновить enums, System UI/контракты, memory adapter и heartbeat. Один выделенный consumer обрабатывает только exports; основной consumer не получает этот тип. Подключить к внешнему worker отдельным циклом и ограниченным pool, с возможностью отдельного процесса.
3. Worker сначала проверяет действующие права автора. Одно чтение в PostgreSQL `REPEATABLE READ READ ONLY` фиксирует набор целевых попыток, все связанные источники и количества. Все source-selects используют **то же соединение/transaction handle**. Методы, которые самостоятельно ходят через обычный pool, здесь не подходят.
4. Время snapshot относится к фактическому началу чтения worker, не к нажатию кнопки. Простая добавка `updated_at <= requestedAt` не воссоздаёт прошлое состояние изменяемой строки. Нельзя обещать исторический snapshot на момент клика без отдельной системы версий.
5. Читать keyset/cursor пакетами, по 100–250 сущностей, с полным tie-breaker ID. Большие дочерние наборы тоже читать постранично. Сериализация/сжатие через streams с backpressure. Ограничить размер одиночной записи, не вычитывать весь архив одним `JSON.stringify` или `Promise.all`.
6. ZIP строить последовательно, одновременно считать counts/hashes. Manifest можно записать последним. Его содержимое не включает собственную checksum; checksum всего архива хранится в metadata запроса. Писать сжатые байты порциями в отдельное соединение: части привязаны к export ID и generation, шифруются до сохранения. Plaintext-файл во временной папке не нужен.
7. Таблицы: `admin_telemetry_exports` (владелец, период, состояние, generation, сроки, размер/hash), `admin_telemetry_export_parts` (generation, номер части, зашифрованный payload), `admin_telemetry_export_members` (связи с calls/preparations/owners), immutable `admin_telemetry_export_events` (создание, попытки, готовность, начало/конец передачи, отказ/отмена/удаление). Причину доступа хранить с ограниченным доступом; без текста разговора в audit.
8. Публиковать `ready` только после полного ZIP, проверки счётчиков/контрольных сумм, действующей lease, прав автора и проверки удаления исходных данных. Недостроенные поколения никогда не скачиваются. При падении до завершения чтения начать новое поколение с **новым snapshot**, удалив прежние части; нельзя продолжить потерянную SQL-транзакцию с прежней гарантией согласованности.
9. Скачивание читает готовые зашифрованные части последовательно через API; browser не собирает многомегабайтный `Blob`. Проверяются целостность и порядок частей. Ошибка/обрыв даёт неполный download, а не успешный пустой ZIP. Готовый архив можно повторно скачать; generation не пересобирается при сетевом обрыве.
10. TTL файла — 24 часа после готовности; сборщик удаляет также просроченные/отменённые/сбойные части. Метаданные audit сохраняются отдельно. Проверка TTL на скачивании обязательна даже при остановленном cleanup. Фоновое создание не зависит от медленного браузера и не удерживает SQL snapshot на время скачивания.

Начальные **предлагаемые**, а не измеренные пределы: 31 календарный день на экспорт; 10 000 целевых попыток; 250 MiB несжатых данных; 1 MiB на сохраняемую часть; одна генерация на всю установку одновременно; один незавершённый запрос на администратора; read snapshot до 60 секунд. Добавить также общий лимит места и числа строк/подготовок. Уточнить значения нагрузочным тестом. Превышение означает понятную ошибку с предложением разделить период, **без обрезания данных**. Для долгих периодов увеличивать инфраструктуру осознанно, а не отключать пределы.

Отдельный индекс для отбора `call_attempts(started_at, id)` отсутствует среди просмотренных migrations; добавить после EXPLAIN. Проверить индексы связей preparations/targets, provider operations, child-таблиц и members для удаления. Пользовательский индекс `(user_id, started_at)` не заменяет глобальную выборку по периоду.

Ограничение snapshot защищает обслуживание базы от бесконечного удержания старых версий. Архитектура с PostgreSQL-частями подходит текущему ограниченному продукту; измерить WAL/backup/cleanup-нагрузку. При регулярных крупных архивах перенести parts в object storage с приватным доступом/TTL, сохранив durable metadata и API-прокси.

## Доступ и удаление

Полный экспорт содержит оригинальные транскрипции и персональные данные. Superadmin + причина соответствуют существующей модели sensitive-access. Проверять актуальную роль/аккаунт/session при создании, просмотре и каждом скачивании; доступ к файлу только автору экспорта. Защита Origin для действий, rate limits, `Cache-Control: private, no-store`, безопасное `Content-Disposition`, отсутствие публичных URL. Reason/телефон/текст не помещать в URL и операционные логи. Пароли, ключи, cookie, auth headers, verification grants и recipient-contact HMAC в формат не входят.

Уже удалённые звонки представлять технической tombstone-записью с причиной недоступности содержимого. Не пытаться восстановить приватные сведения из старых audit, raw payload или provider ID. При pending account deletion исключать контент сразу, а не ждать завершения очереди.

Созданный snapshot может содержать данные, удалённые во время генерации. Одной финальной проверки `data_deleted_at` недостаточно из-за гонки с публикацией. Нужна атомарная координация экспорта и удаления:

- Членство exports → calls/preparations/owners сохраняется для invalidation.
- При запросе account deletion и при локальном удалении содержимого — атомарно отозвать затронутые готовые exports и отменить выполняющиеся. Части удалить; поздняя lease-публикация не должна вернуть `ready`.
- Закрыть гонку «удаление произошло раньше записи membership»: ввести счётчик privacy generation, увеличиваемый в тех же транзакциях удаления/запроса account deletion. Захватить его в source snapshot и сверить при регистрации membership и публикации под коротким общим барьером, которым пользуется deletion. При изменении счётчика незавершённую генерацию перезапустить/отменить; для готовых файлов отзывать только затронутые membership.
- Единый порядок захвата этого барьера и существующих owner/call/job locks документировать и тестировать. Не держать барьер или row locks всё время сборки/скачивания.
- При выдаче проверять состояние/revocation между ограниченными частями. Данные, переданные до отзыва, вернуть невозможно; audit `download_completed` означает окончание серверной передачи, а не подтверждение хранения браузером.
- Включить новое ciphertext-хранилище в encryption inventory, rotation/recovery tests и cleanup после восстановления backup. Зашифрованные временные части также могут попасть в backup: правило replay удаления сохраняется.

Не называть режим с убранным номером телефона «анонимным»: имена, адреса и другие сведения остаются в свободном тексте. Если потребуется отдельная выгрузка для внешних систем, это дополнительный режим с явно описанным качеством редактирования.

## API

| Метод | Назначение |
| --- | --- |
| `POST /api/admin/telemetry-exports` | Создать; body: requestId, preset или local dates, timezone, reason. Ответ `202` с ID, вычисленными границами и состоянием. |
| `GET /api/admin/telemetry-exports` | Собственные экспорты, пагинация; без transcript payload. |
| `GET /api/admin/telemetry-exports/:id` | Статус/фаза, progress, counts, failure code, snapshot time, expiresAt, размер/hash. |
| `POST /api/admin/telemetry-exports/:id/cancel` | Идемпотентная отмена, audit, недоступность результата и очистка. |
| `POST /api/admin/telemetry-exports/:id/retry` | Только допустимые transient failures, новое поколение, ограниченный budget. Ошибка данных/лимита требует исправления или нового запроса. |
| `GET /api/admin/telemetry-exports/:id/download` | Только ready, текущая session автора и superadmin; поток attachment без bearer token в URL. |

UI-состояния: queued, running, ready, failed, cancelled, expired, revoked. Они проецируются из export request/job; job `succeeded` отдельно от срока доступности файла. Междоменное web/API скачивание проверить с текущей cookie/CORS-топологией; при необходимости дать same-origin server route, проксирующий поток без буферизации и без обхода API-авторизации.

## Что улучшить в сборе новых данных

Сам экспорт полезен уже на нынешних данных. Для последующей точной диагностики отдельно добавить:

1. `call_attempt_id` и устойчивую provider/session/item/response-связь к новым live-сегментам; миграция старых данных не должна угадывать привязку.
2. Сохраняемый per-attempt/session runtime descriptor: app build SHA, версии prompt/agent/tool policy, фактические model IDs, voice/VAD, audio format и влияющие feature flags. Точные сгенерированные instructions при необходимости хранить зашифрованно и удалять вместе с call; никаких API keys.
3. Измерения interruption/playback/turn latency и контролируемые error codes с request correlation. Добавлять только нужные диагностические события, не бесконечный дамп всех аудиофреймов. Данные до согласия не превращать в сохранённый transcript.

Эти добавления действуют только на будущие звонки. Их версии и момент начала покрытия должны быть видны в manifest.

## Проверки и порядок реализации

1. Контракты/DTO + таблица покрытия источников, period resolver и export repository с общим transaction handle. Фикстура содержит минимум два звонка, старое задание с новым стартом, несколько ASR revisions, неуспешную подготовку без brief, поздний usage supplement и удалённый контент.
2. Миграция jobs/requests/parts/members/audit, dedicated consumer, шифрование, TTL, idempotency, snapshot и пределы. Удаление/отзыв внедрить до включения скачивания.
3. API и UI, schema/README/summary, диагностический статус в Admin System, feature flag и runtime/config документация.
4. После приёмки основной выгрузки — новые runtime descriptor и привязка live-сегментов.

Обязательные acceptance checks:

- Установить фикстурный список источников/ID и убедиться, что экспорт содержит **все** ожидаемые записи, включая операции, связанные только через preparation/attempt/recording/artifact; отсутствуют дубли от JOIN.
- Yesterday/7 days/30 days/month/custom, Zurich DST, полночь, полуинтервал, одинаковые timestamps и keyset-пагинация. Brief вне периода со стартом внутри включается.
- Конкурентный callback, final ASR и поздняя цена не смешивают состояния разных snapshot. Повтор после crash создаёт новое поколение и новый snapshot.
- Нельзя скачать незавершённый/повреждённый архив. Validate ZIP, JSONL/schema, counts, hashes, unicode/multiline; лимит размера даёт failure без скрытого усечения.
- Worker kill/restart, потеря lease, два worker, retry, disk/database/storage errors, остановленный cleanup, истечение TTL и обрыв download.
- User/admin/чужой superadmin не получают содержимое; отзыв роли/session применяется к повторному скачиванию. Изменение роли во время генерации блокирует публикацию.
- Call/account deletion до membership, во время snapshot, между финальной проверкой и ready, после ready и во время передачи не восстанавливает доступ к содержимому. Проверить отсутствие deadlock и позднего resurrection.
- Схема не содержит секретов; удалённые PII не просачиваются через audit/raw provider metadata. Проверены ротация и restore/deletion replay.
- Месячная нагрузочная фикстура: ограниченная память, размер/WAL, время snapshot, SQL query plan, параллельное обслуживание обычных звонков/ASR/retention. Численные SLA объявить только по измерению.
- Browser: выбор периода, причина, закрытие/повторное открытие страницы, progress, keyboard/focus, скачать пустой корректный архив при нуле данных, большой файл без полного Blob в памяти.

## Внешняя техническая проверка

- [PostgreSQL 17: transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-REPEATABLE-READ): successive reads одной Repeatable Read транзакции используют один snapshot; обычный Read Committed не даёт этой гарантии между запросами.
- [Node.js 22: streams](https://nodejs.org/docs/latest-v22.x/api/stream.html): потоковая передача/backpressure и обработка ошибок pipeline для ограничения буферизации.
- [JSON Lines](https://jsonlines.org/): UTF-8, JSON-значение на каждой строке и разделитель newline.
